## 1. 结论与边界

建议保留现有“业务状态变化 → 已签名通知任务 → Worker 抢占重试”的主链路，在发送边界增加交行开放平台适配，并修正业务报文中的确定性差异。不是把 `notify_url` 替换成银行 URL 就能完成接入。

当前涉及三段协议：

1. 名创 → 本平台：`POST /api/common/mcNotify`，独立 key2 验签，先可靠保存核销事件。
2. 本平台 → 交行业务接收方：V1.2 第 2.5、2.6 节定义业务字段，使用商户级 `signKey/keyId` 和 HMAC-SM3。
3. 本平台 → 交行金融开放平台：接入包提供 `J_IEP_001_2104/v1`，通过开放平台公共参数及 RSA/SM2 签名发送，业务区为 `head/body`，其中 `body.trx_data_imprt` 承载通知信息、`body.protocol` 承载协议信息。

第 3 段是此次接入的主要缺口。第 2 段业务认证与第 3 段网关认证应分别处理。现有 V1.2 并未被银行接入包明确废止，不能自行去掉业务 `sign/keyId`，也不能把网关私钥当作商户 signKey。

**本轮已确认范围：** 尽管 `2104` 的附件功能说明仅写“名创优品商户出券结果”，用户已明确两类通知都使用该接口。以下按两类通知统一接入同一银行传输适配器设计；各自保留业务字段、签名和业务状态含义。两类业务具体如何区分、是否使用不同 protocol，仍需明确。

## 3. 当前实现与差异

### 3.1 已有能力可继续复用

- `V12MessageSignatures` 已区分订单/核销字段集，支持 ASCII 排序、空字符串、完整 32 字节 HMAC-SM3 和 keyId。
- `V1MerchantNotifyPayloadSigner` 创建订单终态通知和作废通知。
- `V12RedemptionNotifyPayloadSigner` 已生成名创消费核销 `state_type=3/use_state=2`，保留名创实际 `use_time`，`invalid_time` 为空。
- `MybatisMinisoWriteOffStore` 在同一事务内保存已签名任务、更新凭据并完成事件；HTTP 发送独立重试。
- `recharge_notify_task`、`RechargeNotifyWorkerService` 已具备任务幂等、抢占、租约恢复、失败重试和次数耗尽转人工。
- `HttpMerchantNotifyClientAdapter` 已在发送前核对可信商户、任务订单身份、历史 keyId 和业务签名；撤销密钥禁止发送，正常重试不重新签名。

### 3.2 P0：缺少开放平台封装、签名和响应适配

证据：`HttpMerchantNotifyClientAdapter.java:96` 直接以 `application/json` 把 `request.payload()` 发送到 `request.notifyUrl()`，随后从响应根节点读取 code。

如果将银行网关直接配置为 notify_url，当前请求将缺少外层 form 公共参数、网关签名及 `head/body` 业务封装；即使收到标准网关响应，也会因 code 路径不匹配而误判。必须增加专用传输实现。

### 3.3 P0：空 notify_url 的业务跳过规则与固定网关路由可能冲突

证据：`RechargeOutboxWorkerService.java:1030` 和 `:1050` 在创建任务前检查订单 URL；`MybatisMinisoWriteOffStore.java:247` 同样先检查订单 URL。任务持久化、Worker 和到期扫描还有空 URL 拦截及清理。

如果交行约定“通知使用固定网关及商户协议配置，下单不必带 notify_url”，只新增发送器不会生成任务。应在任务生成前解析通知目的地，按商户/环境/通知类型决定是否需要投递；配置缺失应作为待恢复错误，不能当成“无需通知”。

是否改变交行下单 notify_url 的必填/可空语义，需要确认并同步对外文档。其他直连商户原有空地址跳过语义可继续保留。

### 3.4 P0：作废通知的状态语义错误

证据：`V1MerchantNotifyPayloadSigner.java:24`、`:25`、`:69`、`:70` 把作废固定写为 `state_type=1/use_state=2`。V1.2 1.4.3 定义此组合为“已兑换”，不是作废；现有签名器测试也固定断言这个组合，所以测试通过不代表业务语义正确。

建议建立具名状态映射：本项目名创通用类，已核销使用 `3/2`，作废使用 `3/3`；其他类型按真实凭据分类映射，不能把所有商品一刀切为 3。第 2.6 节是核销状态变更通知，不应把实际消费和主动作废合并成同一业务事实。

此外 `createWriteOffNotifyTask` 当前用 `clock.instant()` 作为 invalid_time，可能记录补偿执行时间而非作废发生时间。建议读取并冻结可信作废事实时间；缺少事实时如何处理须先确认，不能自行编造时间。应回归“作废结果 → 查询接口 → 通知”的状态与时间一致性。

### 3.5 P1：订单通知金额 JSON 类型不符合文档

证据：`V1MerchantNotifyPayloadSigner.java:38` 返回 `Map<String,String>`，`:45`、`:47` 将金额转换为字符串；持久化后为 `"total_price":"1950"`，文档要求 `"total_price":1950`。

建议使用明确业务 DTO 或 `Map<String,Object>`，在签名前就确定最终字段类型，金额保留整数分。公共签名组件已支持整数和字符串，同一整数值的签名规范化文本相同。不要在正常重试时修改历史报文类型或重签。

现有 `type` 固定为 1、`total_settle_price` 等于 orderPrice。对于当前直充及旧逻辑这是现状，不应在缺少结算定义时擅自更改。若交行确认总价与总结算价不同，需扩充订单可信金额快照并明确数据来源，不能把供应商成本直接当结算价。

### 3.6 P1：nonce 长度满足，但订单/作废并非随机生成

证据：`V1MerchantNotifyPayloadSigner.java:88` 使用订单号、状态和秒级时间摘要截取 32 字符。文档要求 32 位随机字符串；名创核销签名器已使用 `SecureRandom` 生成 16 字节并编码成 32 位 Hex。

建议两类通知统一在首次创建任务时生成随机 nonce，并使用 13 位毫秒字符串 timestamp 以统一输出。文档同时允许 10 位和 13 位，现有秒级 timestamp 本身不是违规。重试仍保持原业务 timestamp、nonce、keyId、sign。

### 3.7 P1：可靠投递边界需随新通道一起补齐

`MybatisRechargeNotifyTaskAdapter` 抢占时检查 retryCount/状态/租约，但 `markSuccess/markFailed/markManualRequired` 只按 taskId 更新，未绑定本次租约或版本。旧 Worker 超时后恢复，可能覆盖新 Worker 的处理结果。银行调用耗时增加后该风险更明显。

建议领取任务返回 claimToken/version，所有结果回写使用 CAS；超时总预算必须小于租约，必要时续租。业务幂等仍由银行接收方保障，不能把租约当成网络请求绝不会重复的承诺。

当前发送失败只有 success 布尔和错误文本；建议区分临时失败、结果未知、配置/报文错误、密钥撤销。网络超时和 P 状态保留待重试；密钥撤销、无法识别的协议及确定性报文错误转人工或等待配置恢复，避免无意义地消耗全部次数。

## 4. 推荐修改方案

### 4.1 选择官方 SDK 适配

**方案 A（推荐）：复用官方 SDK 2.2.6，封装在 infrastructure。** 使用所附 2104 请求/响应结构，委托 SDK 完成网关外层参数、签名、发送和响应验签；本项目负责业务 payload、路由、双层成功判断及重试分类。优点是贴近银行样例、减少自行实现签名差异；代价是需要验证 JDK 21、当前依赖和 SDK 日志行为。

**方案 B：自行实现开放平台 form 协议。** 可复用现有 JDK HttpClient，但必须完整实现 URL 路径及参数签名、RSA/SM2、原文响应验签和错误处理，并用银行固定向量交叉验证。只有 SDK 在当前栈确有不可解决的不兼容时再选该方案，维护和验证成本更高。

不建议为本次两个通知额外建设独立中转服务，也不在失败时自动切回直连。失败后改变发送目的地会破坏幂等、归属及审计依据。

### 4.2 组件职责

建议的新增名称是方案建议，并非当前已有代码：

1. application 增加 `MerchantNotifyRoutePort`，输入可信 orgCode、通知类型及订单上下文，返回通知投递渠道和目的地。区分 `DIRECT_JSON`、`BOCOM_OPENAPI`，不能通过 URL 包含 bankcomm 或供应商名为 MINISO 推断渠道。
2. application 增加通用通知目标模型与 `notifyType` 显式传递；保留 `MerchantNotifyClientPort` 作为发送端口，`MerchantNotifyRequest` 携带 routeId/version/notifyType。
3. infrastructure 增加 `RoutingMerchantNotifyClientAdapter`、`BocomOpenApiMerchantNotifyClientAdapter` 和 `Bocom2104PayloadCodec`。原直连 HTTP 适配器继续承担直连商户。
4. 把现有 HTTP 适配器中的 V1.2 业务身份及历史密钥复核提取为共享发送前守卫，两种通道都必须经过；通道适配器再完成各自的传输认证。
5. `V1MerchantNotifyPayloadSigner` 修正金额类型、随机 nonce 和作废映射；`V12RedemptionNotifyPayloadSigner` 保留真实消费核销语义，可共用 nonce/时间工具。`V12MessageSignatures` 保留现有协议算法。
6. 任务创建侧统一先解析目标，再创建已签名 payload 和冻结路由的任务；名创侧保持任务、凭据和事件完成的原子事务。
7. Worker 继续只投递已存在的业务报文，增加错误分类和 claim CAS。新增 infrastructure 依赖不进入 domain。

### 4.3 报文处理与双层签名

推荐流程：

`可信业务事实 → V1.2业务签名 → 持久化payload及目标 → 发送前业务验签/密钥状态检查 → 2104业务封装 → SDK网关签名和HTTPS发送 → SDK银行响应验签 → 平台及业务结果判定 → CAS回写任务`。

若交行确认 `trx_data_imprt` 承载 JSON 字符串，则把已存储 payload 原文作为该字段的字符串值，不变成嵌套对象，也不自行替换逗号、等号或 keyId 大小写。外层 JSON 对字符串的引号转义属于正常封装，接收方读取后应恢复相同业务文本。若银行要求冒号分隔格式，必须先取得完整字段、分隔符、空值和特殊字符规则，再实现独立 codec；附件短示例不足以确定此规则。

`head/body` 是 `biz_content` 的内容，不是整个网络请求。外层 form、URL 编码及网关签名交由 SDK；HMAC 业务 sign 放在业务通知内部，网关 sign 放在外层，两者不可互相覆盖。

业务重试不重新签名；网关每次物理请求按网关时效要求生成外层 timestamp 和签名。`msg_id` 重试复用还是重新生成，须由交行明确去重/时效规则；业务 taskId 和订单事件身份始终稳定，并记录每次尝试的 msgId/refMsgId 关联。

### 4.4 结果判定

成功至少同时满足：传输成功、SDK 银行验签通过、`biz_state=S`、`body.code` 为协议定义的 200。`rsp_code` 用于诊断与错误分类，取得本接口成功码清单后再实施校验，不能把通用示例 `0000` 直接当唯一成功码。

- `biz_state=S/body.code!=200`：业务未成功，不能关闭通知。
- `biz_state=F`：分类为失败；`P`：结果未确定，保留待恢复状态。
- body 缺失、空响应、解析失败、验签失败：都不能认为成功。
- 超时、断网、5xx：可能银行已接收，保留任务、按约定退避和幂等重试，不回滚充值/核销事实，不因此退款，也不重发供应商发券。

直连通道继续按直连业务响应 `code=200` 判定。两种通道的 ACK 解析不能混用。银行成功 ACK 是否代表权益中心已持久接收、是否还需要查结果，也需联调确认；在确认前只能称“银行接口确认成功”。

### 4.5 配置、数据库与依赖

配置建议放在 `trade.engine.notify.bocom.*`：enabled、测试环境 gateway-base-url、app-id、signature-algorithm、private-key-ref、bank-public-key-ref、connect-timeout-ms、read-timeout-ms。商户路由按 orgCode/环境/通知类型配置 routeId/version 和实际 protocol。平台 app-id 与本服务 V1 业务 app_id 分开命名与管理。

网关私钥、银行公钥引用与商户 HMAC 密钥独立管理；不复制样例私钥，不提交环境密钥。样例中的 `ignoreSSLHostnameVerifier()` 不直接带入项目，实际使用正确主机名及有效证书。

任务表推荐增加 `delivery_channel/route_id/route_version`，必要时保存非秘密的 protocol 快照或保留不可变路由版本；继续存储业务 payload。任务里的 notify_url 可继续作为实际投递目标，银行任务填经可信配置解析后的网关 URL，并同步更新其 DTO/DDL COMMENT。原订单 notify_url 的含义单独保留，避免混淆。

这样扫描及空目标清理仍只处理“没有实际目的地”的任务。必须同步修改所有任务生成入口，不能只修改 Worker。既有 dev/test 待发任务如何显式重建/保留应有清单；不自动把历史任务批量改成银行通道。

为 claim CAS 增加 version 或 claim_token；按需要增加尝试关联记录或审计字段，记录 msgId/refMsgId、有限错误码及结果，不保存密钥或完整敏感响应。

SDK 用可重复构建的 Maven 制品方式接入（如团队私有制品库及校验和），避免 systemPath 绑定个人本地目录。只引入所需 SDK/DTO 和必要依赖，不整包复制附件 `lib`。当前项目 BC 为 1.70，附件为 1.60，Jackson/SLF4J/Logback 也明显跨代，必须用当前受管版本做编译、密码运算和启动验证，不能直接降级覆盖 Spring Boot 依赖。

第三方 SDK 存在验签失败打印业务原文的日志分支，需用专门日志过滤/受控日志策略屏蔽该内容；由本项目边界写脱敏且限频的异常栈及 taskId/orgCode/orderId/msgId 错误分类。指标避免把订单号和 msgId 当标签。

## 5. 必须先由交行明确的事项

1. **通知区分**：2.5、2.6 都走 2104 已获用户确认，不再作为待确认问题；仍需明确同一接口如何区分两类业务，是否使用不同 protocol 或其他明确字段。
2. **trx_data_imprt 格式**：完整 V1.2 JSON 字符串还是 `key:value` 格式；完整成功/失败/核销/作废样本；keyId 是否原样保留。2500 长度按字符还是 UTF-8 字节计算。
3. **真实协议参数**：每类通知实际 protocol、测试网关域名/端口、开放平台 appId、授权方式和 RSA/SM2 选择。文档标“不需要OAuth2”不等于不需要开放平台 appId/签名。
4. **回调目标语义**：固定网关模式是否允许下单 notify_url 为空，是否继续使用该字段表达开启通知；不能由实现方自行修改。
5. **ACK 与幂等**：本接口 rsp_code 成功码、body.code 类型和真实响应、P/超时重试、msg_id 规则、接收去重键；原业务 timestamp 已过时的合法重试如何接收。重放防护不能简单拒绝所有旧 timestamp，否则违背 V1.2 保留原文重试。
6. **业务一致性**：名创状态 3/2 和 3/3 是否获交行确认，是否要求发券通知先于消费核销通知；若有顺序要求再按订单串行投递，避免加无依据的跨任务阻塞。金额结算含义及作废事实时间来源一并确认。

未明确的部分可以继续做分析、测试设计和确定性代码准备；正式实现相应语义前应按 AGENTS.md 停下确认。
