# 交行直充业务系统需求文档

## 1. 文档说明

### 1.1 文档目的

本文档用于说明交行直充业务系统需要支持的业务能力、接口契约、业务规则、异常处理和验收标准。

本文档只描述“系统要做什么、对外表现是什么、验收口径是什么”。具体实现方案以高可用方案设计和详细设计文档为准。

### 1.2 适用范围

本期建设范围包括：

1. 商户对接直充类产品，完成 token 获取、直充下单、订单查询、作废申请、订单状态回调和核销状态回调。
2. 新服务承接直充订单受理、业务校验、余额控制、异步处理、供应商派单、回调通知和异常补偿。
3. 系统保留与旧卡管系统的数据兼容，确保运营查询、售后排查、财务对账可以延续。
4. 系统支持灰度切流和回滚，避免新旧系统在同一商户同一交易范围内重复受理或重复扣款。

本期不直接覆盖：

1. 非直充产品的完整重构。
2. 运营后台、财务后台和供应商后台的完整产品化改造。
3. 旧卡券、批采、客诉补发等非直充主链路重构。
4. 中间件部署细节和底层实现参数。

### 1.3 优先级说明

| 优先级 | 含义 |
| --- | --- |
| P0 | 首期上线必须满足，否则可能影响下单、资金、订单一致性或商户联调。 |
| P1 | 首期建议满足，影响运维效率、排障效率、灰度安全或用户体验。 |
| P2 | 后续优化项，不阻塞首期灰度。 |

## 2. 业务目标

商户通过平台直充接口创建充值类订单。平台接收订单后，需要完成安全校验、业务校验、订单记录、余额控制、供应商处理、订单状态回传和售后追踪。

下单接口返回成功只表示平台已受理订单，不代表充值最终成功。最终结果以订单查询或平台回调为准。

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| G-01 | 系统必须支持直充订单创建、查询、作废、订单状态回调和核销状态回调。 | P0 |
| G-02 | 系统必须保证同一商户订单号不会重复创建、重复扣款或重复派单。 | P0 |
| G-03 | 系统必须保证可识别订单最终有记录可查，包括业务校验失败订单。 | P0 |
| G-04 | 系统必须保证余额、订单、供应商处理和回调状态最终可对账、可追溯。 | P0 |
| G-05 | 系统在关键依赖异常时必须保护资金安全，不能为了继续接单而绕过必要校验或余额控制。 | P0 |
| G-06 | 系统必须支持异常补偿和人工处理，避免订单长时间停留在不可恢复状态。 | P0 |

## 3. 角色与系统边界

| 角色/系统 | 职责 |
| --- | --- |
| 商户系统 | 调用平台接口下单、查询、作废；接收订单和核销回调。 |
| 交行直充新服务 | 提供 V1 接口，处理订单受理、业务校验、异步处理、回调和补偿。 |
| 旧卡管系统 | 灰度期间继续承接未迁移业务，并与新服务共享部分历史数据。 |
| 供应商系统 | 接收派单、查单、作废请求，返回充值或核销结果。 |
| 运营/运维 | 配置商户、商品、白名单、回调地址，处理告警、补偿和人工核查。 |

## 4. 外部接口需求

### 4.1 通用接口要求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| API-01 | 所有接口使用 `POST` 和 `application/json`。 | P0 |
| API-02 | 除获取 token 外，业务接口必须携带合法 token。 | P0 |
| API-03 | token 有效期为 3 小时，建议商户每 2 小时主动刷新。 | P0 |
| API-04 | 请求和回调必须按接口文档约定完成签名和验签。 | P0 |
| API-05 | 金额字段单位统一为分。 | P0 |
| API-06 | 通用返回结构必须包含 `code`、`msg` 和 `data`。 | P0 |
| API-07 | 接口错误码必须覆盖凭证错误、验签失败、参数异常、商品异常、账户异常、订单重复、系统繁忙和处理中等场景。 | P0 |

### 4.2 接口清单

| 接口 | 地址 | 主要能力 |
| --- | --- | --- |
| 获取 token | `/v1/cardapi/auth/getToken` | 校验商户身份并返回调用凭证。 |
| 直充下单 | `/v1/cardapi/order/createRechargeOrder` | 创建直充订单，返回平台订单号和商户订单号。 |
| 订单查询 | `/v1/cardapi/order/getRechargeOrder` | 查询订单状态、商品、金额、账号、核销和作废信息。 |
| 作废申请 | `/v1/cardapi/order/invalid` | 申请作废订单对应权益。 |
| 订单状态回调 | 商户提供 | 平台向商户通知订单状态变化。 |
| 核销状态回调 | 商户提供 | 平台向商户通知核销、作废、过期、回收等状态变化。 |

### 4.3 对外状态码

| 类型 | 状态 | 说明 |
| --- | --- | --- |
| 通用状态 | 200 | 操作成功。 |
| 通用状态 | 401 | 凭证错误。 |
| 通用状态 | 500 | 系统繁忙。 |
| 通用状态 | 501 | 验签异常或不在 IP 白名单。 |
| 通用状态 | 503 | 商品限额、价格异常、无权限或库存不足。 |
| 通用状态 | 504 | 账户不存在或账户余额不足。 |
| 通用状态 | 505 | 订单生成失败、订单号重复或订单状态异常。 |
| 通用状态 | 506/507/508 | 参数、解析或充值用户异常。 |
| 通用状态 | 510 | 异步处理中，建议稍后查询。 |
| 订单状态 | 0 | 新订单。 |
| 订单状态 | 2 | 处理中。 |
| 订单状态 | 6 | 失败。 |
| 订单状态 | 11 | 退款。 |
| 订单状态 | 12 | 成功。 |
| 订单状态 | 13 | 充值中。 |

## 5. 核心业务流程需求

### 5.1 获取 token

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-TOKEN-01 | 系统必须校验 `app_id` 和 `app_secret`，校验通过后签发 token。 | P0 |
| FR-TOKEN-02 | token 必须能识别商户身份，并用于后续业务接口鉴权。 | P0 |
| FR-TOKEN-03 | token 缺失、错误或过期时，业务接口必须拒绝请求。 | P0 |

### 5.2 直充下单

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-CREATE-01 | 下单请求必须包含商品编号、商户订单号、充值账号、时间戳、随机串、回调地址、签名和购买数量。 | P0 |
| FR-CREATE-02 | 当前购买数量限制为 1。 | P0 |
| FR-CREATE-03 | 系统必须先完成 token、IP 白名单、参数格式、时间戳、随机串和签名校验。 | P0 |
| FR-CREATE-04 | 基础安全校验失败且无法识别商户订单时，不应生成业务订单，只记录安全审计。 | P0 |
| FR-CREATE-05 | 基础安全校验通过且能识别商户订单后，无论业务校验成功或失败，都必须形成可追踪订单记录。 | P0 |
| FR-CREATE-06 | 业务校验通过时，系统必须完成余额控制、库存或限购控制，并返回受理成功。 | P0 |
| FR-CREATE-07 | 业务校验失败时，系统必须返回明确失败码和失败原因，并保留失败订单记录。 | P0 |
| FR-CREATE-08 | 下单受理后的后台处理不得影响商户已收到的受理事实；异常时必须通过补偿或人工核查收敛。 | P0 |

### 5.3 订单查询

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-QUERY-01 | 商户必须能按商户订单号查询订单详情。 | P0 |
| FR-QUERY-02 | 查询结果必须包含平台订单号、商户订单号、商品信息、金额、充值账号、订单状态和必要的核销/作废信息。 | P0 |
| FR-QUERY-03 | 对已受理但后台尚未处理完成的订单，查询接口应返回处理中或充值中，不应直接判定为失败或不存在。 | P0 |
| FR-QUERY-04 | 查询接口在缓存或短期数据不可用时，应尽量以最终订单记录兜底。 | P0 |

### 5.4 作废申请

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-INVALID-01 | 系统必须支持商户对订单发起作废申请。 | P0 |
| FR-INVALID-02 | 已使用、已核销、已退款或状态不允许作废的订单必须拒绝作废。 | P0 |
| FR-INVALID-03 | 订单尚未完成必要后台处理时，作废接口应返回处理中或系统繁忙。 | P0 |
| FR-INVALID-04 | 作废成功后，系统必须更新订单状态、核销状态、资金状态，并通知商户。 | P0 |

### 5.5 回调通知

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-NOTIFY-01 | 订单状态变化、核销状态变化、作废或退款完成时，系统必须按需通知商户。 | P0 |
| FR-NOTIFY-02 | 回调报文必须按接口文档约定签名。 | P0 |
| FR-NOTIFY-03 | 空字段需要保留 key，确保商户验签口径一致。 | P0 |
| FR-NOTIFY-04 | 商户返回 `code=200` 视为接收成功；非 200 或网络异常必须重试。 | P0 |
| FR-NOTIFY-05 | 回调必须支持幂等，重复通知不得导致商户侧状态倒退。 | P0 |

## 6. 业务规则

### 6.1 幂等规则

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| BR-IDEM-01 | 同一商户下，`out_order_sn` 必须唯一。 | P0 |
| BR-IDEM-02 | 同一商户订单号重复下单时，系统必须拒绝重复创建。 | P0 |
| BR-IDEM-03 | 重复订单号但请求内容不一致时，必须返回清晰冲突原因。 | P0 |
| BR-IDEM-04 | 重复请求不得重复扣余额、重复生成供应商派单或重复写资金流水。 | P0 |

### 6.2 业务校验规则

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| BR-VALID-01 | 系统必须校验商户状态、商品状态、商品权限、商品价格、库存、限购、充值账号、购买数量和商户余额。 | P0 |
| BR-VALID-02 | 业务校验失败订单必须保存失败码和失败原因，便于商户查询、运营查询和售后排查。 | P0 |
| BR-VALID-03 | 业务校验失败订单不得进入供应商派单，不得产生扣款流水。 | P0 |
| BR-VALID-04 | 商品价格、库存、限购、余额等高并发条件必须以受理时的最新可用状态为准，避免超卖或超扣。 | P0 |

### 6.3 订单状态规则

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| BR-STATE-01 | 系统必须统一订单在接口、后台处理、供应商处理、核销、作废、退款和回调中的状态口径。 | P0 |
| BR-STATE-02 | 订单状态不得被旧处理结果覆盖为更早状态。 | P0 |
| BR-STATE-03 | 供应商处理中时，对商户应表现为处理中或充值中。 | P0 |
| BR-STATE-04 | 成功、失败、作废、退款等终态必须可查询、可回调、可对账。 | P0 |

### 6.4 资金规则

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| BR-FIN-01 | 业务校验通过的订单必须完成余额控制，防止商户余额被超扣。 | P0 |
| BR-FIN-02 | 业务校验失败订单不得扣减商户余额。 | P0 |
| BR-FIN-03 | 供应商最终失败、作废成功或退款时，系统必须释放或回补对应资金。 | P0 |
| BR-FIN-04 | 资金变动必须有流水或等价记录，支持财务对账和售后追踪。 | P0 |
| BR-FIN-05 | 新旧系统灰度期间，同一商户同一交易范围只能由一个系统负责余额写入。 | P0 |

## 7. 数据记录需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| DR-01 | 系统必须记录订单最终事实，包括平台订单号、商户订单号、商户、商品、账号、金额、状态、创建时间和更新时间。 | P0 |
| DR-02 | 系统必须记录业务校验失败原因，支持订单列表、订单详情和售后排查。 | P0 |
| DR-03 | 系统必须记录资金变动，确保扣款、释放、退款和调账可追溯。 | P0 |
| DR-04 | 系统必须记录供应商请求和响应，支持派单重试、查单和售后核对。 | P0 |
| DR-05 | 系统必须记录回调任务状态，支持失败重试和人工处理。 | P0 |
| DR-06 | 系统必须保留与旧表的数据兼容关系，避免影响既有运营查询和旧系统读写。 | P0 |
| DR-07 | 需要新增或调整字段、索引、扩展表时，必须先完成历史数据检查和兼容性评估。 | P0 |

## 8. 异常处理与可靠性需求

### 8.1 通用异常原则

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| REL-01 | 下单链路遇到无法保证资金安全或订单可恢复的异常时，必须拒绝新下单或返回系统繁忙。 | P0 |
| REL-02 | 已受理订单必须有后续恢复入口，不能因为后台异常丢失。 | P0 |
| REL-03 | 订单处理、资金处理和回调处理必须具备幂等能力。 | P0 |

### 8.2 典型异常场景

| 场景 | 期望处理 |
| --- | --- |
| 订单已受理但后台处理暂未完成 | 查单返回处理中或充值中，后台继续处理。 |
| 后台消息投递或消费失败 | 订单保留可恢复记录，后台重试或人工处理。 |
| 数据库短时不可用 | 暂停或延后后台处理，恢复后继续处理存量订单。 |
| 缓存或实时控制层不可用 | 下单保护性失败；查单尽量使用最终订单记录兜底。 |
| 供应商返回处理中 | 订单保持处理中，后续查单确认最终结果。 |
| 回调失败 | 按重试策略继续推送，超过阈值进入人工处理。 |
| 资金差异 | 停止受影响范围的新下单，完成核查和修复后恢复。 |

## 9. 性能与容量需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| PERF-01 | 系统首期性能基线必须支持整体接口请求能力不低于 QPS 300。 | P0 |
| PERF-02 | 系统首期交易处理能力必须支持核心直充交易吞吐不低于 TPS 450。 | P0 |
| PERF-03 | 达到性能基线时，订单幂等、余额控制、状态查询、回调任务和异常补偿能力不得失效。 | P0 |
| PERF-04 | 性能测试应使用接近真实业务比例的数据，覆盖下单、查询、作废、回调和后台处理链路。 | P1 |

## 10. 验收标准

### 10.1 接口验收

| 编号 | 验收项 | 通过标准 |
| --- | --- | --- |
| AC-API-01 | token 获取 | 合法商户可获取 token，错误凭证被拒绝。 |
| AC-API-02 | 直充下单 | 合法请求返回平台订单号；非法请求返回明确错误。 |
| AC-API-03 | 订单查询 | 可查询成功、失败、处理中、退款、作废等状态。 |
| AC-API-04 | 作废申请 | 可作废订单成功作废，不可作废订单明确拒绝。 |
| AC-API-05 | 回调通知 | 订单状态和核销状态能按约定签名、推送和重试。 |

### 10.2 业务验收

| 编号 | 验收项 | 通过标准 |
| --- | --- | --- |
| AC-BIZ-01 | 重复下单 | 同一商户订单号不会重复创建、重复扣款或重复派单。 |
| AC-BIZ-02 | 业务校验失败 | 失败订单可查询失败码和失败原因，不扣余额、不派单。 |
| AC-BIZ-03 | 并发余额控制 | 并发下单不会导致商户余额为负或超扣。 |
| AC-BIZ-04 | 供应商处理中 | 商户查询看到处理中或充值中，最终成功/失败后状态更新。 |
| AC-BIZ-05 | 失败/作废/退款 | 订单状态、资金状态和回调状态一致。 |

### 10.3 可靠性验收

| 编号 | 验收项 | 通过标准 |
| --- | --- | --- |
| AC-REL-01 | 后台处理失败 | 已受理订单不会丢失，恢复后可继续处理。 |
| AC-REL-02 | 数据库短时不可用 | 系统不误判订单终态，恢复后订单最终可查询。 |
| AC-REL-03 | 消息或异步处理异常 | 系统可重试、可告警、可人工处理。 |
| AC-REL-04 | 关键依赖异常 | 新下单按规则保护性失败，存量订单不丢失。 |
| AC-REL-05 | 回调失败 | 系统按策略重试，超过阈值进入人工处理。 |

### 10.4 性能验收

| 编号 | 验收项 | 通过标准 |
| --- | --- | --- |
| AC-PERF-01 | QPS 基线 | 在约定压测环境和业务模型下，整体接口请求能力达到 QPS 300，且错误率、超时率满足上线门槛。 |
| AC-PERF-02 | TPS 基线 | 在约定压测环境和业务模型下，核心直充交易处理能力达到 TPS 450，且不出现重复订单、重复扣款或订单丢失。 |
| AC-PERF-03 | 压测后数据一致 | 压测结束后订单、资金核对一致。 |
