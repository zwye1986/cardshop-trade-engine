## 实施计划

### 1. Redis 后续 Lua 和端口

- 新增 `cancel_unconfirmed_accept.lua`：
  - 仅处理 WAIT 未确认后的回滚。
  - 校验订单仍处于 `PENDING_MQ` 且版本匹配。
  - 对已预扣余额的订单释放 `frozen` 并恢复 `available`。
  - 清理 reservation、pending、org_index、事件索引。
  - 将订单标记为 `ACCEPT_REJECTED` 或删除未确认快照，按脚本 contract 固化。
- 新增 `mark_persist_queued.lua`：
  - MQ confirm ack 后推进 `persist_status=PERSIST_QUEUED`。
  - 写入 `persist_msg_id`、`mq_publish_count`、`updated_at`。
  - 保留 pending，等待 Consumer 落库后再由后续 `markDbPersisted` 清理。
- 新增应用端口：
  - `RechargeReliabilityPort` 或等价命名，承载 WAIT、cancel、mark queued。
  - 端口返回领域化结果，不暴露 Redis 原始数组。

### 2. RabbitMQ 发布端口

- 新增 `PersistTradeOrderMessage`。
- 新增 `PersistRechargeOrderMessagePublisher` 应用端口。
- 新增 Spring AMQP 适配器：
  - 使用 `RabbitTemplate.convertAndSend(exchange, routingKey, payload, correlationData)`。
  - 等待 `CorrelationData.getFuture()`，超时按 confirm 失败处理。
  - mandatory return 视为失败。
  - confirm callback 不访问 Redis/MySQL。
- 新增最小 MQ breaker：
  - 配置关闭或 failure threshold 命中时，Redis Lua 前返回 `MQ_UNAVAILABLE`。
  - 本轮只做内存态最小实现，后续再接监控和半开探测。

### 3. 下单编排改造

- `V1CreateRechargeOrderUseCaseService` 保持现有准备流程。
- Redis `accept` 返回 `ACCEPTED/ACCEPTED_FAILED` 后：
  - 执行 WAIT。
  - WAIT 成功：发布 MQ 并等待 confirm。
  - confirm 成功：调用 `mark_persist_queued.lua`。
  - confirm 失败：保留 Redis pending，返回系统繁忙或处理中语义。
  - WAIT 失败：调用 `cancel_unconfirmed_accept.lua`。
  - cancel 成功：返回系统繁忙，允许调用方稍后重试。
  - cancel 失败：写入 `recharge_accept_anomaly`，并返回“系统繁忙，请稍后查询订单状态”。
- `DUPLICATE/NONCE_REPLAY/CONFIG_CHANGED/BALANCE_REPAIRING/REDIS_WRITE_DISABLED/REDIS_UNAVAILABLE` 保持 fail-closed 映射。

### 4. 查单真实用例

- 新增订单查询端口：
  - Redis：按 `orgCode + outOrderSn` 读取 `order:{outOrderSn}` 快照。
  - MySQL：本轮不接入，留到 D7/D8 异步落库闭环后补。
- 新增 `V1QueryRechargeOrderUseCaseService`：
  - 读取商户资料和协议预检。
  - Redis 命中时按内部状态映射旧接口数字状态。
  - Redis 未命中时返回明确未找到；后续接入 MySQL 兜底后再调整。
  - 不同步调用供应商。

### 5. 作废真实用例

- 新增 `V1InvalidRechargeOrderUseCaseService`：
  - 读取商户资料和协议预检。
  - 订单未落库或 `persist_status != DB_PERSISTED`：返回处理中。
  - 已落库订单：本轮仍返回处理中，并在代码中保留 D10 TODO。
  - 不同步调用供应商。

D5A 审查收口：

1. 异常登记非幂等问题真实存在：`recharge_accept_anomaly.anomaly_id` 有唯一键，原实现使用普通 insert，同一订单重复进入 WAIT_CANCEL_FAILED 会抛唯一键异常并产生误导性 WARN。已改为 `RechargeAcceptAnomalyMapper.insertOrRefreshByAnomalyId`，使用 `ON DUPLICATE KEY UPDATE last_error = VALUES(last_error), updated_at = VALUES(updated_at)`，保留首次 `raw_context/status`，只刷新最近错误和更新时间。
2. HTTP 响应等待异常登记完成问题真实存在：原 `toWaitFailureResult` 通过 `thenApply` 等待 `recordWaitCancelFailedAnomalyAsync` 完成，MySQL 慢或 `tradeDbTaskExecutor` 堆积会放大 cancel 失败路径 RT。已改为 fire-and-forget，登记失败仍内部记录日志，但调用方立即得到“系统繁忙，请稍后查询订单状态”。
3. `anomalyId` 退化为 `unknown` 当前 WAIT_CANCEL_FAILED 正常路径风险较低，因为 Java 在 Redis 前已生成 `orderId`；但 `AcceptAnomalyType` 已预留 `LUA_TIMEOUT/REDIS_BUSY/ACCEPT_STATE_UNKNOWN`，这些路径可能拿不到 Lua 返回体，问题对 D5B 扩展真实存在。已改为无 `orderId` 时使用稳定 `request_hash` 兜底，并按 `anomaly_id varchar(100)` 截断，避免不同订单碰撞到同一个 `unknown`。
4. `raw_context` boolean/字符串混存不是当前写入 bug，但属于 D5B 自动核查契约风险。代码注释已明确 `balance_reserved`、`dispatch_allowed` 以 JSON boolean 保存，核查任务读取时不能按字符串统一解析。

D5A 审查复核：

- `mvn -pl cardshop-trade-engine-api,cardshop-trade-engine-infrastructure -am clean test -Dtest=AcceptAnomalyRecordTest,MybatisAcceptAnomalyRecordAdapterTest,V1CreateRechargeOrderUseCaseServiceTest,MapperContractTest -Dsurefire.failIfNoSpecifiedTests=false`：通过；覆盖 anomaly upsert 契约、响应不等待 DB 写库、无 `orderId` 时 request_hash 兜底，以及 Redis 回调线程不执行 MyBatis 写库。
- `CancelUnconfirmedAcceptResult.cancelled` 已更名为 `rollbackConfirmed`，避免把 WAIT 失败后的 Redis 未确认受理回滚结果误解为 V1 `/invalid` 作废结果；业务语义仍是“Redis 已确认释放余额并清理 pending”。
- 查单状态映射已补协议单测：`VALIDATION_FAILED/FAILED/SUPPLIER_FAILED -> order_status=6`、`REFUNDED -> 11`、`SUCCESS -> 12`、`SUPPLIER_ACCEPTED -> 13`，处理中和未知内部态继续保守返回 `2`。
