# 交行直充业务系统需求文档（反向梳理版）

## 1. 文档说明

### 1.1 文档目的

本文档根据以下资料反向梳理交行直充业务系统的业务需求、接口需求、数据需求、高可用与一致性需求，以及上线验收要求：

- `docs/交行直充业务系统高可用方案设计.md`
- `docs/交行直充接口技术文档-V1.1.docx`

本文档面向产品、研发、测试、运维和联调人员，用于统一系统建设边界、接口契约、业务流程、异常处理、数据一致性和验收口径。

### 1.2 需求范围

本期系统建设范围包括：

1. 面向商户提供直充类产品对接能力，覆盖 token 获取、直充下单、订单查询、代金券作废申请、订单状态回调和核销状态回调。
2. 建设独立的新直充交易服务，承接直充订单受理、实时余额预扣、异步落库、供应商派单、回调通知、补偿和对账。
3. 使用 Redis 作为下单受理期短期数据源和实时控制层，RabbitMQ 作为 Redis 到 MySQL 的异步持久化通道，MySQL 作为订单与资金最终事实。
4. 支持 Redis 主从切换、RabbitMQ 投递失败、MySQL 异步落库失败、补偿任务重试、余额对账和缓存修复。
5. 与现有旧系统共享核心 MySQL 表，并通过扩展表保存新链路的 Redis/MQ/MySQL 一致性状态。

本期不直接覆盖：

1. 非直充产品的完整重构。
2. 旧卡券、批采、补发等非直充业务主流程改造。
3. 商户运营后台、财务后台、供应商后台的完整产品化界面改造。
4. Redis Cluster 迁移实施，仅要求当前 Key 设计兼容后续 Cluster。

### 1.3 需求优先级说明

| 优先级 | 含义 |
| --- | --- |
| P0 | 首期上线必须满足，否则存在丢单、超卖、资金不一致或接口不可用风险。 |
| P1 | 首期建议满足，影响联调效率、排障能力、运维效率或灰度安全。 |
| P2 | 后续优化项，不阻塞首期小流量灰度，但应纳入演进计划。 |

## 2. 背景与业务目标

### 2.1 业务背景

商户通过平台直充接口创建充值类订单。下单成功仅表示平台已受理订单，最终充值结果需要通过订单查询或平台回调确认。系统需要在高并发场景下保证商户订单号幂等、余额不超扣、库存不超卖、失败订单可追溯、订单最终落库，并能在 Redis、RabbitMQ、MySQL 任一环节故障时恢复。

### 2.2 建设目标

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| G-01 | 系统必须支持商户直充订单创建、查询、作废、订单状态回调和核销状态回调。 | P0 |
| G-02 | 系统必须在下单受理阶段先将可识别订单写入 Redis，并通过 RabbitMQ 异步持久化到 MySQL。 | P0 |
| G-03 | MySQL 必须作为订单事实、资金流水、回调任务和对账依据的最终数据源。 | P0 |
| G-04 | Redis 必须承担实时余额预扣、订单短期快照、幂等、库存、限购和待持久化索引职责。 | P0 |
| G-05 | RabbitMQ 必须作为 Redis 到 MySQL 的可靠异步持久化通道，并启用 publisher confirm、持久化消息、手动 ack 和重试/DLQ 机制。 | P0 |
| G-06 | 所有基础安全校验通过且能识别商户和商户订单号的订单，包括业务校验失败订单，最终都必须在 MySQL 中留痕。 | P0 |
| G-07 | Redis 或关键中间件异常时，下单资金链路必须 fail closed，不能绕过 Redis 直接改用 MySQL 扣减余额。 | P0 |
| G-08 | 系统必须提供补投、补偿、余额对账、缓存修复和人工介入能力，保障最终一致。 | P0 |
| G-09 | 系统必须支持按商户灰度切流和回滚，避免新旧系统同时写同一商户同一交易类型余额。 | P0 |

## 3. 角色与外部系统

| 角色/系统 | 职责 |
| --- | --- |
| 商户系统 | 调用 token、下单、查询、作废接口；接收订单状态和核销状态回调。 |
| 交行直充新服务 | 提供 V1 接口，完成安全校验、订单受理、Redis 写入、MQ 投递、异步落库、派单、回调和补偿。 |
| 旧卡管系统 | 与新服务共享部分 MySQL 表；灰度期间可能继续承接未切流商户和非直充业务。 |
| Redis | 实时余额、订单快照、幂等、库存、限购、pending、订单版本事件。 |
| RabbitMQ | 订单异步落库、供应商派单、查单、作废、回调重试等消息通道。 |
| MySQL | 订单事实、资金流水、最终余额、扩展状态、outbox、回调任务。 |
| XXL-Job | MQ 补投、MySQL 持久化重试、outbox 发布、余额刷账、余额对账、缓存修复、回调重试。 |
| Nacos | 环境配置、Redis 写入开关、修复开关、限流、线程池和第三方配置。 |
| 供应商系统 | 接收派单、查单、作废请求，返回充值、核销、失败或处理中结果。 |
| 运维/运营 | 配置商户、商品、白名单、回调地址，处理告警、DLQ、余额差异和人工补偿。 |

## 4. 核心业务术语

| 术语 | 说明 |
| --- | --- |
| 商户订单号 `out_order_sn` | 商户侧提交的唯一订单号，同一商户下必须唯一。 |
| 平台订单号 `order_id` | 平台生成并返回给商户的订单号，对应旧表 `mc_order.order_Id`。 |
| 可识别订单 | 基础安全校验通过后，可以解析出 `orgCode/outOrderSn` 的请求。 |
| 业务校验失败订单 | 商户、商品、余额、库存、限购、价格等业务校验不通过的订单；仍需落 Redis pending 和 MySQL。 |
| 受理成功订单 | 业务校验通过，Redis 已保存订单并完成必要余额、库存、限购预占的订单。 |
| Redis pending | Redis 中待 MySQL 持久化的订单索引，是 MQ 投递失败和 MySQL 落库失败后的补偿入口。 |
| Outbox | MySQL 落库成功后记录的可靠事件，用于供应商派单、查单、作废、余额刷账、缓存修复。 |
| 余额刷账 | 将 Redis 实时预扣产生的余额增量，通过 outbox 批量刷入 `mc_ext_depart.balance`。 |
| fail closed | 故障时拒绝新下单或返回系统繁忙，不继续执行可能导致超卖或丢单的降级逻辑。 |

## 5. 外部接口需求

### 5.1 接口通用要求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| API-01 | 所有业务接口必须使用 `POST` 和 `Content-Type: application/json`。 | P0 |
| API-02 | 除获取 token 接口外，所有业务接口必须携带合法 `Authorization: token`。 | P0 |
| API-03 | token 有效期为 3 小时，商户侧建议每 2 小时主动刷新。 | P0 |
| API-04 | 所有请求和回调签名必须按接口文档规则执行：收集所有非空参数及 `aesKey`，按参数名 ASCII 字典序排序，以 `key=value` 形式拼接后使用 SM3 生成 `sign`；传输的 `sign` 不参与签名计算。 | P0 |
| API-05 | 所有请求必须校验 `timestamp` 和 `nonce_str` 格式；`timestamp` 支持 10 位或 13 位时间戳，`nonce_str` 为 32 位随机字符串且区分大小写。 | P0 |
| API-06 | 涉及金额的字段单位必须统一为分，不得使用元或浮点数参与计算。 | P0 |
| API-07 | 通用返回格式必须包含 `code`、`msg`、`data`，其中 `data` 按接口需要返回。 | P0 |
| API-08 | 对外错误码和文案必须能覆盖凭证错误、系统繁忙、验签异常、商品异常、账户异常、订单重复、参数异常、用户异常和异步处理中。 | P0 |

### 5.2 通用状态码

| 状态码 | 说明 | 商户处理建议 |
| --- | --- | --- |
| 200 | 操作成功 | 正常处理返回数据。 |
| 401 | 凭证错误 | 检查 `app_id`、`app_secret` 或 token。 |
| 500 | 系统繁忙 | 稍后重试或查询订单状态。 |
| 501 | 验签异常/不在 IP 白名单 | 检查签名规则或白名单。 |
| 502 | 网络错误 | 排查网络连接或接口地址。 |
| 503 | 商品限额/商品价异常/商品无权限/库存不足 | 核对商品配置或联系运营。 |
| 504 | 账户不存在/账户余额不足 | 校验充值账户或商户账户状态。 |
| 505 | 订单生成失败/订单号重复/订单号有误/订单状态失败 | 检查订单号唯一性或状态合法性。 |
| 506 | 数据参数异常 | 核对参数格式、必填项和取值范围。 |
| 507 | 入参解析错误/系统异常 | 检查 JSON 格式。 |
| 508 | 充值用户异常 | 校验充值账号合法性。 |
| 510 | 请等待，稍后重新获卡 | 异步处理中，建议 1 到 3 分钟后查询。 |

| API-CREATE-08 | RabbitMQ confirm 达到失败阈值时，可以返回落库任务投递失败类错误，但 Redis 订单和 pending 不得删除，后台继续补偿落 MySQL。 | P0 |

## 6. 下单业务需求

### 6.1 安全校验与订单归属

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-CREATE-01 | 下单入口必须先完成 token、IP 白名单、请求格式、参数必填、时间戳、随机串和签名校验。 | P0 |
| FR-CREATE-02 | 基础安全校验失败且无法识别 `orgCode/outOrderSn` 时，系统不得写订单主表，只记录安全审计日志。 | P0 |
| FR-CREATE-03 | 基础安全校验通过且能识别 `orgCode/outOrderSn` 后，系统必须保证订单进入 Redis-first 受理链路。 | P0 |
| FR-CREATE-04 | 所有日志、指标和排障记录必须携带非敏感上下文，包括 `orgCode`、`outOrderSn`、`orderId`、`messageId`、`eventId`、`traceId`。 | P0 |

### 6.2 幂等与重复下单

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| FR-IDEM-01 | 系统必须以 `orgCode + outOrderSn` 作为直充订单幂等主键。 | P0 |
| FR-IDEM-02 | Redis 必须保存幂等 key，包含请求摘要、平台订单号和持久化状态。 | P0 |
| FR-IDEM-03 | MySQL 必须通过唯一约束兜底同一商户订单号的重复写入。 | P0 |
| FR-IDEM-04 | 重复请求的 `request_hash` 一致时，下单接口必须拒绝重复创建，并提示商户订单号已存在，可引导调用查单接口。 | P0 |

## 10. 高可用与一致性需求

### 10.1 Redis 高可用

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| HA-REDIS-01 | 当前阶段 Redis 必须按 Sentinel 模式部署，生产至少 `1 master + 2 replica + 3 sentinel`。 | P0 |
| HA-REDIS-02 | Redis 数据节点和 Sentinel 必须分散在不同机器或故障域。 | P0 |
| HA-REDIS-03 | 应用必须通过 Sentinel master name 连接 Redis，不得固定 master IP。 | P0 |
| HA-REDIS-04 | Redis 必须启用 AOF、`appendfsync everysec`、`maxmemory-policy noeviction`。 | P0 |
| HA-REDIS-05 | Redis 必须配置 `min-replicas-to-write 1` 和 `min-replicas-max-lag 2`。 | P0 |
| HA-REDIS-06 | 关键写入后必须执行 `WAIT 1 100ms` 或等价副本确认策略。 | P0 |
| HA-REDIS-07 | Redis 主从切换、复制延迟过高或 `WAIT` 失败率超阈值时，必须关闭下单写入并触发修复。 | P0 |
| HA-REDIS-08 | 查单可以在 Redis 异常时降级 MySQL；下单和未落库订单作废不得绕过 Redis 继续执行。 | P0 |
| HA-REDIS-09 | Redis Key 必须使用 `{orgCode}` hash tag，保证后续 Redis Cluster 迁移时同商户 Lua 能落同一 slot。 | P1 |

### 10.2 RabbitMQ 高可用

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| HA-MQ-01 | 所有业务 exchange 和 queue 必须 durable。 | P0 |
| HA-MQ-02 | 订单落库主队列必须使用持久化消息，并优先使用 Quorum Queue。 | P0 |
| HA-MQ-03 | 生产者必须启用 correlated publisher confirm、mandatory return。 | P0 |
| HA-MQ-04 | Consumer 必须使用 manual ack、合理 prefetch、retry queue 和 DLQ。 | P0 |
| HA-MQ-05 | MQ broker 不可用或 publish breaker 打开时，新订单必须在 Redis Lua 前拒绝，避免制造大量 pending。 | P0 |
| HA-MQ-06 | RabbitMQ 队列堆积、confirm 延迟、redeliver、unacked 和 DLQ 数量必须纳入告警。 | P0 |

### 10.3 MySQL 与最终一致

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| HA-DB-01 | MySQL 必须作为订单事实、资金流水、最终余额、outbox 和回调任务的最终数据源。 | P0 |
| HA-DB-02 | MySQL 异步落库失败时，系统不得释放 Redis 余额，必须重试落库。 | P0 |
| HA-DB-03 | 只有业务最终失败、作废退款或明确下单受理失败时，才允许释放 Redis 余额。 | P0 |
| HA-DB-04 | MySQL 写入必须通过幂等约束、版本判断和事务保证不重复写订单、流水和 outbox。 | P0 |
| HA-DB-05 | 高并发运营查询应尽量走从库或归档表，避免影响主库写入。 | P1 |

### 10.4 降级策略

| 场景 | 下单 | 查单 | 作废 | 回调 |
| --- | --- | --- | --- | --- |
| Redis 正常 + RabbitMQ 正常 | Redis Lua 受理 + MQ confirm | Redis 优先 | Redis 快照 + outbox | 通过 notify task |
| Redis 完全不可达 | fail closed，返回系统繁忙或 Redis 不可用 | MySQL 兜底，近期订单可能提示处理中 | fail closed | 继续 |
| Redis 复制延迟高 | 返回繁忙并可能关闭写入 | MySQL 兜底 | 暂停或返回繁忙 | 继续 |
| Redis 主从切换 | fail closed | MySQL 兜底 | fail closed | 继续 |
| RabbitMQ confirm 失败 | pending 保留，按阈值返回处理中或失败 | Redis 返回处理中 | 未落库前不允许作废 | 不触发 |
| RabbitMQ broker 不可用 | Redis Lua 前拒绝新订单 | Redis/MySQL 正常查单 | 未落库前不允许作废 | 不触发 |
| MySQL 异常 | Redis pending 保留，MQ/Consumer 重试 | Redis 返回处理中 | 返回处理中 | 暂停重试 |
| 派单队列异常 | 下单和落库可继续，outbox 堆积 | 正常 | outbox 堆积 | notify task 重试 |

| JOB-09 | 首次部署、全新 Redis DB 或新商户接入时，缓存修复任务必须支持基线预热，重建商户配置、商品配置和余额基线后才能放量。 | P0 |

## 15. 灰度、上线与回滚需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| REL-01 | 上线前必须先完成兼容字段、扩展表和唯一索引变更，并确认不破坏旧系统读写。 | P0 |
| REL-02 | 新服务部署后必须先关闭接单开关，启动 Consumer、Outbox Worker 和补偿任务，再灰度商户。 | P0 |
| REL-03 | 切流前必须完成 Redis 商户配置、商品配置和余额基线预热。 | P0 |
| REL-04 | 切流商户必须冻结 balance owner，确认同一商户同一交易类型只有新服务或旧系统一方写余额。 | P0 |
| REL-05 | 按商户逐步放量，每个灰度阶段必须验证 Redis pending、MQ 队列、MySQL 订单、资金流水、outbox 和回调任务闭环。 | P0 |
| REL-06 | 回滚时，新服务必须先停止接单，等待 Redis pending、RabbitMQ 持久化队列、未刷账 outbox 全部收敛后，才能把 owner 切回旧系统。 | P0 |
| REL-07 | 已写 Redis 但未落 MySQL 的订单，回滚后仍必须由新服务 Consumer/补偿任务继续落库，不能丢弃。 | P0 |

## 16. 验收标准

### 16.1 核心链路验收

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC-01 | Redis Lua 成功、`WAIT` 成功、RabbitMQ confirm 成功 | 接口按 Lua 结果返回；Redis 状态为 `PERSIST_QUEUED`；Consumer 写入 `mc_order/recharge_order_ext`；pending 清理；校验通过订单生成 outbox。 |
| AC-02 | Redis Lua 成功、RabbitMQ confirm 失败 | 接口线程有限重投；达到阈值返回明确错误；Redis 订单和 pending 保留；查单返回处理中；补投后 MySQL 最终落库。 |
| AC-03 | Redis `WAIT` 失败且回滚成功 | 接口返回系统繁忙；余额、库存、限购预占释放；订单标记 `ACCEPT_REJECTED` 或清理未确认快照；同一 `outOrderSn` 可重新创建。 |
| AC-04 | Redis `WAIT` 失败且回滚失败 | 下单写入关闭；订单进入人工审计或异常核查；不能向商户返回受理成功。 |
| AC-05 | Consumer 写 MySQL 失败 | MQ 不 ack 或进入重试；Redis pending 不清理；恢复后最终落库。 |
| AC-06 | Redis 主从切换 | 新下单 fail closed；查单 MySQL 兜底；修复 pending、余额和订单快照后才恢复接单。 |

### 16.2 幂等与一致性验收

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC-07 | 同一 `orgCode + outOrderSn`、相同请求摘要重复下单 | 返回重复订单号类失败；不重复扣余额、不重复发 MQ、不重复派单。 |
| AC-08 | 同一 `orgCode + outOrderSn`、不同请求摘要重复下单 | 返回订单号已存在但内容不一致；记录冲突日志；不新增订单。 |
| AC-09 | 并发余额 TOCTOU | 只有 Redis Lua 内校验通过的订单扣余额；余额不足订单写失败原因并落库；Redis available 不为负。 |
| AC-10 | 并发库存 TOCTOU | 库存不足订单写失败原因并落库；库存不为负；失败订单不派单。 |
| AC-11 | Redis 快照缺失但 MQ 消息存在 | Consumer 使用 MQ 初始快照落 MySQL，标记 `MQ_SNAPSHOT_FALLBACK`，触发告警和缓存修复。 |
| AC-12 | 旧 MQ 快照晚于 Redis 新版本到达 | Consumer 读取 Redis 最新版本写 MySQL，旧消息不得覆盖新状态。 |

### 16.3 资金与 outbox 验收

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC-13 | 校验失败订单 | Redis 和 MySQL 均记录失败码和失败原因；不扣余额；不写扣款流水；不生成派单 outbox。 |
| AC-14 | 多分片同商户余额刷账 | 只有 CAS 抢占成功事件参与聚合；写库按商户行锁串行；余额增量不丢不重。 |
| AC-15 | 供应商派单成功但标记 outbox 前宕机 | 恢复后先查供应商或本地派单流水，不盲目重复派单；outbox 最终成功或人工处理。 |
| AC-16 | 供应商最终失败或作废成功 | Redis reservation 幂等释放；生成正向余额刷账事件；订单状态和回调任务正确生成。 |
| AC-17 | 新旧系统 balance owner 冲突 | 触发告警并关闭对应商户新服务接单，不允许双写余额。 |

### 16.4 降级与容量验收

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC-18 | RabbitMQ Quorum Queue 堆积 | 系统限流或告警生效；pending 不丢失；恢复 Consumer 后可追平。 |
| AC-19 | MySQL 短时不可用 1 到 5 分钟 | Consumer 不 ack 或延迟重试；Redis pending 保留；MySQL 恢复后最终落库；超过保护窗口告警。 |
| AC-20 | Redis `WAIT` 失败率升高 | 达到阈值关闭下单写入；恢复复制并完成修复后再打开。 |
| AC-21 | Outbox 堆积超过阈值 | 告警触发；任务可按 CAS/租约继续恢复；不重复执行副作用。 |

### 16.5 集成测试证据要求

每个端到端测试场景必须记录以下证据：

1. 接口请求和响应。
2. Redis order、idempotent、reservation、pending、org_index 状态。
3. RabbitMQ `message_id`、confirm 结果、队列深度、ack/nack 结果。
4. `mc_order`、`recharge_order_ext`、`mc_depart_record`、`recharge_outbox` 写入结果。
5. 余额前后值、资金流水和未刷账 outbox。
6. 关键日志中的 `trace_id/order_id/out_order_sn/message_id/event_id`。
7. 告警是否触发，以及触发后的开关状态。
