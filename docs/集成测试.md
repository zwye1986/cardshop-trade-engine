watch 尾帧窗口估算也指向同一结论：`recharge_outbox` p50/p95/p99/avg 约 **2.301s / 7.839s / 8.384s / 2.855s**，是最长阶段；`mc_order` 与 `recharge_order_ext` 次之；`commit` 始终在毫秒级。由于 phase 记录在每段 SQL finally 中，失败批次可能导致各 phase count 与总批事务 count 略不一致。

### 4. 结论

1. **同步受理仍稳定**：30000/30000，100 QPS，p99 9ms，无客户端超时。
2. **显式 multi-row 批 adapter 本轮没有带来吞吐提升**：压测 5 分钟窗口落库从上一轮 **5142** 降到 **4853**，批事务全窗口 avg 从 **4.16s** 微升到 **4.375s**，尾段 p95 从 **7.665s** 升到 **10.337s**。
3. **phase 指标定位很清楚**：瓶颈不在 commit，也不在 Hikari；`recharge_outbox` multi-row insert/upsert 是最大耗时来源，约占总批事务均值的一半以上，其次是 `mc_order` 与 `recharge_order_ext`。
4. **失败和长尾仍来自 MySQL 通信/锁等待类问题**：本轮 `failed +40`、retry 最高 20，DLQ 0；`Read timed out` / `Communications link failure` 仍出现，MySQL `trx_lock_wait` 在压测前后都存在。
5. 下一步优化方向应转向 **outbox 写入拆薄或降频**：例如压测时继续暂停 outbox worker 只解决读写竞争，但本轮 phase 显示订单事务内 `recharge_outbox` 写入本身已经是主要耗时；若业务允许，优先评估将 `BALANCE_DELTA_FLUSH` outbox 从主落库事务拆出、或把 outbox 批写进一步拆小/延后，再复测同一压测口径。
