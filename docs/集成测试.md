#### 3.1 PEND-001 暴露问题与修复

现象：

- PEND-001 数据面已成功：MySQL 四表落库，Redis 订单为 `DB_PERSISTED`，该订单 pending 已清理。
- 同一时间日志出现 `Redis订单异步落MySQL成功但markDbPersisted失败`，`failCode=MARK_FAILED`，`failReason=MARK_FAILED`。
- 最新启动行之后未再出现 WebFlux `block()/blockFirst()/blockLast()` 报错，说明人工入口 offload 已生效；该日志不是 event-loop blocking 复发。

根因：

- 真实 Lettuce reactive `eval(..., ScriptOutputType.MULTI).collectList()` 对 Lua table 的返回形态为单元素嵌套 list：`[[code, MARKED, order_id, ...]]`。
- 旧 `RedisSessionAcceptReliabilityAdapter.flatResult(...)` 只识别扁平 list：`[code, MARKED, order_id, ...]`。
- Lua 已经成功执行并推进 Redis `DB_PERSISTED`，但 Java 侧解析不到 `code=MARKED`，默认映射为 `MARK_FAILED`，形成假失败日志。

修复：

- 新增回归测试 `RedisSessionAcceptReliabilityAdapterTest.unwrapsSingleNestedLettuceMultiResultForMarkDbPersisted`。
- RED 证据：修复前单测失败，`Expecting value to be true but was false`。
- GREEN 修复：`flatResult(...)` 增加单元素嵌套 `MULTI` 结果拆包，并保留扁平 list 兼容；代码注释已链接 `docs/交行直充业务系统详细设计.md`「20.13.8 异步落库 Consumer」。
- 设计同步：`docs/交行直充业务系统详细设计.md` 和 `docs/交行直充业务系统高可用方案设计.md` 已补充 Lettuce `MULTI` 返回结构归一化约束。

- Spring 将该结果注册为 `NullBean`；Spring Boot 3.3 在 `callRunners` 阶段按 `Runner` 类型取 Bean 时失败。
- 本服务 DDL 统一由 Liquibase 管理，不使用 MyBatis-Plus DDL 脚本；`DdlApplicationRunner` 对空脚本列表运行是 no-op。

修复方案：

- 新增 `MybatisPlusDdlRunnerCompatibilityAutoConfiguration`，声明在 `MybatisPlusAutoConfiguration` 之前加载。
- 当没有自定义 `DdlApplicationRunner` 且没有 `IDdl` 脚本 Bean 时，提前提供真实
  `new DdlApplicationRunner(List.of())`，阻止 MyBatis-Plus 注册 `NullBean`。
- 若未来确需 MyBatis-Plus DDL 脚本，只要显式声明 `IDdl` 或自定义 `DdlApplicationRunner`，该兼容 Bean 会让位；
  当前 dev/test/prod 仍以 Liquibase 作为唯一 DDL 执行入口。

### 8. 2026-07-09 打开人工入口后的启动失败与本地修复

触发条件：

现象：

```text
Error creating bean with name 'manualRechargeJobController':
Unsatisfied dependency through constructor parameter 0:
No qualifying bean of type 'com.cardshop.trade.engine.job.recharge.RechargePersistMqRepublishJob'
```

根因：

- `ManualRechargeJobController` 只在 dev/test 且 `manual-job-enabled=true` 时注册。
- Controller 依赖 `RechargePersistMqRepublishJob`。
- 旧代码只在普通 `TradeEngineReliabilityConfiguration` 中按 `@ConditionalOnBean(PersistRechargeOrderMessagePublisher.class)` 创建 `RechargePersistMqRepublishService` 和 `RechargePersistMqRepublishJob`。
- 真实启动顺序中 RabbitMQ publisher 由基础设施层后置出现，普通配置类判断过早，导致补投 job 被跳过；打开人工入口后，Controller 依赖缺失并阻断应用启动。

本地修复：

- 新增 `TradeEngineCompensationJobAutoConfiguration`，在 Boot auto-configuration 阶段兜底创建 `RechargePersistMqRepublishService` 和 `RechargePersistMqRepublishJob`。
- `PendingPersistOrderPort.noop()` 仍只作为构造参数级降级，不注册为全局 Bean，避免抢占真实 Redis pending 端口。
- 新增回归测试 `ManualRechargeJobControllerTest.registersWithRepublishJobWhenPublisherComesFromLaterAutoConfiguration`，模拟 publisher 来自后置自动配置时人工入口仍可注册。
- 2026-07-09 16:07 CST 首次部署该修复后，test188 已成功启动且 liveness/readiness 为 `UP`，RabbitMQ `connections=1`、主队列 `consumers=4`；但人工入口 smoke 返回 500。
