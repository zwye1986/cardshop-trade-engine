### 4. 日志异常

压测窗口 `16:25-16:29` 应用日志出现 15 条 WARN/ERROR，集中在 Rabbit listener 线程：

| 项 | 结果 |
| --- | --- |
| MySQL 连接异常 | 5 次 `HikariPool-1 - Connection ... marked as broken because of SQLSTATE(08S01)` |
| 事务异常 | 5 次 `Application exception overridden by rollback exception` |
| MQ 重试 | 5 次 `RabbitMQ持久化消息处理需要重试`，`failCode=MYSQL_PERSIST_FAILED`，`failReason=JDBC rollback failed` |
| retry/DLQ 收敛 | retry queue 最终清零，DLQ 始终为 0 |

这些异常发生在异步落库阶段，不参与 HTTP 成功响应等待；但它说明 16 个 consumer 追落库时，MySQL 连接稳定性已经成为需要单独排查的风险点。

### 5. 结论

1. 本轮 `30/1000 + 5s` 成功率为 `96.6%`，p50 为 `21ms`，说明 30 并发口径下入口主链路大多数请求很快完成。
2. 剩余 34 个 `5s` timeout 不在服务端已完成的同步子阶段内：`sync_total` 平均约 `6.1ms`，Hikari 无 pending，Redis WAIT 和 MQ confirm 平均也远低于 5s。
3. `HTTP create +976` vs 客户端成功 `966` 表明至少约 10 笔是“客户端已超时但服务端稍后成功”；其余约 24 笔未形成服务端成功计数，需要结合 nginx access log 的 `request_time` / `upstream_response_time` 判断是否卡在 `apitest -> test188 nginx -> pro143` 入口层。
4. 异步落库链路仍慢，且本轮出现 5 次 MySQL `SQLSTATE(08S01)` broken connection / rollback failed。虽然最终 retry 清零且 DLQ 为 0，但继续单纯加大 Hikari 或 listener 并发可能会放大 MySQL 连接异常和落库重试。

### 6. 后续动作

1. 下一轮优先抓 test188 nginx access log 的 `request_time`、`upstream_response_time`、upstream 状态，确认客户端 timeout 是否来自入口层排队或代理等待。
2. 对异步落库单独排查 MySQL `SQLSTATE(08S01)`：核对 MySQL `wait_timeout`、网络抖动、连接保活、Hikari `maxLifetime` / `keepaliveTime`，以及 16 consumer 并发下数据库端连接、锁等待和慢 SQL。
3. 暂不建议继续单纯加大 Hikari 或 Rabbit listener 并发；当前 Hikari 已无 pending，应先定位入口层 timeout 与 MySQL 连接断开原因。
