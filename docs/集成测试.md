### 4. 结论

1. **同步受理仍稳定**：30000/30000，100 QPS，p99 11ms，无客户端超时。
2. **拆表优化有效**：5 分钟窗口落库从 **4853** 提升到 **5464**，批事务 avg 从 **4.375s** 降到 **3.868s**；旧 `recharge_outbox` 最大瓶颈被拆薄，dispatch+balance 合计 avg 比旧单段降低 **36.7%**。
3. **瓶颈已经从“单一 outbox 表”转为多段共同长尾**：`mc_order`、`recharge_order_ext`、`recharge_dispatch_outbox` 三段 avg 接近 1s，max_gauge 都有 55-60s 级别极端值；`recharge_balance_delta_outbox` 均值较低，说明余额表拆轻方向正确。
4. **吞吐仍未追上 100 QPS 灌入**：5 分钟窗口只消化约 18 QPS；队列在窗口末仍有约 2.39 万 ready。后续追赶到 15:03:34 才完成 30000 单落库并清空主队列/retry/DLQ，已经远超同步压测窗口。
5. **MySQL 通信/锁等待类风险仍在**：压测中 retry 最高 10、failed +20、DLQ 0；窗口后 backlog 追赶阶段应用日志仍出现 `SQLSTATE(08S01)` / `Communications link failure` / `Read timed out`。下一步优化应优先压低 `mc_order`、`recharge_order_ext` 和 dispatch outbox 的长尾，而不是继续优化 balance delta 写入。
