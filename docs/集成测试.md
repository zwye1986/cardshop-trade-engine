### 5. 结论

1. **同步侧大体稳定**：29999/30000，100 QPS；仅 1 笔 500。
2. **相对同参数上午 B15，异步落库显著回退**：窗口落库 **12095 → 6107**，批 avg **3.14s → 4.99s**，Hikari 从空闲变为 **满池+pending**。
3. **供应商派单成功不到 5000 与落库回退一致**：本轮能进入履约的 `DB_PERSISTED` 订单供给不足，且 XXL 派单并行（`rechargeSupplierDispatchJob` limit=1000, parallelism=8）与落库争用同一 Hikari/MySQL 资源池，导致终态成功继续滞后。
4. **不是「清理导致变差」的直接逻辑结果**：清理后本应更干净；本轮更像 **MySQL 实例争用加剧**（`product_spu` 再出现）叠加 **连接池打满 / JDBC 断连回滚**，外加 XXL 派单并行与落库争用同一池。
5. **batch=15 仍生效**，但不能抵消实例级变慢；继续加大 batch 无意义。
6. **下一步建议**：先核对下午 MySQL/商品同步负载与 Hikari 占用构成；必要时临时停 `product_spu` 同步或降低派单 Job 单轮 `limit`/并行后再复压对照。
