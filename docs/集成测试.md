### 2. Nginx 入口观测

test188 `trade_timing` access log 已包含 `$request_time`、`$upstream_connect_time`、`$upstream_header_time`、`$upstream_response_time`、`$upstream_status`。

| 项 | 结果 |
| --- | --- |
| `/v1/cardapi/auth/getToken` | `1`，status `200` |
| `/v1/cardapi/order/createRechargeOrder` | `1000` |
| create status | `200=983`、`499=17` |
| create upstream_status | `200=983`、`-=17` |
| create request_time | `min=0.000s, p50=0.007s, p95=0.284s, p99=0.515s, max=1.704s` |
| create upstream_connect_time | `p50=0.000s, p95=0.001s, p99=0.002s, max=0.009s` |
| create upstream_response_time | `p50=0.007s, p95=0.010s, p99=0.014s, max=0.453s` |
| create status `499` | `17` 条，`request_time=0.000s`，无 upstream timing |

结论：1000 个 create 请求全部到达 nginx。对已经转发并完成的 `983` 个请求，nginx 到 pro143 upstream 的耗时非常低，p95 约 `10ms`、最大 `453ms`；因此本轮客户端 `5s` timeout 不能归因于应用同步链路或 nginx 等 upstream 慢。`499` 与客户端主动断开有关，但数量 `17` 少于 simulator timeout `30`，剩余差异需要继续在 Java HttpClient 侧拆连接、写请求、读响应耗时。

### 5. 结论

1. 本轮 `30/1000 request-timeout=5s` 已完成，1000 单手机号均不重复；结果为成功 `970`、失败 `30`，失败全部是客户端 `HttpTimeoutException`。
2. nginx timing 已证明：请求均到达 nginx，且已完成请求的 upstream p95 只有 `10ms`，应用同步链路 Prometheus 平均约 `6.51ms`。当前 5s timeout 的直接瓶颈不在 Redis WAIT、MQ confirm、Hikari acquire 或应用同步处理。
3. Rabbit 异步落库仍是系统主要消化段：主队列 ready 峰值 `895`、listener 平均约 `986.3ms/条`，但本轮最终已全部清空，没有 DLQ 残留。
4. Hikari 本轮无 pending、无 timeout，暂不建议单纯继续放大数据库连接池；更应优先定位 MySQL `08S01` 与连接长占用样本。
5. 空 `notify_url` 历史任务和未启动的供应商 mock 仍在制造无效错误日志，会干扰压测窗口判断；下轮建议先清理历史空 URL notify 任务，并确认 supplier mock 是否需要启动或在 load 模式关闭。
6. 下一步建议给 simulator 增加客户端侧 timing 拆分或启用更详细 Java HttpClient 观测，区分 DNS/建连、请求写入、响应头等待、响应体读取和连接复用异常；这是解释 `timeout=30` 与 nginx `499=17` 差异的关键。
