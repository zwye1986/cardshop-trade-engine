### 3. 与 batch=20 轮次对比（同 30QPS×10min）

| 项 | batch=20（昨） | batch=10（本轮） |
| --- | ---: | ---: |
| 平均批大小 | ≈19.78 | **≈9.93** |
| 批 MySQL 均值 / 结束 max | ≈10.98s / 37.45s | **≈6.03s / 33.39s** |
| 窗口失败订单计数 | 560 | **230** |
| 结束时已落库（约） | 7553 | **7548**（刚结束 success 计数 7068，随后继续追） |
| 主队列 ready | ≈10637 | ≈10869 |
| DLQ | 0 | 0 |

回退到 10 后单批更快、失败更少，但 **10 分钟窗口内仍只能落约四成多订单**，追赶速度仍远低于 30 QPS 灌入。

### 4. 结论

1. **同步侧**：稳定达标（18000/18000；`createRechargeOrder` 接口实际 QPS **30.00**；客户端 p99≈10ms）。
2. **batch=10 生效**：平均批大小≈9.93；相对 batch=20，批事务均值从 ~11s 降到 ~6s，失败从 560 降到 230。
3. **主瓶颈未消**：批事务 p95≈11s、尾部 30s+ 仍击穿 `socketTimeout=30s`，产生 `Read timed out` / statement|connection closed，整批 retry；DLQ=0。
4. **Hikari pending=0**：不是连接池不够，是单连接占用过久。
5. **下一步仍建议**：`socketTimeout` 拉到 60s～120s；并行排查 RDS 共享负载与长事务；必要时再试 `max-concurrency=4`。
