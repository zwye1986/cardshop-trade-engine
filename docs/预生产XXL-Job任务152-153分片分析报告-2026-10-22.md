`cardshop-trade-engine-job/src/main/java/com/cardshop/trade/engine/job/recharge/RechargeSupplierQueryJob.java`

```java
        shardTotal,
        shardIndex,

```

`RechargeOutboxPublishJob` 做统一归一化：

```java

return workerService.processDue(
        normalizedTotal,

        RechargeJobParameters.limit(limit),
        RechargeJobParameters.workerId(workerId),
        eventTypes,
        parallelism);
```

`shardTotal < 1` 时按 1 处理；`shardIndex` 越界直接拒绝，不会把越界索引静默并入最后一个分片。

### 4.3 Worker 按分片扫描

`cardshop-trade-engine-application/src/main/java/com/cardshop/trade/engine/application/recharge/RechargeOutboxWorkerService.java`

```java
List<RechargeOutboxEvent> events =
        outboxPort.selectDueForShard(
                shardTotal,
                shardIndex,
                scanLimit,
                normalizedEventTypes);
```

### 4.4 SQL 分片条件

`cardshop-trade-engine-infrastructure/src/main/java/com/cardshop/trade/engine/infrastructure/persistence/mapper/RechargeDispatchOutboxMapper.java`

扫描 SQL 的关键条件：

```sql
and mod(crc32(o.shard_key), #{shardTotal}) = #{shardIndex}
order by o.created_at asc, o.id asc
limit #{limit}
```

这与高可用设计「17.2 分片规则」中的统一表达式一致：

```text
mod(crc32(shard_key), shardTotal) = shardIndex
```

### 4.5 分片键写入

`shard_key` 在写入时固定为 `event_id`，不是扫描时临时计算：

| 事件类型 | event_id 规则 | 写入位置 |
| --- | --- | --- |
| `SUPPLIER_DISPATCH` | `dispatch-{orderId}` | `RechargeOrderPersistenceRowConverter.toDispatchOutbox(...)` |
| `SUPPLIER_QUERY` | `supplier-query-{orderId}` | `MybatisRechargeDispatchOutboxAdapter.enqueueSupplierQuery(...)` |
| `INVALID_ORDER` | `invalid-{orderId}` | `MybatisRechargeDispatchOutboxAdapter.enqueueInvalidOrder(...)` |

DDL 中 `shard_key varchar(128) not null`，不会出现 `shard_key is null` 导致 `crc32(null)` 永远无法命中分片的问题。

### 4.6 XXL-Job 2.4.1 广播语义

XXL-Job 2.4.1 在 `SHARDING_BROADCAST` 下：

- 以 `group.getRegistryList().size()` 作为 `broadcastTotal`；
- 每个执行器分别收到 `broadcastIndex = 0..total-1`；
- 分片信息通过独立的 `broadcastIndex/broadcastTotal` 字段传递，不会污染 `jobParam`。

因此当前 3 个执行器地址会形成：

```text
节点 A：shardIndex=0, shardTotal=3
节点 B：shardIndex=1, shardTotal=3
节点 C：shardIndex=2, shardTotal=3
```

三个分片的并集覆盖全部 `shard_key`。

### 6.1 Job 143

`AcceptAnomalyAutoCheckJob.runOnce(int limit, String workerId)` 不接收 `shardTotal/shardIndex`，服务层按到期异常直接扫描。当前配置为 `FIRST` 是正确的；如果改成 `SHARDING_BROADCAST`，三个节点会重复扫描同一批异常，虽然可能被后续状态更新部分挡住，但会增加重复处理和状态竞争风险。

### 6.2 Job 148

`TradeEngineXxlJobHandlers.runNotifyRetryFromXxlContext(...)` 只把 `limit/workerId` 传给 `RechargeNotifyWorkerService.processDue(...)`，没有把分片参数下推到 `recharge_notify_task` 查询。因此当前虽然是 `SHARDING_BROADCAST`，实际三个节点会扫描同一批到期通知任务，只是依赖 `claim` 做并发控制。

要真正分片，需要：

1. 在 `RechargeNotifyWorkerService.processDue(...)` 增加 `shardTotal/shardIndex`；
2. 在 `RechargeNotifyWorkerTaskPort.selectDueTasks(...)` 及 Mapper 增加 `mod(crc32(task_id), shardTotal) = shardIndex`；
3. 补充 SQL 契约测试和多分片测试。

在代码改造完成前，建议把 Job 148 调整为 `FIRST`，避免三个节点重复扫描。

### 6.3 Job 149

Job 149 `rechargeOutboxPublishJob` 默认也扫描 `SUPPLIER_DISPATCH`，与 Job 152 重叠。当前 149 停用、152 启用，是正确组合。不要同时启用 149 和 152：虽然 CAS 可以防止同一事件被重复执行，但会放大扫描、锁竞争和日志量，并可能造成 `limit` 被重复消耗。

## 7. 风险与注意事项

### 7.1 分片数依赖执行器注册表

`shardTotal` 等于调度中心当前注册表大小。当前为 3，因此是三分片。

需要注意：

- 某节点宕机但仍在注册表中时，其分片会暂时无人执行，直到注册表过期/刷新；
- 注册表存在僵尸地址时，`shardTotal` 可能大于实际存活节点数，导致部分分片空跑；
- 分片数变化时同一事件会映射到不同 `shardIndex`，这是设计允许的，正确性仍由 CAS、版本号和幂等保证。

### 7.2 三个分片共用固定 workerId

152/153 的任务参数中：

```text
workerId=xxl-supplier-dispatch-recovery
workerId=xxl-supplier-query-recovery
```

三个节点使用同一个 `workerId`，写入 `locked_by` 后无法区分具体节点或分片。

这**不影响 CAS 正确性**，因为抢占依赖：

```text
event_id + version + locked_until
```

但会削弱故障排查时的节点定位能力。更理想的做法是不配置固定 `workerId`，让 `defaultWorkerId()` 生成带主机名和进程信息的唯一值，或在参数中按分片区分。

### 7.3 调度频率和批量参数与部署手册存在漂移

`docs/部署手册.md` 的建议值：

- 152：`0/5 * * * * ?`，`parallelism=8`
- 153：`0/10 * * * * ?`

预生产实际值：

- 152：`0/30 * * * * ?`，`parallelism=4`
- 153：`15/30 * * * * ?`，`parallelism=4`

这不影响分片正确性，但会降低补偿时效和吞吐。按 3 分片、每分片 100 条、30 秒一轮计算，152/153 各自的理论处理上限约为 300 条/30 秒，低于手册建议配置。

### 7.4 仓库模板与现场注册组不一致

`deploy/nacos/cardshop-trade-engine-prod.preprod.example.yaml` 中写的是：

```yaml
xxl-job:
  enabled: false
  executor:
    appname: cardshop-trade-engine-prod
```

而现场调度中心实际执行器组是：

```text
app_name = cardshop-trade-engine
```

如果后续误把该模板原样发布，执行器会注册到另一个组，152/153 将找不到执行器。当前现场组名是正确的，但这是明显的配置漂移风险。

### 7.5 当前未观察到数据级分片分布

最近几轮扫描结果均为 0，说明当前没有到期事件。分片参数正确不等于数据分布一定均衡；如果后续要做容量验证，建议在受控测试窗口构造多条不同 `event_id` 的事件，统计：

```sql
select mod(crc32(shard_key), 3) as shard_no,
       event_type,
       status,
       count(*) as cnt
from recharge_dispatch_outbox
group by shard_no, event_type, status
order by shard_no, event_type, status;
```

## 8. 建议

### 8.1 对 152/153

保持当前配置，不需要再修改路由策略：

```text
SHARDING_BROADCAST
trigger_status=1
shardTotal=3
```

继续观察：

- `xxl_job_log.executor_sharding_param` 是否为 `0/3`、`1/3`、`2/3`；
- 三节点应用日志是否分别打印 `shardIndex=0/1/2`；
- 各分片 `scanned/claimed/failed` 是否出现明显倾斜；
- 某节点下线后注册表是否及时刷新，避免分片长期空跑。

### 8.2 对 143/148

- **143**：保持 `FIRST`。如果确需分片，先为 `recharge_accept_anomaly` 设计分片字段和查询条件，不能只改调度路由。
- **148**：建议先改为 `FIRST`，消除“广播但不分片”的重复扫描；后续再按 `task_id` 实现真正的分片扫描。

### 8.3 对 149

保持停用。不要与 152 同时启用。

### 8.4 配置可重复性

建议把预生产 XXL-Job 的关键配置固化到运维脚本或部署手册中，至少包含：

- 执行器组名、地址和端口；
- 每个 Job 的 handler、路由策略、阻塞策略、cron、参数；
- 启用/停用状态；
- 149 与 152 的互斥关系；
- 变更前的调度锁、行锁、CAS 和回滚步骤。

同时修正 `deploy/nacos/cardshop-trade-engine-prod.preprod.example.yaml` 中与现场不一致的 `appname` 和 `enabled` 值，避免模板被误发布。
