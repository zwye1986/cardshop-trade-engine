## 初始实施计划

### 1. Redis 后续 Lua 和端口

- 新增 `cancel_unconfirmed_accept.lua`：
  - 仅处理 WAIT 未确认后的回滚。
  - 校验订单仍处于 `PENDING_MQ` 且版本匹配。
  - 对已预扣余额的订单释放 `frozen` 并恢复 `available`。
  - 清理 reservation、pending、org_index、事件索引。
  - 将订单标记为 `ACCEPT_REJECTED` 或删除未确认快照，按脚本 contract 固化。
- 新增 `mark_persist_queued.lua`：
  - MQ confirm ack 后推进 `persist_status=PERSIST_QUEUED`。
  - 写入 `persist_msg_id`、`mq_publish_count`、`updated_at`。
  - 保留 pending，等待 Consumer 落库后再由后续 `markDbPersisted` 清理。
- 新增应用端口：
  - `RechargeReliabilityPort` 或等价命名，承载 WAIT、cancel、mark queued。
  - 端口返回领域化结果，不暴露 Redis 原始数组。

### 2. RabbitMQ 发布端口

- 新增 `PersistTradeOrderMessage`。
- 新增 `PersistRechargeOrderMessagePublisher` 应用端口。
- 新增 Spring AMQP 适配器：
  - 使用 `RabbitTemplate.convertAndSend(exchange, routingKey, payload, correlationData)`。
  - 等待 `CorrelationData.getFuture()`，超时按 confirm 失败处理。
  - mandatory return 视为失败。
  - confirm callback 不访问 Redis/MySQL。
- 新增最小 MQ breaker：
  - 配置关闭或 failure threshold 命中时，Redis Lua 前返回 `MQ_UNAVAILABLE`。
  - 本轮只做内存态最小实现，后续再接监控和半开探测。

### 3. 下单编排改造

- `V1CreateRechargeOrderUseCaseService` 保持现有准备流程。
- Redis `accept` 返回 `ACCEPTED/ACCEPTED_FAILED` 后：
  - 执行 WAIT。
  - WAIT 成功：发布 MQ 并等待 confirm。
  - confirm 成功：调用 `mark_persist_queued.lua`。
  - confirm 失败：保留 Redis pending，返回系统繁忙或处理中语义。
  - WAIT 失败：调用 `cancel_unconfirmed_accept.lua`。
  - cancel 成功：返回系统繁忙，允许调用方稍后重试。
  - cancel 失败：写入 `recharge_accept_anomaly`，并返回“系统繁忙，请稍后查询订单状态”。
- `DUPLICATE/NONCE_REPLAY/CONFIG_CHANGED/BALANCE_REPAIRING/REDIS_WRITE_DISABLED/REDIS_UNAVAILABLE` 保持 fail-closed 映射。

### 4. 查单真实用例

- 新增订单查询端口：
  - Redis：按 `orgCode + outOrderSn` 读取 `order:{outOrderSn}` 快照。
  - MySQL：本轮不接入，留到 D7/D8 异步落库闭环后补。
- 新增 `V1QueryRechargeOrderUseCaseService`：
  - 读取商户资料和协议预检。
  - Redis 命中时按内部状态映射旧接口数字状态。
  - Redis 未命中时返回明确未找到；后续接入 MySQL 兜底后再调整。
  - 不同步调用供应商。

### 5. 作废真实用例

- 新增 `V1InvalidRechargeOrderUseCaseService`：
  - 读取商户资料和协议预检。
  - 订单未落库或 `persist_status != DB_PERSISTED`：返回处理中。
  - 已落库订单：幂等写入 `INVALID_ORDER` outbox，接口线程仍返回处理中，不同步调用供应商。
  - 不同步调用供应商。

## D7A：Persist Consumer 最小落库闭环计划

目标：补齐 RabbitMQ 落库消息到 MySQL 事实表的第一段闭环，让已 confirm 的 Redis 订单可以写入 `mc_order + recharge_order_ext + recharge_outbox`，并在事务提交后通过 `markDbPersisted` 清理 Redis pending。

实施边界：

1. 先实现不绑定 `@RabbitListener` 的 Consumer 核心服务，输入为 `PersistTradeOrderMessage`，输出为可供后续 Rabbit adapter 判断 ack/nack 的处理结果。
2. application 层只做快照选择、编排和错误语义，不直接依赖 MyBatis、RabbitMQ 或 Spring 事务。
3. infrastructure 层实现 MyBatis 写库端口，事务内写 `mc_order`、`recharge_order_ext`，并在 `dispatch_allowed=true` 时幂等写入 `SUPPLIER_DISPATCH` outbox。
4. Redis 最新快照优先；Redis 快照缺失或读取/映射异常时使用 MQ `initialOrderSnapshot` 兜底，并写 `persist_source=MQ_SNAPSHOT_FALLBACK`。
5. MySQL 事务提交成功后调用 `markDbPersisted`；事务失败时记录 error 日志并调用 `markPersistFailed`，pending 不清理，等待后续补偿。
6. 先补齐 producer 的 `initialOrderSnapshot` 字段，使兜底落库包含 `product_name/product_value/product_type/coupon_type/supplier_channel/request_hash_version/request_hash_alg` 等字段。

验收测试：

1. Consumer 核心服务：Redis 缺失时使用 MQ snapshot 落库并调用 `markDbPersisted`。
2. Consumer 核心服务：Redis 快照版本更新时使用 Redis 快照，`persist_source=REDIS_SNAPSHOT`。
3. Consumer 核心服务：Redis 快照读取异常时记录 error 日志并回退 MQ snapshot。
4. Consumer 核心服务：写库异常时调用 `markPersistFailed`，并返回可重试失败结果。
5. MyBatis 写库适配器：成功订单写 `mc_order + recharge_order_ext + SUPPLIER_DISPATCH outbox`。
6. MyBatis 写库适配器：业务失败订单不生成供应商派单 outbox。
7. V1 下单生产者：MQ `initialOrderSnapshot` 包含 D7A 兜底落库必需字段。
