# 交行直充交易引擎集成测试方案

> 更新时间：2026-07-08
> 适用范围：`cardshop-trade-engine` 开发、测试、预生产和生产灰度前的真实链路集成测试、压测、故障演练和结果评估。
> 不适用范围：单元测试、contract test、纯装配测试不纳入本文档。

## 1. 文档目标

本文档用于沉淀 `cardshop-trade-engine` 的阶段性集成测试方案。它不是一次性完成的测试报告，而是随 D7/D8 落库闭环、D9 供应商履约、D10 回调作废、D11/D12 补偿对账和生产灰度逐步完善的联调 runbook。

集成测试只验证真实系统边界：HTTP 入口、Nacos 配置、Redis、RabbitMQ、MySQL、Liquibase、旧卡管兼容数据、供应商/回调模拟器、监控指标和日志链路。单个类、单个方法、Lua contract、Mapper contract、Spring bean 装配等测试结果只可作为代码质量佐证，不作为本文集成测试用例。

### 3.2 cardshop-trade-engine 启动配置

部署包由 `./scripts/package.sh` 生成，测试机解压后通过 `bin/start.sh` 启停。服务器本地 `config/.<profile>.env` 只保留启动引导配置，启动脚本会加载这些键并提供给应用读取。`.env` 由 Bash `source` 读取，密码、JWT secret、API key 等同类密钥值必须用单引号包起来，尤其当值包含 `$`、`!`、空格、反引号、`&`、`|`、`;`、`<`、`>` 时。

```bash
APP_PROFILE=dev
SERVER_PORT=10080
CARD_SHOP_TRADE_JAVA_HOME=/path/to/jdk21
JAVA_OPTS="-Xms512m -Xmx512m -XX:+UseG1GC -Dfile.encoding=UTF-8"
NACOS_SERVER_ADDR=47.117.130.100:8848
NACOS_NAMESPACE=cardshop-trade-engine-dev
NACOS_GROUP=TRADE_ENGINE_DEV
NACOS_USERNAME=nacos
NACOS_PASSWORD='<从运维密钥或部署平台变量获取>'
SPRING_RABBITMQ_HOST=<rabbitmq-host>
SPRING_RABBITMQ_PORT=5672
SPRING_RABBITMQ_USERNAME=<rabbitmq-user>
SPRING_RABBITMQ_PASSWORD='<从运维密钥或部署平台变量获取>'
SPRING_RABBITMQ_VIRTUAL_HOST=cardshop-trade-dev
LEGACY_CARD_SHOP_BASE_URL=<旧卡管地址，未启用代理时留空>
V1_CARDAPI_JWT_SECRET='<从运维密钥或部署平台变量获取>'
```

MySQL、Redis、灰度名单、业务开关、SM4/SM3 商户密钥等运行配置必须来自 Nacos 或部署密钥，不能写入 Git、Markdown、启动脚本或应用日志。

Nacos 至少准备以下 DataId：

| DataId | 内容 |
| --- | --- |
| `cardshop-trade-engine-common.yaml` | 通用日志、Actuator、线程池、基础开关 |
| `cardshop-trade-engine-${profile}.yaml` | 环境级 datasource、Redis、RabbitMQ、Liquibase、灰度和业务开关 |
| `cardshop-trade-engine-supplier.yaml` | 供应商地址、超时、限频和模拟器配置 |
| `cardshop-trade-engine-risk.yaml` | 风控、限流、故障注入和演练开关 |

### 3.4 环境隔离要求

1. `local` profile 不参与本文任何集成测试结论。
2. dev/test/prod 不得共用 RabbitMQ vhost。
3. test/prod 不得共用 Redis DB index、key prefix 或 Sentinel master。
4. dev 复用旧卡管测试 Redis 时，只允许使用 `cardshop:trade:recharge:{orgCode}:...` 新链路 key，不得覆盖旧系统 token 以外的业务 key。
5. 生产 `spring.liquibase.enabled=false`，DDL 只允许由发布流水线执行。
6. 所有测试订单使用统一前缀，例如 `IT20260708HHmmssNNN`，便于清理、追踪和报表过滤。
7. 故障注入开关只能在 dev/test 打开，生产禁止执行破坏性故障演练。

### 4.2 MySQL 前置数据

集成测试必须准备独立的测试商户和商品，不使用真实生产商户直接压测。

| 数据对象 | 必填要求 | 说明 |
| --- | --- | --- |
| `mc_ext_depart` | 测试商户 `org_code`、`app_id`、`app_secret`、AES/SM4 密钥、可用状态、余额 | 用于 `/auth/getToken`、验签、余额预扣和灰度识别 |
| `mc_depart_product` | 测试商户绑定父产品 `product_id`，状态启用，价格配置满足订单金额 | 用于商品候选选择和商户权限校验 |

| `mc_order` | 确认兼容字段存在：`produt_code`、`order_Id`、`out_orderId`、`fail_code`、`fail_reason`、`direct_recharge_out_order_key` | D7/D8 落库和幂等唯一键验证 |
| `recharge_order_ext` | 表、唯一键、版本字段、状态字段、索引存在 | 验证 Redis/MQ/MySQL 一致性状态 |
| `mc_depart_record` | `before_balance`、`balance` nullable；`trade_engine_record_key` 生成列和唯一键存在 | 验证预扣流水幂等 |
| `recharge_outbox` | 表、`event_id` 唯一键、状态和重试索引存在 | D9 供应商履约前置 |
| `recharge_accept_anomaly` | 表和索引存在 | WAIT/cancel/Lua unknown 异常核查前置 |

### 4.3 Redis 前置数据

Redis 需要准备和核验以下 key 空间。示例中的真实 key 会自动叠加 `trade.engine.redis.key-prefix`，默认前缀为 `cardshop:trade`。

首次联调、全新 Redis DB 或新商户接入前必须先预热商户配置、商品配置和余额基线；`accept_recharge_order.lua` 只读取和校验这些 key，不负责从 MySQL 自动初始化。版本字段必须与 MySQL 源一致：`merchant:config.version = mc_ext_depart.id`，`product:config.version = mc_product.version`，`balance.available` 基线取自 `mc_ext_depart.balance`。若缺失或版本不一致，Lua 会按 fail closed 返回 `CONFIG_CHANGED` 或系统繁忙，不能把该结果误判为 RabbitMQ 或 MySQL 落库故障。

| Key 类型 | 示例 | 前置要求 |
| --- | --- | --- |
| Token | `token:app_id:{appId}` | `/auth/getToken` 生成；新旧服务共享 token 规则 |
| 商户余额 | `cardshop:trade:recharge:{orgCode}:balance` | 余额足够，字段版本与 Lua 期望一致 |
| 商户配置 | `cardshop:trade:recharge:{orgCode}:merchant:config` | 状态启用、版本号存在 |
| 商品配置 | `cardshop:trade:recharge:{orgCode}:product:{productId}:config` | 商品启用、价格/版本和 MySQL 候选一致 |
| 幂等 key | `cardshop:trade:recharge:{orgCode}:idem:{outOrderSn}` | 测试前不存在；重复请求时只能生成一个 |
| 订单 hash | `cardshop:trade:recharge:{orgCode}:order:{outOrderSn}` | 下单后生成，包含 accept/persist/order_version 等字段 |
| 预扣 reservation | `cardshop:trade:recharge:{orgCode}:reservation:{orderId}` | 成功预扣时生成，落库/刷账前可追踪 |
| pending ZSET | `cardshop:trade:recharge:{orgCode}:persist:pending` | MQ confirm 成功到 DB 标记完成前存在 |
| org index | `cardshop:trade:recharge:persist:pending:org_index:{bucket}` | pending 商户索引，补投扫描前置 |
| repairing lock | `cardshop:trade:recharge:{orgCode}:balance:repairing_lock` | 用于余额修复期间阻断新单 |

### 4.4 RabbitMQ 前置拓扑

| 组件 | 默认名称 | 验证重点 |
| --- | --- | --- |
| 持久化 exchange | `recharge.persist.exchange` | durable，publisher confirm 开启 |
| 持久化 routing key | `recharge.persist.mysql` | 与主队列 binding 一致 |
| 主队列 | `recharge.persist.mysql.queue` | 推荐 Quorum Queue，手动 ack，DLX 已配置 |
| retry exchange | `recharge.persist.retry.exchange` | 业务失败后先进入 retry |
| retry queue | `recharge.persist.mysql.retry.queue` | TTL 到期后 DLX 回主队列 |
| DLX | `recharge.persist.dlx` | poison message 和 reject 可进入 DLQ |
| DLQ | `recharge.persist.mysql.dlq` | 保留反序列化失败和超过重试上限消息 |

### 4.5 业务请求前提

1. 准备测试商户 `app_id/app_secret/aesKey/orgCode`，真实值只保存在密钥系统或受保护的测试数据文件。
2. `/auth/getToken` 能成功返回 token，Redis 中 `token:app_id:{appId}` 已写入。
3. `trade.engine.routing.gray-app-ids` 或 `gray-org-codes` 包含测试商户。
4. 下单请求按 V1 协议生成 `timestamp`、`nonce_str`、`sign`；开启 SM4 时请求体按商户密钥加密。
5. `notify_url` 指向测试回调接收器，不能指向真实商户生产地址。
6. 如果执行 D9 之后用例，供应商接口必须使用测试供应商或本地/测试环境 mock server。

## 5. 集成测试目标和指标

### 5.1 阶段目标

| 阶段 | 目标 | 当前状态 |
| --- | --- | --- |
| D7/D8 主链路 | 证明 Redis 接单、WAIT、MQ confirm、RabbitMQ Consumer、MySQL 落库、Redis `markDbPersisted/markPersistFailed` 可在同一真实订单链路闭环 | 当前最优先执行 |
| D9 履约链路 | 证明 `SUPPLIER_DISPATCH` outbox、供应商 Gateway、供应商流水、订单状态回写可闭环 | 代码级首版和 fake HTTP Gateway 单测已具备；待真实供应商/mock server 集成执行 |
| D10 回调/作废 | 证明查单、作废、回调签名、回调重试和商户非 200 退避可闭环 | 代码级首版已具备；待供应商作废、商户回调 mock 和退款/释放流水联调 |
| D11/D12 补偿对账 | 证明 pending 补投、outbox 重试、余额刷账、异常核查、缓存修复可恢复一致性 | MQ 补投 claim/二次确认、job facade 和 MySQL 余额刷账首版已具备；待真实 XXL-Job、余额对账/缓存修复真实适配和故障演练执行 |
| 灰度准入 | 证明灰度商户小流量接入后可观测、可回滚、无重复扣款/重复派单 | 生产灰度前执行 |

### 5.2 技术指标

首轮指标用于建立基线，后续压测可按容量目标调整。

| 指标 | 目标值 | 采集方式 |
| --- | --- | --- |
| `/createRechargeOrder` 成功请求 P95 | 首轮基线不高于 300ms | 压测工具、网关日志、应用 timer |
| `/createRechargeOrder` 成功请求 P99 | 首轮基线不高于 800ms | 压测工具、网关日志、应用 timer |
| Redis `accept.lua` P99 | 不高于 30ms | `trade.lua.accept.duration` |
| Redis `accept.lua` P99.9 | 不高于 100ms | `trade.lua.accept.duration` |
| Redis WAIT 失败率 | 正常环境低于 0.1%，故障演练期间必须可解释 | `trade_redis_wait_total` |
| MQ publish confirm P99 | 首轮基线不高于 500ms | `trade_mq_publish_confirm_latency`、应用日志 |
| MQ confirm 失败率 | 正常环境为 0；故障注入时 breaker 行为符合预期 | `trade_mq_publish_confirm_total` |
| Consumer 落库延迟 P95 | 首轮基线不高于 3s | MQ 消费时间、`recharge_order_ext.created_at/updated_at` |
| pending 清理延迟 P95 | DB 落库后 5s 内清理 | Redis pending ZSET、`markDbPersisted` 日志 |
| MySQL 落库成功率 | 正常环境 100% | `trade_persist_consume_total`、表数据 |
| DLQ 消息数 | 正常业务流量为 0 | RabbitMQ 管理端 |
| readiness | 压测和联调期间保持 UP | `/actuator/health/readiness` |

### 5.3 业务指标

| 指标 | 目标 |
| --- | --- |
| 重复受理 | 同一 `orgCode + out_order_sn` 并发请求只生成一个有效订单 |
| 重复扣余额 | 0 |
| 重复预扣流水 | 0；`mc_depart_record` 对同一订单的 `PRE_DEDUCT` 幂等 |
| 订单丢失 | 0；Redis、MQ、MySQL 至少一个证据可追踪 |
| 失败订单可追踪 | 身份和签名通过后的业务校验失败必须能落 Redis/MySQL，并有失败码 |
| 成功订单一致性 | Redis 订单、`mc_order`、`recharge_order_ext`、`mc_depart_record`、`recharge_outbox` 字段一致 |
| 灰度隔离 | 灰度商户进入新链路，非灰度商户代理旧系统 |
| 回滚安全 | 关闭灰度或关闭路由后，新请求不再进入新链路；已受理订单继续可补偿 |

### 7.2 证据采集清单

每次集成测试必须至少保留以下证据：

1. 应用启动日志：profile、端口、Nacos、readiness。
2. 下单请求样本：脱敏后的 `out_order_sn`、响应 code、trace_id。
3. Redis 证据：order hash、idem、pending、org_index、reservation 的存在和清理结果。
4. RabbitMQ 证据：主队列、retry、DLQ、publish confirm、consumer ack/nack。
5. MySQL 证据：`mc_order`、`recharge_order_ext`、`mc_depart_record`、`recharge_outbox` 行数据。
6. 指标截图或导出：Prometheus/Actuator、压测报告、RabbitMQ 管理端。
7. 异常场景日志：必须能按 `trace_id/org_code/out_order_sn/order_id/message_id` 串联。

示例核查 SQL 只能使用测试订单前缀：

```sql
select order_Id, out_orderId, order_status, data_status, fail_code, fail_reason
from mc_order
where out_orderId like 'IT20260708%';

select order_id, out_order_sn, persist_status, persist_source, redis_order_version,
       persisted_version, dispatch_status, balance_reserved, last_error
from recharge_order_ext
where out_order_sn like 'IT20260708%';

select order_id, type, value, trade_engine_record_key
from mc_depart_record
where trade_engine_record_key like 'PRE_DEDUCT:%'
  and order_id in (
      select order_Id from mc_order where out_orderId like 'IT20260708%'
  );

select event_id, aggregate_id, event_type, status, retry_count, locked_until
from recharge_outbox
where aggregate_id in (
    select order_Id from mc_order where out_orderId like 'IT20260708%'
);
```

### 7.3 通过标准

D7/D8 主链路准入通过需要同时满足：

1. 环境启动、readiness、Nacos、Redis、RabbitMQ、MySQL 全部正常。
2. 成功订单可完成 Redis 接单、WAIT、MQ confirm、Consumer、MySQL 落库、Redis pending 清理。
3. 失败订单可追踪，不派单、不产生预扣流水。
4. 重复订单和重复 MQ 消费不造成重复扣款、重复流水、重复 outbox。
5. RabbitMQ retry/DLQ 行为可观测，毒消息不阻断正常消息。
6. Redis 快照缺失时 MQ snapshot 兜底落库可验证。
7. 压测基线中核心指标未超过本方案定义的首轮目标，或超过时有明确瓶颈分析和整改项。

灰度前通过还必须满足：

1. D9-D12 补偿和履约用例完成。
2. 回调、作废、供应商异常、余额刷账和对账用例完成。
3. 生产 profile 的写开关、路由开关、灰度开关和回滚路径演练完成。
4. 监控告警覆盖 Redis pending、RabbitMQ 堆积/DLQ、MySQL 落库失败、余额差异、Lua 慢执行和 WAIT 失败率。

## 8. 技术实现方案

### 8.1 测试驱动架构

集成测试建议由四类工具组成：

| 工具 | 职责 |
| --- | --- |
| V1 请求生成器 | 生成 token、SM4 请求体、SM3 签名、nonce、timestamp、订单号，支持批量和并发 |
| 压测工具 | 执行阶梯升压、秒杀尖峰、长稳压和混合读写流量，可选 k6、JMeter、Gatling |
| Mock 服务 | 模拟供应商、商户回调、旧卡管代理响应和异常行为 |
| 结果核查器 | 从 Redis、RabbitMQ、MySQL、Prometheus 和日志聚合订单级证据，输出通过/失败报告 |

V1 请求生成器不应硬编码密钥。密钥从本地忽略文件、CI secret、部署平台变量或测试数据服务读取，日志只打印脱敏 appId、orgCode、out_order_sn 和 trace_id。

### 8.2 真实业务请求链模拟

标准请求链：

```text
1. /v1/cardapi/auth/getToken
2. Redis 写 token:app_id:{appId}
3. /v1/cardapi/order/createRechargeOrder
4. API 层解密、验签、timestamp、nonce、灰度路由
5. MySQL 读取商户和商品候选
6. Redis Lua 原子接单、幂等、余额预扣、pending 写入
7. Redis WAIT
8. RabbitMQ publish + confirm
9. markPersistQueued
10. RabbitMQ listener 消费
11. MySQL 事务写 mc_order/recharge_order_ext/mc_depart_record/recharge_outbox
12. markDbPersisted 或 markPersistFailed
13. /v1/cardapi/order/getRechargeOrder 验证 Redis/MySQL 状态
```

阶段性扩展请求链：

```text
14. outbox worker 抢占 SUPPLIER_DISPATCH
15. supplier mock 返回成功、失败、超时或处理中
16. 更新供应商流水和 mc_order 状态
17. 生成商户回调任务
18. callback mock 返回 200、500 或超时
19. 作废接口生成 INVALID_ORDER outbox
20. 补投、对账、余额刷账和异常核查 Job 恢复一致性
```

### 8.3 秒杀/抢购流量曲线

压测至少覆盖以下模型：

| 曲线 | 描述 | 目的 |
| --- | --- | --- |
| 阶梯升压 | 每 5 分钟提升一个 RPS 档位 | 找到系统基线容量和第一瓶颈 |
| 秒杀尖峰 | 30 秒内从 0 到目标峰值，保持 2 分钟后快速回落 | 验证 Redis Lua、MQ confirm、pending 排空能力 |
| 热商户热点 | 80% 流量集中在一个测试商户，20% 分散到其他商户 | 验证 hash tag 热点、商户余额 key 和 pending org_index |
| 重复订单风暴 | 高并发请求同一 `out_order_sn` | 验证 Redis 幂等、MySQL 唯一键和流水幂等兜底 |
| 混合读写 | 下单、查单按 1:5 或 1:10 混合 | 验证查单不会放大供应商压力或拖垮写链路 |
| 长稳压 | 2-4 小时稳定压力 | 验证连接池、内存、线程池、MQ 堆积和日志量 |

### 8.4 故障注入方式

故障注入只允许在 dev/test 执行。

| 故障 | 注入方式 | 验证重点 |
| --- | --- | --- |
| Redis 不可达 | 临时改 Nacos Redis 地址、网络隔离或使用故障注入开关 | 下单 fail closed，不代理旧系统，不产生脏订单 |
| Redis WAIT 失败 | 降低副本可用性或调整 WAIT 参数 | cancel 成功/失败路径、anomaly 登记 |
| Redis BUSY/Lua timeout | 使用测试 Redis 脚本阻塞或故障注入 | `ACCEPT_STATE_UNKNOWN`、HA Guard、异常核查 |
| RabbitMQ confirm timeout | 阻断 broker、错误 exchange/routing、降低 timeout | pending 保留、breaker、补投恢复 |
| Consumer 崩溃 | 消费过程中停止应用或断开连接 | 未 ack 消息重放，MySQL 幂等 |
| MySQL 写失败 | 临时只读、断开 datasource 或注入 SQL 异常 | retry、`markPersistFailed`、pending 不丢 |
| 供应商超时 | mock 延迟超过超时 | outbox 重试，不阻塞查单 |
| 回调失败 | callback mock 返回非 200 | 回调退避重试和失败可追踪 |

### 8.5 自动化实现建议

短期可先使用脚本化半自动方式：

1. `scripts/package.sh` 打包。

3. V1 请求生成器发起 token、下单、查单请求。
4. Redis/RabbitMQ/MySQL 核查脚本按订单前缀采集结果。
5. 生成 Markdown 或 HTML 结果报告。

### 11.1 test188 本轮执行证据

- 应用状态：`dev` profile 运行，`/actuator/health/liveness` 与 `/actuator/health/readiness` 均为 `UP`。
- Redis WAIT：dev Redis 在 `WAIT 1 100` 下返回 `0`，因此本轮按确认策略临时使用 `trade.engine.redis.wait-replicas=0` 跑通单笔 happy path。该结论不能替代 `WAIT >= 1` 环境下的复制确认测试。
- RabbitMQ：管理端版本为 `3.8.8`，Erlang `21.3`，vhost 为 `cardshop-trade-dev`。主队列和 DLQ 使用 quorum queue；由于 RabbitMQ `3.8.8` 不接受 quorum queue 搭配 `x-message-ttl`，`recharge.persist.mysql.retry.queue` 调整为 classic durable queue + TTL/DLX。
- RabbitMQ 连接问题：曾出现 `cardshop-trade-dev` connection/consumer 为 `0`。代码分析和 class histogram 证明根因是 `RechargeOrderPersistencePort`、`PersistRechargeOrderConsumerService`、`RabbitPersistRechargeOrderMessageListener` 被早期 `@ConditionalOnBean` 级联跳过；补齐 `TradeEngineMybatisPersistenceAutoConfiguration`、`TradeEngineConsumerAutoConfiguration`、`TradeEngineRabbitListenerAutoConfiguration` 后，RabbitMQ connection 恢复为 `1`，主队列 consumer 恢复为 `4`。
- 单笔测试单：`out_order_sn=IT20260708512338083`，平台订单号 `202607081208032650608747`。Prometheus RabbitMQ 指标显示 `rabbitmq_connections=1`、`rabbitmq_channels=5`、`rabbitmq_published_total=1`、`rabbitmq_consumed_total=1`；主队列 `messages_ready=0`、`messages_unacknowledged=0`，retry queue 和 DLQ 无积压。
- MySQL 落库：`mc_order` 1 行，`order_status=2`、`data_status=PROCESSED`；`recharge_order_ext` 1 行，`persist_status=DB_PERSISTED`、`persist_source=MQ_SNAPSHOT_FALLBACK`、`redis_order_version=1`、`persisted_version=1`、`dispatch_status=WAIT_DISPATCH`、`balance_reserved=1`；`mc_depart_record` 1 行；`recharge_outbox` 1 行。
- Broker 级自动化用例：`RabbitPersistRechargeOrderBrokerIntegrationTest` 已覆盖真实 broker 拓扑声明、retry queue 延迟重投后 ack、坏消息拒绝进 DLQ、consumer channel 关闭导致未 ack 消息重投。本轮真实环境以单笔链路验证为主，broker IT 可作为后续回归用例接入 dev/test 准入。

### 11.2 “异常窗口可恢复”目标评估

结论：D7/D8 的 Redis 接单、RabbitMQ confirm、Consumer 落 MySQL、Redis pending 补投这一段已经达到“代码级主要异常窗口可恢复”，并且 test188 已证明最小 happy path 可闭环；accept Lua timeout、Redis BUSY 和未知 Redis 异常也已补齐代码级 anomaly 登记与 HA Guard 关闭。但“异常窗口可恢复”作为上线准入目标尚未完全达成，真实 `WAIT >= 1`、Redis 状态未知故障注入、XXL-Job 故障演练、自动三方核查和缓存修复仍缺真实环境证据或完整实现。

| 异常窗口 | 代码现状 | 本轮证据 | 结论 |
| --- | --- | --- | --- |
| RabbitMQ 全局不可用发生在 Redis 写入前 | `V1CreateRechargeOrderUseCaseService` 在 Redis Lua 前检查 `persistMessagePublisher.isAvailable()`；publisher 连续失败会打开最小 breaker，新订单 fail closed，不制造新的 Redis pending | 本轮主要验证 RabbitMQ 连接和 consumer 恢复，未做 broker 不可用故障注入 | 代码级部分达成；breaker 的 rolling window / half-open 仍是 TODO |
| Redis 写成功但 MQ confirm 失败或超时 | accept Lua 原子写订单、reservation、`persist:pending` 和 `org_index`；publisher confirm 失败时接口返回处理中语义，pending 保留；`RechargePersistMqRepublishService` + `RedisPendingPersistOrderAdapter` 可扫描、claim、MySQL 二次确认并补投 MQ | test188 happy path confirm 成功；本地/代码测试覆盖 confirm nack、pending 补投编排 | 代码级达成，真实故障演练未完成 |
| Consumer 写 MySQL 失败 | `PersistRechargeOrderConsumerService` 捕获事务异常后调用 `markPersistFailed`，保留 pending 并刷新下次重试时间；Rabbit listener 不 ack，进入 retry queue，超过阈值进 DLQ | broker IT 覆盖 retry/DLQ；test188 单笔未注入 MySQL 故障 | 代码级达成，需 MySQL 短时不可用演练 |
| MySQL 已提交但 Redis `markDbPersisted` 失败 | Consumer 返回 `PERSISTED_REDIS_MARK_FAILED` 且 listener ack，避免已提交订单无限重复；pending 补投扫描会先用 MySQL `PersistedOrderStatePort` 二次确认并修复 Redis `DB_PERSISTED` 状态 | 单笔 happy path 未触发该窗口；代码测试覆盖 mark 超时/取消 | 部分达成；`RechargeCacheRepairPort` 真实基础设施实现仍缺，缓存修复不应只依赖 noop |
| Redis 快照缺失但 MQ 消息存在 | Consumer 优先读 Redis 最新快照，缺失或读取异常时使用 MQ `initialOrderSnapshot` 兜底落库，并写 `persist_source=MQ_SNAPSHOT_FALLBACK` | test188 单笔 `recharge_order_ext.persist_source=MQ_SNAPSHOT_FALLBACK` | 该窗口已在本轮被实际触发并成功落库；后续补告警和缓存重建 |
| WAIT 未达标且 cancel 成功 | 同 session WAIT 未达标时调用 `cancel_unconfirmed_accept.lua`，释放余额、清理 reservation/pending/org_index，接口返回系统繁忙 | dev 因 `wait-replicas=0` 未覆盖该窗口 | 代码级达成，需 `WAIT >= 1` 环境验证 |
| WAIT 未达标且 cancel 失败 | 用例层登记 `WAIT_CANCEL_FAILED` anomaly，关闭 Redis HA Guard 写入，接口返回“稍后查单”保守语义 | 代码测试覆盖 anomaly 登记、HA Guard 关闭；真实环境未注入 | 部分达成；`AcceptAnomalyAutoCheckService` 当前只用合并查单端口，缺显式 Redis/MQ/MySQL 三方 probe，自动判定未受理仍未达成 |
| Redis Lua timeout / Redis BUSY / 客户端状态未知 | `RedisSessionAcceptReliabilityAdapter` 已将 BUSY、timeout、其他 Redis 异常分类为 `REDIS_BUSY`、`LUA_TIMEOUT`、`ACCEPT_STATE_UNKNOWN`，关闭 HA Guard，并通过 `AcceptAnomalyRecordPort` 异步登记 anomaly | 单元测试覆盖三类状态未知分支；test188 未做真实 Redis 故障注入 | 代码级达成，生产灰度前仍需真实 Redis 故障演练 |
| 重复消费或补投并发 | MySQL mapper 使用 `on duplicate key update`、版本单调推进、outbox `event_id` 幂等、`mc_depart_record` 生成列唯一键兜底；pending 补投有订单级 claim | 单笔测试未覆盖并发，代码/mapper 测试覆盖主要契约 | 代码级达成，需并发故障演练；`mc_order` 唯一键漂移仍是独立前置风险 |

下一轮集成测试应优先补：在可确认副本的 Redis 环境恢复 `wait-replicas>=1`；执行 Redis Lua timeout/BUSY、RabbitMQ confirm nack/timeout、MySQL 短时不可用、consumer crash、Redis mark 失败、pending 补投并发的真实故障演练；补齐 Redis/MQ/MySQL 三方自动核查和真实缓存修复端口后，再把“异常窗口可恢复”从“代码级部分达成”升级为“集成准入通过”。
