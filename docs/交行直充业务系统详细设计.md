# cardshop-trade-engine 系统详细设计

> 交行通知认证目标已于2026-10-19修订：业务正文取消sign/keyId，采用开放平台RSA/SM2。本文旧HMAC通知描述的适用边界及服务待实施项，以文末「交行开放平台通知认证修订 2026-10-19」为准。

## 1. 文档说明、当前实现边界与术语

本文是 `cardshop-trade-engine` 的实现级详细设计，按系统层次和业务模块组织，用来约束 Java 代码、Redis Lua、RabbitMQ、MySQL/Liquibase、XXL-Job、Nacos 配置和 dev/test 集成测试。执行证据、联调日志和测试单据不写入本文，统一沉淀在 `docs/集成测试.md`；测试规划、用例编号和执行口径统一沉淀在 `docs/集成测试方案.md`。

当前实现边界如下：

| 边界 | 当前结论 |
| --- | --- |
| 接入协议 | 兼容旧 `/v1/cardapi`，优先覆盖 token、创建直充订单、查单、作废四类能力。 |
| 写入模型 | 下单链路 Redis-first，接口返回前完成 Redis 原子接单、Redis WAIT、RabbitMQ publish confirm；MySQL 由异步 Consumer 落库。 |
| 履约模型 | MySQL 订单事实提交后，通过拆分后的 `recharge_dispatch_outbox` 驱动供应商派单/查单/作废，通过 `recharge_balance_delta_outbox` 驱动余额刷账；旧 `recharge_outbox` 是未上线旧实现，不进入目标模型。 |
| 测试环境 | 集成测试只按 dev/test 环境执行；local 只可作为开发自测，不作为本文验收证据口径。 |
| 手工入口 | `ManualRechargeJobController` 只允许 dev/test profile、`trade.engine.integration.manual-job-enabled=true`、服务器本机 loopback 调用。 |
| 敏感配置 | Nacos、`.env`、部署脚本只写变量名和占位符。同类密钥、token、密码、签名密钥、AES/SM4 密钥等值在 `.env` 中必须使用单引号包裹，例如 `JWT_SECRET='<secret-value>'`，禁止提交真实值。 |

术语说明：

| 术语 | 含义 |
| --- | --- |
| Redis accept | `accept_recharge_order.lua` 原子完成幂等、校验、余额预扣、订单 hash、pending ZSET 和事件索引写入。 |
| pending | Redis 中等待 MQ 补投或 MySQL 落库追平的订单索引，核心 key 为 `recharge:{orgCode}:persist:pending`。 |
| initial snapshot | MQ 消息 `PersistTradeOrderMessage.initialOrderSnapshot` 携带的最小完整订单快照，用于 Redis 快照不可读时兜底落库。 |
| outbox | MySQL 可靠事件表族。目标态分为 `recharge_dispatch_outbox`（供应商履约生命周期）与 `recharge_balance_delta_outbox`（余额刷账生命周期）；`recharge_outbox` 仅作为未上线旧混合实现背景。 |
| notify task | MySQL 表 `recharge_notify_task`，承载商户回调重试任务。 |
| accept anomaly | MySQL 表 `recharge_accept_anomaly`，记录 Redis 接单状态未知窗口的核查入口。 |

旧代码注释仍可能引用旧章节号。为保持可追溯性，本文保留稳定小节标题：`Redis Lua 入参与 Key 构造`、`异步落库 Consumer`、`派单 Outbox`、`回调设计`、`XXL-Job Handler 契约`。后续改代码注释时应优先引用这些标题，而不是旧章节号。

## 2. 系统模块与依赖关系

Maven 根工程按责任拆分为以下模块：

| 模块 | 职责 | 依赖约束 |
| --- | --- | --- |
| `cardshop-trade-engine-domain` | 领域状态、枚举、纯业务规则。 | 不依赖 Spring、MyBatis、Redis、RabbitMQ。 |
| `cardshop-trade-engine-application` | 用例编排、端口接口、可靠性补偿服务。 | 依赖 domain，不依赖具体中间件实现。 |
| `cardshop-trade-engine-api` | WebFlux Controller、V1 DTO、协议预检、V1 路由。 | 调用 application use case 和安全/路由组件。 |
| `cardshop-trade-engine-infrastructure` | Redis Lua 适配、RabbitMQ、MyBatis、Nacos 配置绑定。 | 实现 application 端口，不能反向污染 domain。 |
| `cardshop-trade-engine-job` | framework-free `runOnce(...)` 任务门面。 | 依赖 application 服务，不直接暴露 HTTP。 |
| `cardshop-trade-engine-bootstrap` | Spring Boot 启动、Actuator、auto-configuration、dev/test 人工入口。 | 负责真实 Bean 装配和 profile 边界。 |
| `cardshop-trade-engine-migration` | Liquibase changelog。 | DDL COMMENT 是字段字典权威来源之一。 |
| `cardshop-trade-engine-test-support` | 集成测试夹具。 | 只放跨模块测试复用能力。 |

依赖方向必须保持 `api/bootstrap/job/infrastructure -> application -> domain`。Infrastructure 只能通过端口向上提供能力，domain 不能出现 Spring 注解、Mapper、Redis key 或 MQ payload。

关键运行装配：

| 装配项 | 约束 |
| --- | --- |
| MyBatis | `TradeEngineMybatisPersistenceAutoConfiguration` 必须在 MyBatis-Plus 自动配置、事务管理器自动配置之后执行，确保 `BaseMapper` 通用方法和 `PlatformTransactionManager` 可用。 |
| Consumer | `TradeEngineConsumerAutoConfiguration` 在 MySQL 落库端口之后创建 `PersistRechargeOrderConsumerService`，再由 Rabbit listener 订阅队列。 |
| Redis pending | `TradeEngineRedisPendingAutoConfiguration` 负责 `RedisPendingPersistOrderAdapter` 和 Redis 快照端口，不在普通 infrastructure configuration 中重复声明同签名 Bean。 |
| D12 job facade | 余额刷账、余额对账、缓存修复服务只允许构造参数级 fallback；`runOnce` 执行时必须晚绑定真实端口，缺失时 fail-fast，不能长期固化 noop。 |

## 3. API/V1 接入层

`V1RechargeOrderController` 承接 `/v1/cardapi/order` 三个旧兼容入口：

| 路径 | 用例 | 当前行为 |
| --- | --- | --- |
| `/v1/cardapi/order/createRechargeOrder` | 创建直充订单 | 认证后只要路径受支持且路由开关开启，即进入新链路；新链路异步调用 `V1CreateRechargeOrderUseCaseService`。 |
| `/v1/cardapi/order/getRechargeOrder` | 查单 | 认证后只要路径受支持且路由开关开启，即执行新查单；新查单 Redis 优先、MySQL 兜底。 |
| `/v1/cardapi/order/invalid` | 作废 | 认证后只要路径受支持且路由开关开启，即执行作废用例；未落 MySQL 的订单不得直接调用供应商。 |

接入层只处理协议兼容、认证、临时全量接管路由、旧链路代理兜底和响应包装，不直接拼 Redis key、不写 MySQL、不发布 RabbitMQ。token 兼容校验可能读取共享 Redis key `token:app_id:{appId}`，必须放到 `boundedElastic` 或等价隔离线程，避免阻塞 Netty event-loop。

临时接入口径：dev/test 当前共用 test188 的 `dev` profile，现阶段只接入 A39 交行机构，暂不按灰度名单切流。`trade.engine.routing.enabled=true` 且 path 在 `supported-paths` 内时，`/auth/getToken`、下单、查单、作废均直接进入新交易引擎；`gray-org-codes` 和 `gray-app-ids` 暂不参与路由判定，仅保留为后续恢复灰度/生产切流时的配置兼容字段。V1.2统一切换后，路由开关关闭或path不受支持时直接拒绝，不再代理旧系统。

V1 协议基线：

| 项 | 规则 |
| --- | --- |
| 响应包装 | `V1CardApiResponse` 固定 `code/msg/data` 三段式，失败时保留旧接口数字码语义。 |
| 请求体 | 外部 JSON 支持 snake_case 和兼容 camelCase alias；落到 DTO 后再做协议预检。 |
| 签名 | 创建、查单、作废请求必须参与 timestamp、nonce、sign 校验；通过有效token确定商户，使用商户当前独立signKey，见3.1节。 |
| 防重放 | `nonce_str` 写 Redis nonce key，TTL 由 `trade.engine.v1.nonce-replay-ttl-seconds` 控制。 |
| 身份可信源 | 创建订单请求里的 `org_code` 仅兼容承载，真实 `orgCode/appId` 以后端 token 和商户资料为准。 |
| 压测验签 | V1.2取消所有签名旁路；`X-Load-Test`及旧load-test-token配置不再影响验签。压测同样使用真实HMAC-SM3签名。 |

创建订单协议处理流程：

1. `V1TokenAuthenticator` 解析 Authorization，校验 JWT 和最后签发 token。
2. `V1RouteDecisionService` 根据path和总路由开关决定是否开放V1.2；关闭时拒绝，不向旧系统代理。
3. `V1ProtocolPrecheckService` 完成JSON、SM4、timestamp和HMAC-SM3预检；nonce防重放由后续Redis受理负责，不允许旁路。
4. `V1CreateRechargeOrderUseCaseService` 读取商户资料，并按请求父产品号解析 Redis 选品快照；快照缺失或达到刷新窗口时，只有持有父商品刷新锁的请求从 MySQL 候选中选定实际子商品并刷新缓存。
5. Java 使用选中子商品快照执行 Redis `refreshIfMissingOrStale`，原子保持父商品选品快照和实际子商品配置一致，再生成 request hash 并构造 `AcceptRechargeOrderCommand`。
6. Redis accept、WAIT、MQ confirm 由 application 用例编排；接口只返回旧协议可理解的成功、业务失败、重复、处理中或系统繁忙。

商户安全资料读取约定：

1. `prepare()` 需要 `aesKey/enabled/configVersion` 做SM4和Lua版本门禁（HMAC-SM3使用独立凭证），不能只依赖 Redis
   `merchant:config`（该 key 按设计只存 `status/version`，禁止写密钥）。
2. `V1MerchantProfilePort` 默认由 `CachedV1MerchantProfilePort` 装饰 MySQL 适配器：对
   `findByAppIdAndOrgCode` / `findByOrgCode` 使用进程内短 TTL 本地缓存，避免压测或高峰下每单直打
   `mc_ext_depart` 与异步落库 Consumer 争抢 Hikari。
3. 默认 `enabled=true`、命中 TTL `60s`、未命中负缓存 TTL `10s`、单实例最大条目 `1024`；密钥轮换或停用商户
   最多延迟一个 TTL 生效。`findByAppIdAndAppSecret`（发 token）不走该本地缓存，避免把密钥拼进缓存键。
4. 本地缓存查找结果通过低基数指标
   `trade.engine.merchant.profile.cache.hit.total{result=hit|negative|miss,lookup_type=app_org|org}`
   暴露；禁止 appId/orgCode/aesKey 进入标签。命中路径不得输出 `aesKey`；该缓存不替代 Redis
   `merchant:config` 启动预热或批量缓存修复。



### 3.1 V1.2 HMAC-SM3 签名升级（2026-10-16修订）

协议以《交行直充接口技术文档-V1.2-商户级签名密钥修订稿》（2026-10-16）及本节为准。本次文档修订替代“每次getToken生成新密钥并绑定订单”的上一轮方案；标准Base64、operation前缀、百分号编码和signVersion均不启用。

实施状态：2026-10-16代码已切换至本节商户级方案，包含服务端、模拟器及Java源码示例；本地验证记录见实施计划，真实环境联调另行记录。

1. 按商户机构orgCode及环境管理独立签名密钥。商户首次成功getToken时初始化32字节安全随机signKey及唯一keyId；已有当前有效版本时直接复用并与token一并返回。普通token刷新不轮换keyId/signKey，同一商户同一环境仅有一个当前有效版本；并发首次签发须原子保证唯一。signKey采用43字符Base64URL无填充编码，完整32字节用于HMAC-SM3，不从token、aesKey或app_secret派生，不截取。
2. aesKey仅用于SM4请求体编解码，完全退出新版签名用途。明文测试配置下不以aesKey是否存在决定验签资格，启用SM4时仍严格校验其格式。签名按ASCII字段名升序，以原值key=value和半角逗号拼接，UTF-8编码，不增加操作名前缀、不转义、不trim。结果为64字符小写Hex，解码后常量时间比较，失败不回退旧算法。
3. 下单签名字段为account/nonce_str/notify_url/num/out_order_sn/product_id/timestamp；查询、作废为nonce_str/out_order_sn/timestamp。请求缺失/null/空串不参与，0参与。原有服务端选品、价格、身份和状态规则保留，不信任请求额外字段。
4. 两类回调使用对外文档定义的下划线字段名及keyId，全部定义字段参与签名，空字符串保留为key=；不再新增独立callbackSignKey。字段缺失和JSON null不自行补签或静默丢弃。
5. token用于访问鉴权，默认3小时到期、建议2小时刷新，刷新后旧token失效；signKey独立有效至专门轮换或撤销，不因token到期、刷新或服务重启自动改变。新请求先校验当前token并确定可信商户，再按商户读取当前有效密钥验签，不需要token与特定keyId绑定。token唯一签发标识应使用独立jti等字段，不能再依赖每次变化的keyId。
6. 订单不保存signKey或keyId绑定，Redis接单、MQ兜底和MySQL订单持久化不承担密钥选择职责。新建两类回调时按订单可信orgCode加载商户当前密钥并签名；同一订单跨轮换生成的不同通知可以使用不同keyId。接收方按可信商户及报文keyId选对应密钥，验签后核对订单归属、业务状态、防重放和幂等，不比较订单创建时的keyId。
7. 回调任务保存keyId及已签名报文，正常重试保持原报文；发送前按商户及任务报文keyId复核版本有效性，不重新选择当前版本代替旧版本。轮换与getToken分离：协调暂停新请求及新回调生成，平台启用新版本，调用方经HTTPS获取并保存后恢复。旧版退出业务请求和新回调签名用途，但允许已签名任务重试。密钥撤销则连旧任务发送及验签一并拒绝，补发需以新密钥显式重建通知，不涉及订单换绑。
8. 密钥加密持久化，日志、DTO的toString、指标、订单快照和MQ中不得包含明文。未轮换密钥没有随token计算的TTL；轮换旧版保留至该版本已签名任务重试及双方约定的人工补发期限结束，不再按某批绑定订单的完整生命周期计算。未知、跨商户及撤销keyId拒绝，不尝试其他版本，不回退算法；普通getToken不得自动恢复撤销版本或替代专门轮换流程。
9. 公共算法位于application层，不依赖Spring；API、回调及仓库内模拟器共用字段、规范化和认证码规则。原测试控制台不可恢复，改由可执行协议示例承担商户按keyId管理密钥的接入验证。
10. 验证覆盖固定向量、完整32字节、错误密钥/篡改/空值/中文、并发首次初始化、刷新token保持keyId/signKey、token到期不影响回调、订单无密钥绑定、轮换前任务重试、轮换后新通知、跨商户keyId拒绝、撤销失败关闭和日志脱敏。真实联调证据仍写入docs/集成测试.md，不能以文档修订替代实现和验证。

用户于2026-10-16确认：本服务为全新开发项目，当前处于开发到测试阶段，直接使用V1.2，不保留旧签名入口、验签旁路或向旧系统代理降级。本阶段不涉及旧业务数据迁移、旧订单换绑、旧回调任务清理或生产流量切换；部署时完成测试基础表准备、Liquibase结构初始化、独立存储主密钥配置及HTTPS入口确认即可开展联调。原测试控制台已删除不可恢复，使用仓库内模拟器及可执行协议示例替代。

## 4. Application 用例编排层

Application 层是业务用例和可靠性协议的中心，不直接依赖具体 Redis/RabbitMQ/MyBatis 类。

| 用例/服务 | 责任 |
| --- | --- |
| `V1CreateRechargeOrderUseCaseService` | 创建订单：协议结果转业务命令、Redis 优先的父商品选品快照解析、请求级单飞刷新、子商品配置一致性修复、依赖可用性 gate、Redis accept、WAIT、MQ confirm、状态回写和异常登记。 |
| `PersistRechargeOrderConsumerService` | 异步落库 Consumer：消费 `PersistTradeOrderMessage`，读取 Redis 快照或 MQ initial snapshot，写 `mc_order` 与 `recharge_order_ext`，提交后回写 Redis。 |
| `RechargePersistMqRepublishService` | Redis pending 补投：扫描 org_index/pending，claim 订单，二次确认 MySQL，再补发 MQ。 |
| `RechargeOutboxWorkerService` | 派单 outbox worker：抢占 `recharge_dispatch_outbox`，执行供应商派单、查单、作废等供应商履约动作。 |
| `RechargeNotifyWorkerService` | 商户回调 worker：抢占 `recharge_notify_task`，按退避规则发送已签名 payload。 |
| `RechargeBalanceDeltaFlushService` | 余额 delta 刷账：扫描 `recharge_balance_delta_outbox`，将 Redis 余额预扣/释放 delta 聚合沉淀到旧表余额。 |
| `RechargeBalanceReconcileService` | 余额对账：比对 MySQL 最终余额、未完成 delta 和 Redis 实时余额，输出差异。 |
| `RechargeCacheRepairService` | 批量缓存修复：持有修复锁后重建 Redis 余额基线；完整选品快照和商品配置的批量扫描、全量重建另列后续任务。V1 请求级单飞刷新和子商品配置修复由下单用例承担。 |

创建订单异常窗口恢复目标：

| 窗口 | 当前恢复设计 | 目标状态 |
| --- | --- | --- |
| Redis accept 成功但 WAIT 未达标 | 尝试 `cancel_unconfirmed_accept.lua` 回滚余额、pending 和索引；回滚失败则关闭 Redis 写入并登记 `recharge_accept_anomaly`。 | 已具备自动核查入口，需持续补 dev/test 证据。 |
| Redis 成功但 MQ confirm 失败 | 订单保留 `PENDING_MQ` 和 pending ZSET，`RechargePersistMqRepublishService` 可补投。 | PEND 系列用例覆盖中。 |
| MQ 到达但 MySQL 写入失败 | Listener 进入 retry queue 或 DLQ；Redis 保留 pending，落库失败写 `PERSIST_FAILED`，后续补偿可重试。 | 代码目标已具备，服务级 MySQL 短时不可用不纳入当前集成测试项。 |
| MySQL 成功但 Redis mark 失败 | `recharge_order_ext` 是事实兜底；pending 补投二次确认 MySQL 后可修复 Redis `DB_PERSISTED`。 | 已纳入 PEND-005/PEND-006 方向。 |
| outbox/notify 网络失败 | `TaskStatus`、retry_count、locked_until、next_retry_time 驱动退避重试或转人工。 | 需按 dev/test 后续用例补证据。 |

## 5. Domain 状态与业务规则

领域枚举是状态值唯一来源，禁止在 controller、adapter、worker 中散落魔法字符串。

| 枚举 | 状态 | 语义 |
| --- | --- | --- |
| `LegacyOrderStatusCode` | `ACCEPTED=2`、`FAILED=6`、`REFUNDED=11`、`SUCCESS=12`、`SUPPLIER_ACCEPTED=13`、`UNKNOWN=0` | 旧 `mc_order.order_status` 和 V1 查单数字状态。 |
| `ValidationStatus` | `PASSED`、`FAILED` | 能形成订单的业务校验结果；协议失败不形成订单。 |
| `PersistStatus` | `PENDING_MQ`、`PERSIST_QUEUED`、`PERSISTING`、`DB_PERSISTED`、`PERSIST_FAILED`、`MANUAL_REQUIRED` | Redis、RabbitMQ、MySQL 持久化技术状态。 |
| `OutboxEventType` | `SUPPLIER_DISPATCH`、`SUPPLIER_QUERY`、`INVALID_ORDER`、`BALANCE_DELTA_FLUSH`、`BALANCE_RELEASE`、`CACHE_REPAIR` | MySQL 事实提交后的可靠动作类型；拆表首期目标只写入/扫描前三类供应商履约事件和 `BALANCE_DELTA_FLUSH`，`BALANCE_RELEASE`、`CACHE_REPAIR` 暂作历史/预留枚举值。 |
| `TaskStatus` | `INIT`、`PROCESSING`、`SUCCESS`、`FAILED`、`MANUAL_REQUIRED` | outbox、notify 等可抢占任务通用状态。 |
| `AcceptAnomalyType` | `WAIT_CANCEL_FAILED`、`LUA_TIMEOUT`、`REDIS_BUSY`、`ACCEPT_STATE_UNKNOWN` | Redis 接单状态未知类型。 |
| `AcceptAnomalyStatus` | `INIT`、`CHECKING`、`RESOLVED_ACCEPTED`、`RESOLVED_NOT_ACCEPTED`、`MANUAL_REQUIRED` | 接单异常核查状态。 |

业务规则：

| 规则 | 说明 |
| --- | --- |
| 直充数量 | 首期直充只允许 `num=1`；非 1 时形成业务失败订单或直接返回参数错误，视协议阶段而定。 |
| 商品类型 | 新链路只处理 `product_type=1` 的直充商品。 |
| 商户身份 | 以后端商户资料为准，请求 `org_code` 不能覆盖 token 解析结果。 |
| 幂等 | 同一 `orgCode + outOrderSn` 命中 Redis idem 或 MySQL 唯一事实时，必须返回重复或原订单结果，不能重复预扣。 |
| 资金一致性 | Redis 预扣成功后必须留下 reservation 和 pending，可通过 MQ 补投或余额释放追平。 |
| 供应商派单 | 只有 `ValidationStatus.PASSED`、`dispatchAllowed=true`、MySQL 已落库的订单才能进入供应商派单 outbox。 |

`/v1/cardapi/order/createRechargeOrder` 的 `product_id` 沿用旧卡管父产品号语义。请求父产品号记为 `productId`，实际子商品号记为 `selectedProductId`。新链路优先按 `orgCode + productId` 读取 Redis 完整选品快照；快照缺失或达到刷新窗口时，再按商户 `org_code + mc_depart_product.parent_id = 请求 product_id` 拉取已授权子商品，沿用旧卡管既定候选顺序选定一项，并用授权行的 `product_id` 读取 `mc_product`。订单金额取该授权行售价，`product_type`、`coupon_type`、面值、商品配置版本、`supplier_channel` 和 `product_name` 均冻结在选中子商品快照中。选定后不得在派单或重试阶段切换其它 sibling，保证受理校验、扣款/退款金额和实际履约目标一致。

商品价格变更采用最长 30 分钟最终生效口径：快照加载后 25 分钟内直接使用 Redis，不访问 MySQL；25 至 30 分钟为软过期窗口，允许继续按旧价成交，同时仅一个请求持有父商品刷新锁并从 MySQL 刷新；达到 30 分钟硬过期后，新单必须等待刷新成功后使用新快照，刷新失败则返回系统繁忙，不能无限期使用旧价。软过期刷新失败后必须重新读取当前时间，只有仍早于原快照 `expire_at` 才能回退旧价；`accept_recharge_order.lua` 还要在原子受理时再次校验父快照 `expire_at > now`，关闭“选品时未过期、接单时已过期”的时间窗。已受理订单继续使用订单内冻结价格，不受后续改价影响。

## 6. Redis 受理与缓存层

### 6.1 Redis Lua 入参与 Key 构造

`accept_recharge_order.lua` 的第 13 个 key 为当前请求父商品 `recharge:{orgCode}:product-selection:{productId}`，必须与余额、订单、商户配置和子商品配置共享 `{orgCode}` hash tag。ARGV 必须与 `AcceptRechargeOrderCommand` 保持一致：`orgCode/appId/outOrderSn/orderId/productId/selectedProductId/account/notifyUrl/nonceStr/num/amount/productName/productValue/productType/couponType/supplierChannel/requestHash/requestHashVersion/requestHashAlg/candidateValidationStatus/candidateFailCode/candidateFailReason/merchantConfigVersion/productConfigVersion/productSelectionFingerprint/productSnapshotAvailable/now/nextRetryTime/pendingTtlMs/nonceTtlMs`。

选品缓存采用逻辑过期而不是每单回源。父商品选品快照至少包含 `product_id/selected_product_id/supplier_channel/product_name/coupon_type/product_type/product_status/sale_price/face_value/base_price/product_version/selection_fingerprint/product_snapshot_available/validation_status/fail_code/fail_reason/loaded_at/refresh_after/expire_at/cache_kind`。`selection_fingerprint` 是对完整 `V1ProductSelection` 的稳定 SHA-256 指纹，覆盖父子商品号、渠道、名称、券类型、类型、售价、面值、底价、商品版本、是否有真实子快照以及候选校验结果；任何字段改变都产生新的父快照代际。旧缓存缺少该字段或字段与反序列化结果不一致时按 cache miss 强制刷新。默认 `refresh_after=25m`、`expire_at=30m`、Redis 物理 TTL 为 `60m`。快照年龄小于 25 分钟时所有请求只读 Redis；25 至 30 分钟时刷新锁持有者同步查询 MySQL 并返回新快照，其它并发请求继续使用旧快照；达到 30 分钟后刷新锁持有者同步回源，其它请求最多等待有限时间读取刷新结果，超时或 MySQL 不可用时返回系统繁忙。刷新锁默认 TTL 为 5 秒，持有者按不超过 TTL 三分之一的周期使用 token 校验 Lua 续租，直至 MySQL 查询和缓存完成结束；续租失败后原 token 不能提交快照。无权限、商品不存在等无可信快照结果使用短 TTL 负缓存，避免无效请求持续击穿数据库。

`V1ProductConfigPreheatPort` 的语义升级为 `refreshIfMissingOrStale`。当完整选品快照从 MySQL 刷新成功时，使用同一 Redis Lua 原子更新父商品选品快照和实际子商品 `status/version/price/product_type`；当父商品选品快照仍在有效期内但子商品配置缺失或字段漂移时，允许仅依据该可信快照修复子商品配置，不访问 MySQL。比较修复只是提前修复子 key，不作为最终一致性边界；比较修复和接单 Lua 都必须校验父快照 `selection_fingerprint` 与命令一致，接单 Lua 还要校验 `product_id/selected_product_id/sale_price/product_version/product_type/product_snapshot_available/cache_kind/expire_at`，再校验实际子商品配置，防止父快照在比较修复后因底价、渠道、名称、候选校验结果或其它任一字段变化而旧请求继续成交。无真实子商品快照的负缓存业务失败跳过子商品配置校验；负缓存写入异常时仍允许基于 MySQL 已确认的失败结果落失败订单，不得预扣余额或派单。请求级刷新不能替代旧卡管商品变更主动同步、批量扫描或全量缓存重建。

`trade.engine.v1.merchant-config-preheat` 提供启动期商户配置白名单预热，只用于补齐 `merchant:config` 这个 Lua 硬门禁 key，默认关闭且不会扫描全量商户。开启后应用启动时按 `org-codes` 去 `V1MerchantProfilePort.findByOrgCode` 读取旧库 `mc_ext_depart` 资料，并写入 `recharge:{orgCode}:merchant:config` 的 `status=ENABLED|DISABLED`、`version=mc_ext_depart.id`。`fail-on-error=true` 时，白名单为空、任一白名单商户缺失、版本为空或 Redis 写入失败都应阻止启动，避免 Nacos 已打开 Redis 写入但基线缺失导致首单在 Lua 中持续返回 `MERCHANT_CONFIG_STALE`；联调排障期可临时设为 `false` 记录错误后继续启动。该启动预热不替代后续批量缓存修复、主动同步或余额基线重建。

只有 `trade.engine.environment=local` 且 `trade.engine.redis.write-enabled=false` 的轻量自测允许在 Redis 选品缓存端口缺失时直接查询 MySQL；该模式不会进入 Redis Lua 接单写路径。local 一旦显式开启 Redis 写入，或运行在 dev/test/prod，必须保留缓存优先包装器并 fail closed 返回系统繁忙，避免父商品快照缺失导致 Lua 全量拒绝，或部署配置错误在秒杀流量下静默击穿共享数据库。

商户授权售价来自 `mc_depart_product.price`，不保证修改售价时会同步递增 `mc_product.version`。因此缓存刷新不能只依赖商品版本不一致，必须在逻辑刷新窗口回源后重写完整选品快照，并逐字段同步实际子商品的 `status/version/price/product_type`；`version` 是 Lua 门禁字段之一，但不是售价变更的唯一失效信号。

### 6.3 Redis HA Guard 与状态未知窗口

Redis 写入前必须先通过 HA Guard 和 MQ breaker gate。如果 Redis 不可用、修复锁存在、WAIT 未达标且无法确认回滚，则新写入必须 fail closed，避免扩大资金不确定窗口。

`cancel_unconfirmed_accept.lua` 负责 WAIT 失败后的原子回滚：恢复余额、清理订单/幂等/reservation/pending/org_index 并写事件。若 cancel 失败，`V1CreateRechargeOrderUseCaseService` 必须登记 `AcceptAnomalyRecord`，并返回“稍后查单”的保守语义。

## 7. RabbitMQ 持久化消息层

RabbitMQ 只承载 Redis 到 MySQL 的可靠落库消息，不承载供应商履约 outbox。

生产基线为 RabbitMQ 4.3.x + Erlang/OTP 27.x，同一集群内必须固定同一
RabbitMQ patch、同一 Erlang/OTP patch 和同一 Docker 镜像 digest。当前三机部署通过
Docker Compose 在 `pro143/pro197/pro120` 上运行 trade-engine 专用 RabbitMQ 集群，
使用独立端口和独立 vhost；pro120 若保留旧 RabbitMQ 4.1.x，则该旧 broker 不参与本项目集群。
Compose 中 RabbitMQ 服务必须保留 `rmq-pro143`、`rmq-pro197`、`rmq-pro120` 的
`extra_hosts` 映射，避免容器重建后节点名解析不完整。

| 配置项 | 默认字段 | 说明 |
| --- | --- | --- |
| Exchange | `trade.engine.mq.persist-exchange` | 持久化主 exchange。 |
| Routing key | `trade.engine.mq.persist-routing-key` | 主消息路由键。 |
| Queue | `trade.engine.mq.persist-queue` | `RabbitPersistRechargeOrderMessageListener` 订阅队列，dev/test 应使用 Quorum Queue。 |
| Retry exchange/queue/routing | `persist-retry-*` | Consumer 失败退避，不立即 requeue。 |
| DLX/DLQ | `persist-dead-letter-*` | 毒消息或重试耗尽后的人工排查入口。 |
| Confirm | `publish-confirm-timeout-ms`、`publish-retry-times` | Redis 成功后必须等待 publisher confirm；失败保留 pending 补投窗口。 |
| Batch consumer | `persist-batch-enabled`、`persist-batch-size`、`persist-batch-receive-timeout-ms`、`persist-batch-poll-timeout-ms` | 异步落库 Consumer 批消费灰度开关、业务批大小、攒批等待上限（`batchReceiveTimeout`）和单次拉取等待（`receiveTimeout`）；默认关闭，开启后由 bootstrap 自动配置同步默认 Spring Rabbit simple listener factory，并校验 JDBC `rewriteBatchedStatements=true`。 |
| Breaker | `trade.engine.mq.breaker.*` | MQ 发布不可用时在 Redis accept 前 fail closed。 |

`PersistTradeOrderMessage` payload 字段：

| 字段 | 来源 | 约束 |
| --- | --- | --- |
| `messageId` | Producer 生成，形如稳定前缀加随机后缀 | Confirm 关联 ID；补投时使用补投幂等号。 |
| `orgCode`、`orderId`、`outOrderSn` | Redis accept 结果和命令 | Consumer 定位订单。 |
| `requestHash` | request hash | MySQL 扩展表幂等核查。 |
| `orderVersion` | Redis 订单版本 | Consumer mark 与二次确认。 |
| `initialOrderSnapshot` | Producer 构造 | 必须包含写 `mc_order` 和 `recharge_order_ext` 的最小字段。 |

RabbitMQ 连接可观测要求：应用启动后 RabbitMQ 管理端若在目标 vhost 看不到连接，不能只判断“队列为空”。应同时检查应用日志、`RabbitPersistRechargeOrderMessageListener` Bean、publisher confirm 配置、vhost/用户名/权限、Nacos `spring.rabbitmq.*` 和 `trade.engine.mq.*`。没有成功建立连接时，创建订单新链路应在 MQ gate 前拒绝或保留可恢复 pending，而不是假定 broker 可用。

批消费配置分为两层：Spring Rabbit 容器层负责把 broker 投递聚合成 `List<Message>`，业务层负责决定是否注册批 listener。`trade.engine.mq.persist-batch-enabled=false` 时必须只注册单条 listener，保持一消息一事务的回退路径；开启批模式时由 `TradeEngineRabbitListenerAutoConfiguration` 注册批 listener，并对默认 `SimpleRabbitListenerContainerFactory` 显式设置 `consumerBatchEnabled=true`、`batchSize=persist-batch-size`、`receiveTimeout=persist-batch-poll-timeout-ms`、`batchReceiveTimeout=persist-batch-receive-timeout-ms`。Spring AMQP 3.1.x 中二者语义不同：`receiveTimeout` 是每一轮 `nextMessage` 的阻塞上限，`batchReceiveTimeout` 是从本批首条消息起、在两次 receive 之间检查的攒批上限；不要把 poll timeout 盲目放大到秒级，否则低流量 partial batch 也会被拖长。批开关打开但 `RechargeOrderBatchPersistencePort` 缺失，或 JDBC URL 缺少 `rewriteBatchedStatements=true` 时必须启动失败，不能等消费时才整批 retry。部署侧自定义或替换 `rabbitListenerContainerFactory` 时，必须在自定义 factory 中保持同样批模式、批大小和等待时间设置。阶段 1 默认 `persist-batch-size=10`、`persist-batch-receive-timeout-ms=200`、`persist-batch-poll-timeout-ms=200`，`prefetch` 必须大于等于 batch size，基础 `application.yml` 保持 `prefetch=50`、`max-concurrency=16`；灰度初期若想保守控压，可在 Nacos 将 `prefetch/max-concurrency` 调为 `20/8`，不要同时放大批大小和消费者并发。

### 8.3 异步落库 Consumer

`PersistRechargeOrderConsumerService` 的事务边界：

1. 消费 `PersistTradeOrderMessage`。
2. 优先通过 Redis 读取最新 `PersistOrderSnapshot`。
3. Redis 快照缺失或不可读时，使用 `initialOrderSnapshot` 构造 `PersistOrderSnapshot`，`persist_source=MQ_SNAPSHOT_FALLBACK`。
4. `CONFIG_CHANGED` 等发生在 Lua 写 Redis 订单前的失败也要持久化到 MySQL；Producer 必须在 `initialOrderSnapshot` 标记 `redis_order_written=false`，Consumer 只使用 MQ 快照写库。
5. 默认在同一 MySQL 事务内写 `mc_order`、`recharge_order_ext`，并按需要生成 `recharge_dispatch_outbox` 和 `recharge_balance_delta_outbox`；不写旧 `recharge_outbox`，不设计双写回滚。开启 `trade.engine.persist.outbox-async-enabled` 后，批路径改为两段事务：事实事务只写 `mc_order`、`recharge_order_ext` 与必要的 `mc_depart_record`，两张 outbox 表由独立连接池的异步 writer 在事实事务提交后幂等写入，见本节「Outbox 异步落库模式」。
6. 对已写 Redis 订单，事务提交后调用 Redis mark 脚本推进 `DB_PERSISTED`，清理 pending 和 org_index。
7. 对 `redis_order_written=false` 的 mysql-only 失败事实，事务提交后不调用 Redis mark 脚本，因为 Redis 中没有对应订单、pending 或幂等快照。
8. Redis mark 失败不回滚 MySQL 事实，由 pending 二次确认修复 Redis。

Consumer 不得吞异常。可重试异常应进入 RabbitMQ retry/DLQ 或 Redis pending 补偿；不可恢复的数据缺失应记录上下文并转人工。

批消费模式是该单条协议的灰度优化，不改变订单事实集合。`PersistRechargeOrderConsumerService` 保留 `persist(message)` 单条入口，并新增 `persistBatch(messages)` 批入口；批入口先逐条选择 Redis/MQ 快照，再调用独立的 `RechargeOrderBatchPersistencePort`。批写 adapter 必须独立于 `MybatisRechargeOrderPersistenceAdapter` 实现，二者只共享 `RechargeOrderPersistenceRowConverter` 字段映射组件，避免 MyBatis `ExecutorType.BATCH` 的延迟返回值影响单条路径中基于 `orderInserted == 1` 的控制流。

阶段 1 批模式约束：

1. **MySQL 批事务整批原子**：任一订单写库异常时整批 rollback；listener 不对原批次做成功 ack，而是进入 Rabbit retry/DLQ 分流。
2. **Rabbit retry/DLQ 按单条分流**：同批消息按各自 `x-retry-count` 判定；耗尽的 `basicReject` 进 DLQ，未耗尽的 publish 到 retry queue。毒消息不得拖死同批新鲜消息。
3. 批事务成功后，对 Redis-backed 订单逐条执行 `markDbPersisted`；任一 Redis mark 失败不回滚 MySQL，整批仍可 ack，由 pending 二次确认修复 Redis。
4. `redis_order_written=false` 的 mysql-only 失败事实可混入批内，写 MySQL 后仍跳过 Redis mark。
5. Rabbit 主队列可能存在已由其它副本落库的重复消息。批入口在构造批事务前，必须批量查询 `recharge_order_ext`，以 `order_id + org_code + out_order_sn + persisted_version` 判断 MySQL 是否已覆盖本次选中的快照版本。已覆盖的消息不进入 `RechargeOrderBatchPersistencePort.persistBatch`，但 Redis-backed 消息仍执行幂等 `markDbPersisted`，用于修复 Redis `DB_PERSISTED`、pending 和 org_index；这些消息随原批次 ack，并以 `skipped_already_persisted` 指标计数。
6. 批写 adapter 内部按 `orgCode + outOrderSn + orderId` 稳定排序，并按表分组固定 `mc_order -> recharge_order_ext -> mc_depart_record -> recharge_dispatch_outbox -> recharge_balance_delta_outbox` 写表顺序，降低并发批次锁等待和死锁概率。
7. 批写 adapter 不得依赖 `mc_order.insertIfAbsent` 的即时返回值决定是否写 `mc_depart_record`；资金流水必须直接调用幂等 `insertIfAbsent`，由 `uk_mc_depart_record_trade_engine_key` 唯一键兜底。
8. 批写 adapter 必须调用显式 multi-row mapper 方法：`insertOrderBatchIfAbsent`、`insertExtBatchOrUpdatePersistState`、`insertDepartRecordBatchIfAbsent`、`insertDispatchOutboxBatchIfAbsent`、`insertBalanceDeltaBatchIfAbsent`。`ExecutorType.BATCH + 单条 mapper 循环` 仅可作为单条路径兼容实现，不作为批消费正式写库路径。
9. 阶段 1 不引入 per-order MySQL savepoint 或批内部分提交。retry publish 中途失败时，已 confirm 进入 retry queue 的原消息必须 ack，未发布成功的原消息再 requeue，避免 retry 副本与主队列 requeue 双份并存。
10. 阶段 1 坏 JSON 仍导致整批进入 retry/DLQ 分流（设计选择）；日志必须带失败下标、失败 deliveryTag、body 长度和 SHA-256 摘要，禁止直接打印完整 body。
11. 数据源 URL 必须启用 `rewriteBatchedStatements=true`；批开关打开时启动期校验，缺失则 fail-fast。
12. 批观测指标：`trade.engine.persist.batch.size`、`trade.engine.persist.batch.mysql.duration`、`trade.engine.persist.batch.mysql.phase.duration{phase}`、`trade.engine.persist.batch.orders.total{result}`。`phase` 仅允许 `mc_order`、`recharge_order_ext`、`mc_depart_record`、`recharge_dispatch_outbox`、`recharge_balance_delta_outbox`、`commit` 这类固定低基数取值；旧 `recharge_outbox` 只作历史压测对比背景；`result` 至少包含 `success`、`failed`、`skipped_already_persisted` 三类低基数取值。

#### Outbox 异步落库模式（`trade.engine.persist.outbox-async-enabled`）

动机与适用前提见 `docs/superpowers/specs/2026-07-24-persist-outbox-async-design.md`：timer 热路径对 `recharge_dispatch_outbox` 的 claim UPDATE 与批事务内 outbox INSERT 在唯一键/二级索引页上争用，timer ON 时批事务秒级、落库吞吐随履约并行度放大而塌陷。开启本模式后，批路径事务边界从「5 表同一事务」改为两段，timer 可保持常开。

两段事务边界：

1. **事实事务**（`persistBatchFactsOnly`，`@Transactional`）：只写 `mc_order`、`recharge_order_ext` 与必要的 `mc_depart_record`，原子提交后行锁即释放。二次确认已落库的消息仍被跳过（降本优化只作用于本段）。
2. **Outbox 异步写**（`RechargePersistOutboxAsyncWriter.writeBatch`）：事实事务提交后同 consumer 线程同步调用，在 **独立 Hikari 连接池 + 独立事务管理器** 的短事务内整批幂等写入 `recharge_dispatch_outbox`、`recharge_balance_delta_outbox`。writer 入参为 **本批全部 selected aggregates，不随二次确认跳过收缩**：事实事务提交后 `persist_status=DB_PERSISTED` 已成立，若跳过已落库订单，「事实已提交、outbox 未写」崩溃窗口的重投将永久缺失 outbox 行、派单永不发生；重放 ODKU 对已存在 `event_id` 是无害 no-op。
3. Outbox 写成功后才调用 `scheduleDispatchAfterMysqlCommit`（对全部 selected 中满足 `dispatchOutboxRequired() && balanceReserved()` 的聚合，timer 同 eventId 替换幂等），再执行 `markDbPersisted` 与 ack。

失败语义与不变量：

- 任一阶段失败（事实事务或 outbox 写）均不 ack、不 `markDbPersisted`，整批走现有 Rabbit retry/DLQ 与 `markPersistFailed` 保留 Redis pending；重消费时事实表 ODKU 跳过、outbox 无条件补写。
- **ack 必在 outbox 写成功之后**，因此「Redis pending 已清的订单必有 outbox 行」。
- 崩溃恢复不新增机制：Redis pending + MQ 重投 + `event_id` 唯一键 ODKU 覆盖全部窗口；「outbox 已写、timer 未调度」窗口由低频 recovery scan 兜底，重投时热路径重 schedule 提前覆盖。

配置键（`trade.engine.persist.*`）：

| 配置键 | 默认 | 说明 |
| --- | --- | --- |
| `outbox-async-enabled` | `false` | 灰度开关；`false` 时批路径保持 5 表同一事务（回滚兜底），单条 `persist()` 路径不受本开关影响。 |
| `outbox-writer-hikari-max` | `8` | writer 独立 Hikari 上限；必须与 persist consumer 主池隔离，启动期校验 >0 且与主 DataSource 非同实例。writer 池的连接超时/生命周期调优（如 `connection-timeout`、`max-lifetime`）继承主池 `spring.datasource.hikari.*`，池大小独立。 |
| `outbox-writer-batch-enabled` | `true` | writer 整批 multi-row ODKU；`false` 退化为逐条写入，仅排障使用。 |

观测：两个 outbox phase 标签不变，但在本模式下度量的是 writer 独立事务耗时；新增 `trade.engine.persist.outbox.writer.duration` 记录 writer 端到端耗时；writer 连接池水位读标准 Hikari 指标 `hikaricp.connections.*{pool="persist-outbox-writer"}`。事实事务与 writer 耗时背离或 writer 池持续 pending 时，按 spec「风险与回滚」评估二期 fire-and-forget。

## 9. Outbox、供应商派单、作废与商户回调

### 9.1 派单 Outbox

`recharge_dispatch_outbox` 承载 MySQL 事实之后的供应商履约可靠动作，首期只写入并扫描 `SUPPLIER_DISPATCH`、`SUPPLIER_QUERY`、`INVALID_ORDER`。`BALANCE_DELTA_FLUSH` 不再写入派单表，而是进入「9.2 余额 Delta 刷账 Outbox」；失败/作废后的余额释放不使用 `BALANCE_RELEASE` outbox 事件，而是写入 `recharge_balance_delta_outbox(delta_type=RELEASE)`。`CACHE_REPAIR` 继续由 `RechargeCacheRepairService` 独立链路处理。旧 `recharge_outbox` 是未上线旧实现；新代码的 mapper、adapter、worker 注释必须引用本节和「9.2」，不得继续把两种生命周期混在一个“通用 outbox”概念里。

由于新交易引擎与旧卡管系统共享 `mc_order` 等旧表，派单 outbox 自动任务必须先确认事件关联订单属于新系统处理范围。归属边界以新系统独占维护的 `recharge_order_ext` 为准：扫描和抢占 `recharge_dispatch_outbox` 时，必须同时匹配 `order_id + org_code + out_order_sn`，且 `recharge_order_ext.persist_status = DB_PERSISTED`。不满足该边界的事件不得被扫描、抢占、派单、作废或写回共享表，避免处理旧卡管订单或异常历史数据。

派单 outbox 任务先使用状态、`next_retry_time` 和租约条件筛选当前具备执行资格的事件，再在每个分片的可执行集合内按 `created_at ASC, id ASC` 处理，保证先生成的事件优先获得处理机会。`next_retry_time` 只作为执行资格条件，不作为到期事件的主排序字段。调度侧将 `SUPPLIER_DISPATCH` 与 `SUPPLIER_QUERY`/`INVALID_ORDER` 拆到独立 XXL Handler，避免查单 due 与派单争抢同一 `limit`；兼容入口 `rechargeOutboxPublishJob` 默认仅扫 `SUPPLIER_DISPATCH`。

进程内 `RechargeDispatchTimerPort` 是派单和查单的低延迟热路径，但由 `trade.engine.fulfillment.timer-enabled` 灰度控制且默认关闭：订单 MySQL 事务写入 `dispatch-{orderId}` 后，只有开关显式打开才由 Consumer 按 `trade.engine.fulfillment.dispatch-initial-delay-seconds`（默认 1 秒）延迟调度指定 `event_id`；派单返回处理中或不可确认后写入 `supplier-query-{orderId}`，Worker 按 2 秒延迟调度查单事件；后续查单处理中/不可确认失败按 4、6、8、16、32 秒继续调度同一事件。timer 基于 `ScheduledThreadPoolExecutor` 做到点唤醒，只保存内存 future，不保存业务事实；真正的 DB/供应商 HTTP 状态机提交到独立有界 worker executor，避免慢供应商占住调度线程。`recharge_dispatch_outbox` 仍是唯一持久任务事实，也是进程重启、中断恢复、多节点重复触发和 timer 调度失败后的恢复来源；低频 XXL-Job 扫描继续按 `next_retry_time` 兜底补漏。timer 本地待触发任务有 `timer-max-pending-tasks` 上限，并通过 `trade.engine.dispatch.timer.pending`、`trade.engine.dispatch.timer.max.pending`、`trade.engine.dispatch.timer.rejected.total`、`trade.engine.dispatch.timer.worker.rejected.total` 暴露当前积压、上限、热唤醒拒绝和 worker 执行拒绝累计，压测时用于判断热路径唤醒是否成为瓶颈。

Worker 单批流程为：按 `eventTypes` overfetch（`limit * outbox-scan-overfetch-factor`）→ 账号去重与 Redis 频控预检得到 `deferred`（不 claim、不计 failed）→ 串行 CAS claim → 线程池按 `outbox-parallelism`（默认 8）并行履约；同账号履约串行。观测同时暴露 `since_created` 与 `since_due` 年龄，调度排序仍只用 `created_at`。

派单 outbox 执行规则：

| 规则 | 说明 |
| --- | --- |
| 抢占 | 通过 `status + next_retry_time + locked_until + version` CAS 抢占，`locked_by` 写 workerId。 |
| 退避 | 失败写 `last_error`，递增 `retry_count`，按配置推迟 `next_retry_time`。 |
| 上限 | `retry_count >= max_retry_count` 转 `MANUAL_REQUIRED`。 |
| 幂等 | 供应商流水、查单事件、作废事件和余额释放 delta 必须有业务幂等键。 |
| 分片 | `shard_key` 固定使用 `event_id`，避免不同 job 分片语义冲突。 |
| 归属边界 | `recharge_order_ext` 中必须存在同 `order_id + org_code + out_order_sn` 且 `persist_status=DB_PERSISTED` 的记录。 |
| 处理顺序 | 已具备执行资格的事件按 `created_at ASC, id ASC` 稳定扫描，先生成先处理。 |
| Job 隔离 | `rechargeSupplierDispatchJob` 仅 DISPATCH；`rechargeSupplierQueryJob` 处理 QUERY+INVALID；旧 PublishJob 默认仅 DISPATCH。 |
| 公平与并行 | 批内账号去重 + 频控预检记 `deferred`；claim 后按 `trade.engine.fulfillment.outbox-parallelism` 并行执行。 |
| timer 热路径 | timer 只调度指定 `event_id` 并把单事件 worker 提交到有界执行池；多节点互斥、重启恢复和人工补偿仍由 outbox CAS 与扫描兜底保证。 |

供应商派单只允许在 `dispatchAllowed=true`、`balanceReserved=true`、`persist_status=DB_PERSISTED` 后执行。供应商 HTTP 开关由 `trade.engine.supplier.http-enabled` 控制，渠道 URL 和超时只来自 Nacos 或环境变量，不写入日志。

名创 MINISO 在新交易引擎中仍按“直充无卡密”处理：履约目标是客户手机号对应的名创账户。客户最终获得的是该账户内的卡号卡密权益，但交易引擎不按本地卡券/卡密出库建模，也不把 MINISO 供应商结果转成卡券库存履约产物。

供应商派单返回 HTTP 5xx、超时、连接异常或其他不可确认结果时，Worker 不释放预扣、不生成失败回调、不盲目重派；它会把订单推进到 `SUPPLIER_ACCEPTED`/旧状态 `13`，补写 `supplier-query-{orderId}` 并关闭原 `SUPPLIER_DISPATCH`。DISPATCH 恢复扫描时如果订单已是 `SUPPLIER_ACCEPTED`，或发现同订单最近存在 `mc_order_supplier_flow` 流水，说明请求已经可能发出，也必须按同一规则先查单确认终态。

供应商返回处理中时，Worker 先把订单推进到 `SUPPLIER_ACCEPTED`/旧状态 `13`，再按稳定事件号
`supplier-query-{orderId}` 幂等写入 `recharge_dispatch_outbox(SUPPLIER_QUERY)` 并结束当前派单事件。查单事件由同一张派单 outbox
抢占、timer 热唤醒和分片任务执行：返回处理中、HTTP 5xx、超时、连接异常或查单地址未配置时只退避查单事件，不退款、不生成终态回调；
明确成功/失败时分别复用成功回调或失败释放预扣、`recharge_balance_delta_outbox` 和失败回调副作用，副作用完成后才标记查单事件成功。
如果订单已被其他重试推进终态，查单 Worker 只关闭重复事件；如果失败终态的预扣释放尚未完成，则继续使用该事件补偿释放。

### 9.2 余额 Delta 刷账 Outbox

`recharge_balance_delta_outbox` 只承载 `BALANCE_DELTA_FLUSH`，用于把 Redis 实时余额预扣/释放产生的 delta 沉淀到旧表 `mc_ext_depart.balance`。该表不保存通用 `payload`、`event_type`、`shard_key`，而使用结构化字段 `delta_type`、`delta_amount`、`org_code`、`order_id`、`out_order_sn`，降低订单落库事务中的 JSON 写入和通用 outbox 索引维护成本。

余额 delta 写入规则：

| 场景 | 事件 ID | delta_type | delta_amount |
| --- | --- | --- | --- |
| Redis 预扣成功后订单落库 | `balance-flush-{orderId}` | `PRE_DEDUCT` | 负数，金额单位分 |
| 供应商失败或作废释放预扣 | `balance-flush-release-{orderId}` | `RELEASE` | 正数，金额单位分 |

`RechargeBalanceDeltaFlushService` 扫描 `recharge_balance_delta_outbox` 时，先按 `status + next_retry_time` 找到到期事件，并按 `status + locked_until` 恢复租约过期的 `PROCESSING` 事件；逐条 CAS 抢占为 `PROCESSING` 后，再按 `org_code` 聚合本轮抢占成功的 `delta_amount`。写库阶段必须在同一 MySQL 事务中锁定 `mc_ext_depart` 商户余额行，执行 `balance = balance + sum(delta_amount)`，并把参与聚合的 delta 标记为 `SUCCESS`。任一 `markSuccess` CAS miss 必须回滚整个商户组事务，不能留下余额已更新但 delta 未成功的状态。同一商户多个分片并发时，最终仍通过商户余额行锁串行。商户组事务失败后，系统在事务外逐条标记 `FAILED` 或 `MANUAL_REQUIRED`；若失败标记也因数据库抖动失败，事件保留在 `PROCESSING`，由租约过期后的下轮 reclaim 继续处理。

余额对账只汇总 `recharge_balance_delta_outbox` 中未 `SUCCESS` 的 delta，不再扫描派单表或旧 `recharge_outbox`。dev/test 历史压测数据不做迁移，下一轮压测前按测试数据清理。

### 9.3 作废设计

作废请求按 `orgCode + outOrderSn` 定位订单。订单未落 MySQL 或 `persist_status != DB_PERSISTED` 时返回处理中或保守结果，不能直接调用供应商。已经发券成功的订单通过 `recharge_dispatch_outbox(INVALID_ORDER)` 进入供应商作废链路（终态与查询规则见9.6节），失败后按派单 outbox 退避重试。

MINISO接入核销回调后的附加合同见9.5节：已持久接收核销事件即阻止自动作废退款，即使事件仍在等待凭据或商户密钥。作废前、远端成功后本地终态及失败终态的余额释放补偿均按同订单锁复核，矛盾转人工；不能由既有状态3优先合并覆盖核销证据。

### 9.4 回调设计

`recharge_notify_task` 保存已签名 payload。`RechargeNotifyWorkerService` 重试时不重新计算业务签名，只负责抢占、HTTP 发送、状态推进和退避。非 200、网络错误、超时都进入重试；达到上限转 `MANUAL_REQUIRED`。
下单请求的 `notify_url` 允许为空；为空时订单仍按正常履约推进，但终态和核销状态变化不生成 `recharge_notify_task`，避免对空地址或占位地址发起 HTTP 回调。非空 `notify_url` 仍必须是 http/https URL。
若历史脏数据或旧版本防御缺口写入了空 `notify_url` 任务：`RechargeNotifyWorkerService` 在每轮扫描前会批量将其标记为 `SUCCESS`，且 `selectDueTasks` 不再扫到空 URL；运维也可执行 `scripts/cleanup-blank-notify-tasks.sql` 一次性清理。
若历史脏数据或防御缺口写入了空 `notify_url` 任务，`RechargeNotifyWorkerService` 在每轮扫描前会批量将其标记为 `SUCCESS`，且到期扫描查询排除空 URL；运维亦可执行 `scripts/cleanup-blank-notify-tasks.sql` 一次性清理。

回调 payload 不记录密钥。日志只允许记录 taskId、orgCode、orderId、outOrderSn、bizStatus、HTTP 状态和错误摘要。

### 9.7 通知重试的实际规则（2026-10-19核对）

订单结果、作废及名创核销通知复用同一Worker及HTTP发送器。首次任务为INIT、retry_count=0、next_retry_time=创建时刻，事务提交后由下一次`rechargeNotifyRetryJob`扫描发送，不在创建事务内同步发HTTP。只在HTTP 2xx且响应JSON的业务code为200时确认SUCCESS，数值200与字符串200均兼容；其他业务码、非2xx、空响应、网络/解析异常均失败。发送前签名、可信身份或密钥撤销检查失败同样消耗失败次数，但不实际发HTTP。

默认`trade.engine.notify.retry-backoff-seconds=30`，失败完成写库时设置下次到期时间为当前时间加30秒，为固定退避，不是指数/阶梯。`claim-lease-seconds=60`、`http-timeout-ms=3000`；默认共享HTTP客户端连接超时3秒。XXL调度周期在调度中心配置，代码不硬编码：部署手册建议15秒扫描，联调准备报告建议5秒，均不能作为已核验的线上配置。实际发送时间还受扫描周期、串行批处理、积压和数据库耗时影响，30秒只表示失败后的最早到期等待。

订单成功/失败及作废任务max_retry_count为代码常量10，名创核销任务为代码常量100。retry_count仅在失败持久化时加1，包含首次失败；正常轨迹下分别是首发加9次、首发加99次失败处理，不是额外再重试10/100次。最后一次失败先写FAILED及下次时间，到期后再次抢占才转MANUAL_REQUIRED，期间不再发HTTP。SUCCESS/MANUAL_REQUIRED不会进入普通到期扫描。失败次数不是严格HTTP总次数审计：宕机租约恢复不加计数，已收到成功但本地未落SUCCESS时会重复发送；接收方必须按业务事实幂等。

重试保持原payload、URL、timestamp、nonce、keyId及sign；密钥撤销后不自动重签。空notify_url正常不建任务；历史空地址任务的SUCCESS是清理结果，不代表银行确认接收。人工run-once只触发普通到期扫描，不绕过到期时间、不恢复MANUAL_REQUIRED、不清零或重签。目前未实现专门的人工重建补发接口。

调度参数应显式填写`limit=100,workerId=xxl-notify-retry`：通知批内串行，mapper单批最多1000，XXL缺省limit=0会被钳制为1。当前claim有状态/次数CAS，但结果回写仅按task_id，租约过期时存在旧Worker覆盖新结果的窗口；本轮记录该问题，不将计数上限承诺为严格网络发送上限，也不改变通知重试策略。失败写库异常可能中断本批，依赖后续调度及租约恢复。详细答复和源文件索引见本轮接口问题修订记录。

Task10重入旁路同样受保护：旧`order`异常收尾不得将已交给MINISO的尝试改成FAILED；限频等待只在主库锁内确认仍为未尝试WAIT时写入，不能用陈旧对象覆盖13/18或冻结标记。`retryOrder`对已接管MINISO仅按原单查证，不把原流水置失败或换渠道。一键补发对MINISO13/18或带本协议冻结标记的订单直接拒绝，提示按原单查询或人工核实，不复制新订单号、不改原单备注；其他渠道的补发规则不变。

状态同步的386排除按可信主单渠道识别，不猜测旧批次表的channel/state_type默认值：主单渠道属于MINISO且批次为MINISO/type3的直充券走上述guard事务；主单明确为stock的人工库存批次保留原状态同步，仅更新该stock主单关联记录并排除新引擎归属，不能恢复按券码无渠道限制的批量写。未知/多归属不降级成直充或人工；人工记录的channel/state_type为空或历史默认填值均不能改变其来源。`ownCartOrder`的发券/出库/库存写入仍不改动。

旧退款必须在候选查询及主单锁内最终写前排除**任意存在recharge_order_ext**的订单，不按渠道、扩展状态或预扣标记缩小排除范围；单笔/V2/任务等可达入口同样适用，保护不随桥接开关关闭。旧MINISO作废的供应商adapter不再自行改批次；前置短事务→锁外远端→最终短事务复核证据及条件更新批次/主单。旧退款在单笔事务内提交余额、退款流水、退款状态，异常整笔回滚，不能吞流水异常后提交余额；旧端不套用新端12/CANCELLED模型。

新端MINISO首次资金许可由终态及持久释放授权同事务提交，所有派单FAILED、查单FAILED、作废完成及补偿共用此边界，不能依赖REQUIRES_NEW检查返回后已释放的锁。核销接收先提交则禁止授权；授权先提交则迟到核销可靠保存转人工，不自动撤销授权。之后锁外幂等释放Redis，再同事务插入/核对稳定RELEASE delta及置balance_reserved=0。已有授权恢复不重新门禁，避免“Redis已释放、delta未写时宕机，再被迟到核销阻断”的账务缺口；此完成标记不等于delta已刷账。**2026-10-20用户已确认：授权一旦提交，即使Redis尚未执行，迟到核销也只转人工，不自动撤销授权，继续恢复该授权的资金步骤**。

无券码时无法关联未知inbox；**用户已接受：可能已发券但本地没有券码或履约凭据的MINISO先按原订单号查单补证据，仍无法确认则转人工，期间不自动退款**。查单耗尽或转人工不等于允许退款，不把缺凭据当未发券。可证明未发券的具体失败码及证据属于实施前协议核验项，未核验不作放行依据。历史CANCELLED/FAILED或已释放但无授权字段不自动回填授权。完整候选方案、断点及测试矩阵见规格第2、6、8、11节；本轮未执行业务测试或共享DDL。

发布仅限获授权的开发测试范围，先核验唯一URL/HTTPS及接入身份、供应商重试、全部新旧资金/凭据写入者升级，再受控切换BRIDGE；不允许旧LEGACY路径与新协议混写。回滚保留证据、guard及未完成授权；退回不识别新合同的JAR前须停相关资金写入。保护不受接收/路由/处理开关影响，缺表/异常失败关闭。真实MySQL并发、崩溃恢复和资金隔离验收按规格执行并记录《集成测试.md》，不能将历史H2通过当成本次InnoDB并发证据。

## 10. XXL-Job 与 dev/test 人工任务入口

### 10.1 XXL-Job Handler 契约

`cardshop-trade-engine-job` 提供 framework-free `runOnce(...)` 门面，真实 XXL-Job handler 和 dev/test HTTP 人工入口都只负责解析参数并委托门面。

| Job | 门面 | 当前用途 |
| --- | --- | --- |
| `rechargePersistMqRepublishJob` | `RechargePersistMqRepublishJob.runOnce` | Redis pending MQ 补投。 |
| `rechargeOutboxPublishJob` | `RechargeOutboxPublishJob.runOnce` | 兼容入口：默认仅推进 `SUPPLIER_DISPATCH`；可用 param `eventTypes=ALL` 恢复混扫。 |
| `rechargeSupplierDispatchJob` | `RechargeSupplierDispatchJob.runOnce` | 仅 `SUPPLIER_DISPATCH`；支持 `parallelism=`。 |
| `rechargeSupplierQueryJob` | `RechargeSupplierQueryJob.runOnce` | `SUPPLIER_QUERY` + `INVALID_ORDER`；支持 `parallelism=`。 |
| `rechargeNotifyRetryJob` | `RechargeNotifyWorkerService.processDue` | 商户回调任务退避重试。 |
| `rechargeBalanceDeltaFlushJob` | `RechargeBalanceDeltaFlushJob.runOnce` | `BALANCE_DELTA_FLUSH` 刷旧表余额。 |
| `rechargeBalanceReconcileJob` | `RechargeBalanceReconcileJob.runOnce` | 余额对账。 |
| `rechargeCacheRepairJob` | `RechargeCacheRepairJob.runOnce` | Redis 余额基线修复。 |
| `acceptAnomalyAutoCheckJob` | `AcceptAnomalyAutoCheckJob.runOnce` | Redis 接单异常自动核查。 |

真实 handler 统一由 bootstrap 层注册；handler 只解析 XXL-Job 分片、`limit`、`batchId`、`workerId` 等调度参数，并在触发时晚绑定 application/job facade。这样可以避免 dev/test 中 job facade 或 MyBatis 端口晚于 executor 扫描完成而造成 `handler not found` 或 `job is not available`。

`RechargeBalanceDeltaFlushJob`、`RechargeBalanceReconcileJob`、`RechargeCacheRepairJob` 在 dev/test 人工触发时必须晚绑定真实端口。若 RedisTemplate 或 Mapper 装配缺失，应失败并暴露错误，不能返回空扫描掩盖装配问题。

## 12. 观测、日志与告警

日志必须覆盖关键业务定位字段，但不能输出密钥、token、原始敏感 payload 或完整手机号/账号等敏感内容。

| 场景 | 必备上下文 |
| --- | --- |
| V1 路由 | path、target、reason、appId、orgCode。 |
| 创建订单 | appId、orgCode、outOrderSn、orderId、requestHash、Redis accept code、WAIT 结果、MQ confirm 结果。 |
| Redis Lua 慢执行 | Lua 名称、orgCode、outOrderSn/orderId、耗时、key 类型，不输出敏感值。 |
| V1 商品选品缓存 | cache result、快照年龄、刷新 result/耗时、MySQL 回源次数；商品号和商户号不得作为 Micrometer label。 |
| V1 商户资料本地缓存 | `hit/miss/negative` 低基数 result；lookup 类型仅允许 `app_org`/`org`；禁止 appId、orgCode、aesKey 进入 label。 |
| V1 下单同步子阶段 | `trade.engine.v1.create.stage.duration` 的 stage 仅允许 `prepare`/`accept`/`wait`/`mq_confirm`/`mark_persist_queued`/`redis_session_connect`/`sync_total`；禁止订单号/商户号进入 label。 |
| MQ 发布/消费 | messageId、exchange、routingKey、queue、orderId、outOrderSn、attempt、confirm/retry/DLQ。 |
| MySQL 落库 | orderId、outOrderSn、persistSource、persistStatus、事务结果。 |
| outbox/notify | eventId/taskId、eventType/notifyType、status、retryCount、workerId、lockedUntil。 |
| 人工入口 | jobName、shardTotal、shardIndex、limit、workerId、status、耗时。 |

异常日志规则：

| 规则 | 说明 |
| --- | --- |
| 不静默吞异常 | 降级、重试、fallback、返回默认值的 catch 必须记录带堆栈日志。 |
| 高频路径限流 | per-request filter、consumer loop、scheduled scan、hot retry branch 若可能刷爆日志，应使用 warn、采样、批末汇总或共享限流工具。 |
| 直接重抛 | 当前层立即 rethrow 或 wrap 后 rethrow 时，不重复打印同一异常。 |
| 敏感数据 | `app_secret`、`aes_key`、`jwt-secret`、`access-token`、密码、供应商 URL 凭证等只允许出现字段名或占位符。 |

建议告警：

| 指标/信号 | 告警目的 |
| --- | --- |
| Redis WAIT 失败、cancel 失败、HA Guard 关闭 | 防止继续扩大 Redis 状态未知窗口。 |
| MQ confirm 失败率、RabbitMQ 连接缺失、DLQ 积压 | 发现 Redis 成功但 MQ 未可靠接收。 |

| `trade.engine.merchant.profile.cache.hit.total` | 发现商户资料短 TTL 本地缓存未命中偏高，prepare 仍频繁打 `mc_ext_depart`。 |
| `trade.engine.v1.create.stage.duration` | 拆分下单同步路径尾延迟：`prepare`/`accept`/`wait`/`mq_confirm`/`mark_persist_queued`/`redis_session_connect`/`sync_total`。 |
| pending ZSET 积压和最大年龄 | 衡量 MySQL 落库或 MQ 补投延迟。 |
| `trade.engine.dispatch.timer.pending`、`max.pending`、`rejected.total` | 发现进程内履约 timer 积压、达到上限或被迫降级到 outbox 扫描恢复。 |
| `recharge_accept_anomaly` 未处理数量 | 发现状态未知订单。 |
| outbox/notify `MANUAL_REQUIRED` 数量 | 发现供应商/回调长期失败。 |
| 余额对账差异 | 发现 Redis 与 MySQL 资金状态偏差。 |

### V1.2 密钥存储实施约束

以下为2026-10-16商户级密钥方案已落实的实现约束。

本轮实施采用独立的商户当前版本指针表与商户密钥版本表。事务先确保商户指针行存在并加行锁，再读取或首次创建密钥；轮换与撤销使用同一行锁串行执行。版本状态为CURRENT、RETIRED、REVOKED；RETIRED仅允许已签名回调重试，撤销后保留指针且普通getToken不得自动重建。追加0019结构变更，保留已提交0018及其旧字段，旧凭证表与订单绑定字段不再参与新实现；不执行旧数据搬迁或删除。轮换端口只供受控内部维护调用，不增加对外管理接口；维护前后暂停和恢复商户流量由部署流程控制。

- 密钥表保存keyId、商户orgCode、加密signKey、创建时间、版本状态及撤销信息；按商户维护唯一当前版本。appId用于鉴权和审计，不作为每次签发新密钥的理由。同一商户同环境的应用按同一商户密钥口径执行，环境之间隔离。
- 首次初始化在数据库事务或唯一约束保护下完成；同商户并发getToken只能创建一个当前版本，已有版本直接读取。密钥可靠持久化后再发布token；token缓存失败时不返回半套凭证，后续获取仍复用已保存的当前密钥。
- 保留独立部署主密钥及AES-256-GCM存储信封，AAD至少绑定不可变的商户与keyId。主密钥不复用JWT/app_secret/aesKey，跨实例一致，重启保留；签名密钥不存JWT、订单hash或MQ快照，不按token请求到期字段删除或判断其存续。
- 取消订单signing_key_id的协议职责，不再要求受理、MQ、落库及补偿传递此字段。0018包含上一轮实现的该字段并保留结构记录；当前代码已移除订单字段、Redis参数、MQ快照和MyBatis映射，不再读写旧绑定。
- 回调新任务以商户当前版本签名，任务快照持有keyId与原报文；重试以商户和报文keyId加载该版本，只检查商户、轮换状态和撤销状态，不查订单绑定。旧版可标记仅允许已签名回调重试，撤销版则全部拒绝；已有订单在轮换后产生的新任务直接使用新版本。
- 未初始化与已撤销须区分：首次getToken可初始化，撤销后须完成专门的密钥启用流程，不能通过重试getToken悄悄恢复。轮换操作、双方同步及恢复测试期间不包含生产变更，实际联调按docs/集成测试.md留证。


### 名创 MINISO 专属协议实施约束（2026-10-17）

本轮依据用户提供的《名创三方对接文档V1.5 2023-11-22 (3).pdf》（正文首页标1.4）和 `/Users/mac/codespace/cardshop` 的 MCUtils/MINISOSupplierTradeServiceImpl 实施，细化方案见 `docs/superpowers/specs/2026-10-17-miniso-legacy-request-auth-design.md`。以下为本轮已确认的实现合同。

## 交行开放平台通知认证修订 2026-10-19

本节为用户确认的目标设计，优先于本文此前关于交行通知携带 keyId 及业务 HMAC-SM3 的描述；此前描述仅作为现有直连实现背景。交行 2.5 订单通知、2.6 核销及作废通知均走 J_IEP_001_2104，业务正文取消 keyId 和业务 sign，统一由开放平台 RSA/SM2 对包含业务载荷的 biz_content 提供认证。接收业务系统必须只从已通过网关认证并绑定可信商户的链路接收通知，随后验证订单归属、金额、状态、事件时间及幂等；不能将普通公网无签名 JSON 当作可信通知。

商户调用平台的 2.2—2.4 保留 token、HMAC-SM3(signKey) 和原 SM4 请求封装，不增加 keyId。`/v1/cardapi/auth/getToken` 的成功响应 data 仅包含 token、signKey，不再对外返回 keyId；普通刷新不轮换签名密钥。服务端内部 keyId 继续用于商户密钥版本、轮换、撤销及 AES-GCM AAD，不得因取消对外字段而删除表字段、密钥状态或存储加密绑定。开放平台 appId、私钥、银行公钥与商户 signKey 分开管理。

通知任务在事务中保存冻结的业务事实及可信路由，不再依赖商户 HMAC 密钥可用性或生成商户业务签名。订单金额保存为 JSON 整数分，nonce 首次安全随机生成；重试保持业务正文、timestamp、nonce、protocol 和编码结果不变，每次物理投递由 SDK 生成外层 timestamp/sign。历史直连任务按创建时冻结的通道及协议版本处理，不能在重试中静默删除字段或切换通道。银行通道成功条件为 SDK 银行响应验签通过、biz_state=S 且 body.code=200，任务回写须使用租约持有者 CAS。

实施时须按通道拆开 V1MerchantNotifyPayloadSigner、V12RedemptionNotifyPayloadSigner、HttpMerchantNotifyClientAdapter 及名创核销任务生成中的旧 HMAC 前置依赖；getToken 响应和模拟器也须同步。内部 findCurrent、findForCallback、密钥撤销和 AAD 仅按其实际适用范围保留，银行任务不得再因缺少业务 keyId 或商户 HMAC 密钥而拒发。相关注释须引用本节及详细设计 9.4、9.6、9.7。

本次增量仅落实 getToken 响应移除 keyId，内部密钥版本、轮换、撤销及存储加密逻辑不变；模拟器请求客户端接受 token/signKey，旧直连回调缺少可信 keyId 时在发送业务请求前明确拒绝，不从通知报文学习 keyId、不尝试密钥兜底。TODO：按本节完成 2104 通知及模拟器接收链路改造，当前不得将旧直连场景宣称为银行通知验收。此前交付修订设计、接口文档及独立调用方参考包，其余上述业务服务变更尚未实施，亦未部署。本次对接已确认的 trx_data_imprt 格式、长度单位、通知类型及固定网关任务生成规则见下一节；三类通知共用按商户配置的 protocol；本次采用的 msg_id 重试规则见下节。环境参数及银行去重行为仍需在 dev/test 联调验证，当前不得猜测实际参数或启用真实投递。启用前同步更新服务、模拟器、执行样例和集成指引，在《集成测试.md》记录环境和证据。

### 本次交行回调对接确认

本节记录用户在 `feat/bocom-callback` 隔离任务中逐项确认的规则，优先于本文此前与之冲突的旧规则；这里只同步设计，尚未实现或部署。
