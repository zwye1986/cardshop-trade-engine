## 3 名创配置与调度清单

以下是待填实参的配置片段，合并到现有配置，不能覆盖完整DataId。示例是最终准备就绪状态；首次启用须按第2节顺序，先保持callback.enabled=false。占位值不能用于启动。[S3,S6,S8]

```yaml
trade:
  engine:
    supplier:
      http-enabled: true
      miniso:
        enabled: true
        base-url: ${MINISO_BASE_URL:}
        tenant: MINISO
        tripartite: ${MINISO_TRIPARTITE:}
        version: tripartite1.0
        key: ${MINISO_API_KEY:}
        timeout-ms: 3000
        callback:
          processing-enabled: true
          enabled: true
          key2: ${MINISO_CALLBACK_KEY2:}
          batch-size: 100
          retry-backoff-seconds: 60
          max-retry-count: 100
```

四个MINISO环境变量需在所有可接收流量、运行任务的节点配置。现有env.example没有这四项，应补入受限的实际环境文件；start.sh加载环境文件时会自动导出。MINISO_API_KEY和MINISO_CALLBACK_KEY2分别用于主动请求和供应商核销通知，不能混用，也不能复用交行signKey。base-url应为供应商确认的HTTPS源站根地址：当前客户端固定从根路径拼接/tripartite/coupon/，带网关前缀的地址须先核对实际请求路径。[S6,S9]

**XXL任务建议。** 以下频率是单笔功能联调建议，执行前结合现有任务保持一套有效调度，避免重复创建任务。支持分片的任务由调度中心给出一致分片参数；现有三节点可使用分片广播，workerId按实例可区分。[S7,S8]

- rechargeSupplierDispatchJob：建议5秒；推进派单。
- rechargeSupplierQueryJob：建议5秒；处理查单及INVALID_ORDER作废事件。
- rechargeNotifyRetryJob：建议5秒；向交行发送充值及核销通知。
- minisoWriteOffProcessJob：建议5秒；参数limit=100,workerId=miniso-integration；处理核销事实、归属和通知任务。
- rechargeBalanceDeltaFlushJob：建议5至10秒；刷账并核对预扣、释放与MySQL余额。
- rechargePersistMqRepublishJob与rechargeOutboxPublishJob：建议10秒，作为受理消息及outbox恢复兜底。
- rechargeBalanceReconcileJob、rechargeCacheRepairJob、acceptAnomalyAutoCheckJob：按原恢复计划配置；不要在首笔联调时对共享账户强制全量修复。

每个核心任务至少留一份近期成功执行记录，同时查看本轮新增订单或事件是否推进。历史“XXL分片回执正常”不能证明新加入的minisoWriteOffProcessJob已创建并启用。[S1,S7,S8]

建议向交行发一个接入资料包，接口文档与源码包使用同一商户级V1.2版本。下列信息以安全渠道交付，报告内不填写实际密钥。[S10]

8. **核销语义。** 名创实际消费回调在交行侧体现为state_type=3、use_state=2，use_time为名创核销时间，invalid_time为空；与主动“订单作废”分开验收。商户级修订稿已列出3/2定义，开场确认交行对该商品采用此口径。

**我方同时向交行索取：** 调用出口公网IP、回调HTTPS URL及其白名单要求、可控测试手机号、已实现的V1.2版本、响应样本、超时重试策略、是否可验证真实到账和核销状态。没有有效notify_url的订单只能验证发券与查单，不能宣布采购方回调闭环完成。[S3,S11]

## 7 明天的联调顺序与通过标准

**开场前。** 三方确认测试环境、专用租户/商户、允许发券数量、测试手机号、谁执行消费核销和作废、联系人及停止条件。建议第一轮串行执行，每个场景使用独立商户订单号，主动作废与真实消费使用不同券。保留平台订单号、商户订单号、名创orderNo、核销eventId和通知taskId的受控对应关系，不在普通日志输出完整手机号、券码或凭证。

1. **入口与鉴权。** 严格HTTPS通过且路由新服务；交行成功getToken，离线固定向量通过。刷新一次token，验证token变化但keyId/signKey不变，更新调用方当前token。不要多方用同app重复领token互相挤掉凭证。
2. **单笔发券闭环。** num=1、有效batchId、足额测试余额、真实notify_url。交行发单，确认平台受理、MQ落库、派单使用冻结批次及平台orderNo；名创证明发券，平台保存完整凭据及成功终态，充值通知在交行成功验签并幂等入库。
3. **查单与重复请求。** 交行查到同一订单；按协议重试相同out_order_sn，确认不重复发券、不重复扣款。测试重试须遵守当前nonce和签名规则，不能用过期样本报文模拟新请求。
4. **未使用券作废。** 新建独立订单并保持未使用；作废先核对本地及远端凭据，仅对本单券码操作。查单、作废通知及余额释放完成，不能作废其他手机号或其他订单券码。
5. **真实消费核销。** 另建订单，由名创完成一次真实核销并发送mcNotify。先确认入站认证和持久事件，再确认use_time更新、通知任务生成；交行收到state_type=3/use_state=2、实际use_time、空invalid_time、keyId及有效HMAC-SM3。同一事实重投无重复业务效果。
6. **通知失败恢复。** 由交行配合让一笔指定测试通知返回非成功，再恢复接收；平台按原payload/keyId重试，交行幂等确认，task收敛成功。不要直接关闭共享网关或制造整个环境故障。
7. **已核销保护与结果未知。** 已核销券的作废/退款应被保护，不能误释放余额。若名创提供专用可控场景，再验超时/处理中/未知错误码后的查单恢复；未提供时将其列待补，不能宣称所有负向用例已通过。[S6–S8,S11]

**每项留证。** 记录请求时间、脱敏定位ID、接口业务码、DB/Redis状态、供应商侧结果、交行侧接收结果和重试次数。真实执行后追加docs/集成测试.md，标注本次namespace/group、DataId、配置变更与实际使用节点。当前报告是准备材料，不替代执行记录。

**暂停规则。** 证书或路由不符、批次/手机号/凭据错配、重复发券/扣款、已核销仍退款时暂停新单。关闭入口准入或停止指定测试商户，保持查单、核销处理和商户通知恢复；不能关闭名创适配后让未确认订单落回通用mock，也不能把同一平台订单交旧系统重新发券。[S3,S6]

**通过标准。** 至少完成一笔发券、查单、未使用券作废、真实消费核销及双方通知确认；采购方、我方、供应商三方结果一致，余额与凭据可追踪，测试任务无未解释积压。未完成真实核销只算发券链路通过，不算三方全闭环。
