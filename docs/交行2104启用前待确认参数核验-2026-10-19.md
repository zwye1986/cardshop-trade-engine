## 3. 逐项判定

### 3.1 两类通知如何区分及各自 protocol

**判定：真实缺口，必须保留；但不能预设一定使用两个不同 protocol。**

已有依据：

- [B1] 功能描述仅为“名创优品商户出券结果通过金融开放平台通知卡中心买单吧权益中心”，没有核销/作废的区分规则。
- [B1][B5] 请求体只有 `trx_data_imprt` 和 `protocol`，没有独立通知类型字段。
- [B1][B4] 只给出一个 `FWS202604090265` 示例，没有说明它是本项目获配值、如何绑定 appId/商户，或是否同时接收核销。
- 当前 `RechargeOutboxWorkerService.java:1052-1086` 及 `MybatisMinisoWriteOffStore.java:303-310` 有本地 `ORDER_STATUS/VOUCHER_STATE` 类型；它们不是银行接口已定义的字段。

不能据此推导：两个通知必须配置两个不同协议号；可以共用该示例号；可以新增 `notify_type`；银行会自动按字段集合区分。

应确认：实际 protocol、其 appId/商户/环境绑定，以及两类通知共用或分别使用该值时的识别规则。要求各提供一份完整可接收样本即可，不要先强加一种区分设计。

### 3.2 trx_data_imprt 完整编码及长度单位

**判定：真实缺口；但字段类型、最大数值和外层字符集已经明确。**

已明确：[B1][B5] 为 String、必输、最大 2500；protocol 为 String、必输、最大 200；[B1][B2] 报文 UTF-8。`biz_content` 为 JSON，不能把 String 字段擅自变成嵌套对象。

未明确：[B1][B4] 唯一载荷示例为：

```text
order_id:2024051410460831111495,out_order_sn:2024022120200772347024,total_price:1950
```

这说明银行提供了冒号/逗号格式的示例，不能说“毫无格式线索”；但它没有订单状态、账号、核销/作废字段，也没有完整字段顺序、空字符串、冒号/逗号等特殊字符转义规则。它不能证明银行接受完整 V1.2 JSON 字符串，也不足以定义完整的分隔符编码器。

2500/200 没有标明按 Unicode 字符、UTF-16 单元或 UTF-8 字节校验。UTF-8 是传输编码，不自动等于长度按字节。Java DTO 只有 String，没有长度校验实现，无法从 getter/setter 反推银行服务端规则。[B1][B2][B5]

应确认：完整成功/失败/核销/作废样本；精确编码及空值/特殊字符规则；2500 和 200 的计量对象与单位。目标内层不含业务 sign/keyId 已由此前确认，不再重新列为未知。

### 3.3 测试配置和 RSA/SM2 选择

**判定：部分真实，需从“协议不明”改为“实际接入配置待落实”。**

已明确：

- [B1] 测试参考完整地址：`https://open.test.bankcomm.com:9443/api/trade/J_IEP_001_2104/v1`。
- [B1] 不需要 OAuth2，不要求全报文加密；这不免除开放平台 appId、签名及接口权限。
- [B2] 4.8 支持 RSA（SHA256WITHRSA）和 SM2（SM3WITHSM2）。[B4] 给出 RSA 默认演示及 SM2 注释示例；[B7] 明确给出 SM2 配置方法。因此不能将“本接口是否支持 SM2”继续泛列为未知。
- [B4] APP_ID、MY_PRIVATE_KEY 是占位符，须替换为入驻 appId 和登记公钥对应的私钥；银行公钥必须按环境/算法匹配。
- [B6] 2.2.6 的普通构造路径会按银行公钥是否以 `04` 开头选择 SM2/SM4，否则保留 RSA/AES。SDK 自动识别是实现行为，不是本项目已完成算法登记的证明；2104 的不全报文加密约定不因此改变。

实际仍需落实：

- 当前项目已登记的算法、公钥和 appId，是否已开通 2104 权限；若尚未登记，先由双方选定算法并完成入驻。
- 实际联调后台及入口。[B4] 注释按端口区分 UAT/UAT2/UATC/TRL；[B3] 问题十八另给环境后缀方案，并明确先向后台或测试中心确认。不能把示例 9443 不加说明地认定为已绑定本项目的最终环境。
- 配套私钥由本方安全保管，银行不应被要求提供本方私钥。配置及核验不应在分析报告中暴露凭证。

如果这些入驻资料已具备，可由项目配置清单消项，无须再请求银行解释 RSA/SM2 基础规则。

### 3.4 msg_id 及 P/超时恢复规则

**判定：基础定义明确，重试/幂等恢复约定确实缺失。**

已明确：

- [B2] 4.3：msg_id 为必输 String，最大 40，描述为消息通讯唯一标识，示例 UUID；4.5 给出关联字段 ref_msg_id。
- [B4] 单次调用显式传入去连字符的随机 UUID。[B6] 无参 `execute(request)` 也生成这种 32 字符值；显式入参重载使用调用者的 msg_id。
- [B2] 4.5、4.7、6.7 及 [B3] 问题十七：P 表示处理中/未决/未知，不能按成功处理。[B6] `isSuccess()` 只认 S。
- [B6] 默认 prepareParams 按当前 GMT+8 时间生成外层 timestamp，格式 `yyyy-MM-dd HH:mm:ss`；[B3] 问题二十一指出旧外层时间可能触发 OAPICK0023。

未明确：同一业务事件超时重投是否复用 msg_id；重复请求去重键与窗口；返回“重复访问/禁止重复提交”时如何确认前次结果；P 是查结果、继续等待还是重新上送；查结果/人工核对渠道和最终终止条件。[B2] 6.7.3 列有重复及超时错误码，却未给出 2104 的恢复契约。

随机 UUID 示例只证明首次请求的生成方式，不证明“每次重试必须换号”，也不证明 msg_id 就是银行的业务幂等键。FAQ 的一般性“隔几分钟再试”不足以保证结果未知时不重复处理。

应只保留上述恢复问题。保留业务事件身份与原业务载荷，同时更新网关层时效参数，不等于已经确定了 msg_id 重投策略。

### 3.5 银行 ACK 含义

**判定：基础成功判断已明确；可靠接收/最终处理边界确实未明确。**

已明确：

- [B1][B5] 业务回执在 `body.code`，类型 String，`"200"` 明确表示成功。
- [B2] 4.5、4.8：响应为 rsp_biz_content/sign，须验银行响应签名。
- [B2] 4.7 和 [B3] 问题十七：biz_state 是当前平台交互状态；业务体有业务状态时须继续判断业务体。
- [B6] SDK `BocomResponse.isSuccess()` 只比较 biz_state 与 S，不校验 body.code。不能照搬 [B4] 只调用 isSuccess() 的简化演示作为最终业务成功条件。

因此，传输成功、银行响应验签通过、`biz_state="S"`、`body.code="200"` 的判断已有依据，不应再问“200 是不是成功”或要求 SDK 猜测。

尚未明确：此成功由哪一层产生，是否保证权益中心已可靠持久化、是否仅代表入口受理、是否仍需后续结果查询，以及重复事件是否同样成功确认。[B1] 只写“200:成功”，不能证明数据库提交边界。

目标文档 1.6.4 的“业务系统可靠持久化后给出 code=200”应理解为期望契约，不能引用该段来证明银行现有服务已提供此保证。rsp_code 在 2104 文档中也没有固定成功值；[B2] 通用例子同时存在 0000、SC0000，不能硬编码唯一 0000。成功样本及错误分类仍值得索取，但“未知 rsp_code 清单”不等于既有 body.code 成功定义也未知。

### 3.6 固定网关模式下 notify_url 的可空及启用语义

**判定：现状明确；新模式存在真实的契约决策点和漏通知风险，但不是银行 SDK 参数缺失。**

- [B1][B5] 2104 请求体根本没有 notify_url。调用方设置的 serviceUrl 是银行 API 地址，不是本平台下单接口的 notify_url。
- [B8] 和 [B2] 6.6.3 的 notify_url/communication_url 指“交行主动通知第三方”的地址。方向相反，不能拿其 appid@、80/443、解密回执规则解释本平台向银行调用 2104。
- 当前 `RechargeOutboxWorkerService.java:1052-1090` 在订单、作废通知创建前检查 notifyUrl，空值直接 return。
- 当前 `MybatisMinisoWriteOffStore.java:247` 在订单 URL 非空时才创建核销任务；为空只处理核销事实。
- 当前 `HttpMerchantNotifyClientAdapter.java:64-70` 再次拒绝空 URL；`:96-112` 按该 URL 直发 JSON，并读取根节点 code。

因此，现行直连“可空且不产生通知”的语义不是未知。改成固定网关后，如果交行下单不传 notify_url，而平台只新增银行发送器，不同步修改任务入口，就完全没有任务可发送。

应由双方决定：有效银行商户路由是否即表示开启两类通知；notify_url 在银行订单中是忽略、兼容字段，还是保留为显式启用开关；缺路由与主动关闭如何区分。最终目的地必须来自可信路由，不应由任意下单 URL 决定。

可建议“银行路由配置负责目标及启用，notify_url 不控制银行通知”，但这属于建议，尚未获确认，本次不修改现有行为。
