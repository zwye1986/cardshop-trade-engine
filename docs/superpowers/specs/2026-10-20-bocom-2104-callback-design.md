# 交行 J_IEP_001_2104 通知对接设计

日期：2026-10-20。工作区：`.worktrees/feat/bocom-callback`；分支：`feat/bocom-callback`。

状态：对话中的总体方案已获用户批准；本文将其细化为书面设计，待复核后编制实施计划。本文不是已实现、已部署或银行已验收的证明。

## 1. 目标与非目标

为订单结果、实际核销、作废完成增加交行开放平台通知通道，复用 MySQL 通知任务与 Worker，保留原直连通道。一次实现覆盖业务事实生成、可靠任务保存、SDK 投递、结果判定、租约隔离、离线银行模拟器及接入指引。

本次只做离线实现与验证，不部署，不发布 Nacos，不修改真实环境数据，不访问银行或供应商接口。不修改商户请求的 token/HMAC-SM3/SM4 认证，不删除内部 keyId、密钥生命周期及 AES-GCM AAD，不恢复旧卡管 AES 通知签名，不建设独立中转服务。

## 2. 已确认协议

1. 三类通知均调用 `POST /api/trade/J_IEP_001_2104/v1`。`body.trx_data_imprt` 内 `operate_type` 为 `1`（订单）、`2`（核销）、`3`（作废）。订单失败仍属于订单通知，不能映射为作废。
2. `trx_data_imprt` 为 UTF-8 字符串，格式为 `key:value,key:value`，不是 JSON。字段值按业务约束不会含逗号，不发明逗号转义协议。时间值中的冒号保留，解码以每个键值项的首个冒号为界；空值保留为 `key:`。
3. 最大长度为 2500 字符，不是字节。本实现采用 Unicode 码点计数，中文和补充字符分别按一个字符计数；拒绝非法孤立代理项，不截断报文。外层 JSON/form 转义长度不参与该业务字段限制。
4. 银行业务正文不含 `sign/keyId`。网关 SDK 对含业务正文的 `biz_content` 签名，银行响应必须通过验签。
5. 同一商户三类通知共用配置中的 `protocol`，任务创建时冻结；不默认采用 demo 协议号。
6. 交行任务生成不依赖订单 `notify_url`；即使为空仍生成对应通知。实际银行目标仅来自可信配置，不采用下单方 URL。
7. 每次物理投递产生新的无连字符 UUID `msg_id`，正常重试保持任务 ID、业务正文、timestamp、nonce、protocol 和编码结果不变。记录每次请求及银行 `ref_msg_id`。这是用户批准的实施策略，并非银行已明确保证的去重协议；离线测试不能替代银行业务幂等验收。
8. 仅在传输正常、SDK 银行响应验签通过、`biz_state=S` 且 `body.code=200` 时确认成功。兼容业务 code 的字符串和数值 200。不擅自要求 `rsp_code` 等于某个附件未明确的固定成功码。

资料：用户指定目录 `/Users/mac/捷荣金服项目文档/product_mricttrade_api_2121(第三方商户接入买单吧权益中心)_标准版202610` 下的接口输出文档、开放平台接入规范和 2104 demo。示例 appId、协议号、密钥和地址均不是项目默认配置。

## 3. 方案选择与模块职责

采用官方 SDK 2.2.6 的专用适配器；不自研完整网关协议，不另起中转服务。

- **domain**：明确通知操作类型与 1/2/3 映射，保留现有券状态分类，不引入 Spring、数据库或 SDK。
- **application**：集中准备通知业务事实、选择显式通道、生成冻结任务；Worker 只领取、发送和按领取凭证回写，不在重试时重新签名或重新拼接银行正文。
- **infrastructure**：实现可信商户路由、业务编码、SDK 调用、配置绑定、任务及尝试记录持久化。`MerchantNotifyClientPort` 保留为发送 seam，分别使用直连与银行 adapter，由冻结的通道选择，不根据 URL 字符串或供应商名猜测通道。
- **simulator**：独立的银行网关桩校验 form 与网关认证、解析 head/body/业务字段，生成可验签响应；旧 `A39CallbackServer` 只继续承担直连场景。

创建侧统一入口覆盖 `RechargeOutboxWorkerService` 中订单结果与作废完成，以及 `MybatisMinisoWriteOffStore` 中实际核销。银行分支不调用商户 HMAC 密钥存储；直连分支保留现有签名、历史版本和撤销检查。

## 4. 业务事实与编码

业务字段沿用现有订单/核销协议，加上 `operate_type`，不根据 SDK demo 的三个字段删减正式通知字段。字段顺序采用固定白名单：先 `operate_type`，再按对应协议既有字段顺序；只编码该通知类型定义的字段，不混入路由、密钥或内部任务元数据。

- 订单：平台订单号、商户订单号、金额、类型、结算金额、timestamp、nonce_str、订单状态、account。金额在内部结构化快照中保持整数分，在键值文本中输出十进制整数，不加引号、不转换为元、不取供应商成本。
- 核销：保留实际 `use_time`，名创 `state_type=3/use_state=2`，`invalid_time` 为空。
- 作废：`use_time` 为空，`invalid_time` 取既有可信作废事实时间；名创为 3/3，其他直充保留现有领域映射。不将作废变为订单失败，不重置事实时间为重试时间。
- timestamp 在首次创建时冻结，nonce 使用安全随机 16 字节的 32 位十六进制文本。

编码发生在首次创建任务时，结构化业务事实与实际编码文本同时保存。发送前核对可信商户/订单身份、操作类型、路由归属、长度及无业务签名字段等不变量；不通过重新构造 payload 改写历史任务。若业务约束被破坏而出现逗号或超长数据，明确拒绝该报文，保留可靠事件和诊断，不转义、不截断、不按成功跳过。

## 5. 路由、配置与恢复

配置使用 `trade.engine.notify.*`，银行连接参数放在 `trade.engine.notify.bocom.*`。显式商户通道注册与发送 enabled 开关分离：关闭银行发送不使交行商户回退到直连。

- 按可信 `orgCode` 选择通道，配置每商户的 protocol 和路由版本。银行 client 配置包括 appId、签名算法、网关地址、版本化私钥引用、银行公钥引用、连接和读取超时。
- 任务冻结通道、商户、gateway URL、protocol、appId、算法、凭据引用及路由版本；不存明文私钥、商户 signKey 或完整敏感响应。凭据引用必须能明确匹配冻结身份，缺少对应版本时禁止借用其他 appId 或密钥发送。
- 初始默认不启用银行真实发送。真实 dev/test 采用 HTTPS、正常证书与主机名校验；本地离线桩仅在测试隔离配置中允许 loopback HTTP，不复制 demo 的 `ignoreSSLHostnameVerifier()`。
- 交行路由缺失或不完整时，由原有可靠 Outbox/核销事件保留待恢复事实，任务生成不得返回“无需通知”；通过现有重试和人工处置恢复，不因此重复供应商发券、作废或退款。
- 已有冻结任务遇到发送关闭或凭据不可用时保留任务，不视为成功，不切换通道；配置恢复后继续原任务。确定性报文错误与响应验签异常转人工；暂时网络失败及不确定结果按现有退避和上限重试，耗尽转人工。暂停发送不消耗物理发送重试次数，也不能使同一批次热循环。
- 非银行直连仍按原规则处理空 notify_url。历史通道不因后续商户配置变更自动迁移；本次不批量重建历史任务。

## 6. 持久化与租约隔离

追加 Liquibase changeset，不改已执行 changeset 的校验和。任务表增加：

- `delivery_channel`：默认 `DIRECT_JSON`，使既有任务明确保留直连语义。
- `route_snapshot`：不含秘密的路由 JSON，银行任务必须完整。
- `encoded_payload`：银行 `trx_data_imprt` 的冻结文本，使用支持完整 Unicode 的存储；直连为空。
- `claim_version`：每次成功领取递增的租约代次，初始为 0。

`payload` 继续保存业务 JSON 快照：直连为原已签名报文，银行为不带 sign/keyId 的结构化事实。`notify_url` 对银行任务保存经可信路由解析的实际网关目标，订单原 URL 仍留在订单字段，不混用。DTO/实体注释与新增或修订 DDL COMMENT 保持一致。

新增通知尝试记录表，按 taskId、claimVersion、msgId 关联，保存尝试时间、有限结果分类、HTTP/平台/业务状态码及 refMsgId，不保存密钥或正文。先在有效领取凭证下记录本次请求身份，再发送网络请求；无法可靠登记则不发送。无实际 HTTP 的配置等待不伪造物理投递记录。旧 Worker 即使迟到返回也可留下本次尝试的事实，但不能改写新租约的任务状态。

领取返回带 `claim_version`、持有者和租约截止时间的新快照。SUCCESS、FAILED、MANUAL_REQUIRED、配置等待等回写均要求 taskId、PROCESSING、claimVersion、持有者及有效租约匹配。CAS 未命中不计为本 Worker 成功，不清理其他持有者锁。HTTP 总超时预算小于租约，避免正常请求必然跨租约。

空 URL 清理与到期扫描按通道区别处理：仅保留原直连清理语义，银行空目标绝不能被标为 SUCCESS。迁移、单元测试和兼容构造入口都必须显式覆盖此区别。

## 7. SDK 与日志安全

官方 jar 通过项目本地固定 Maven 坐标 `com.bocom:bocom-openapi-sdk:2.2.6` 接入 infrastructure；该坐标不声称已发布于 Maven Central。不使用 systemPath 或个人绝对路径。本次核对的 jar SHA-256 为 `8df82ae2931dd5cc52fcbbea5643cd6819412f27f9cf64478b476c2e53120fad`。提供 SHA-256 校验的 SDK 本地安装脚本与使用说明：输入用户自备银行接入包路径，安装指定 jar 及项目维护的依赖 POM；CI/团队可将同一制品发布到已有受控 Maven 仓库。本次不创建或配置远端制品服务，不提交银行二进制包。

DTO 按附件的 2104 request/response 结构适配，仅引入所需类，不复制整包示例或示例密钥。保留当前受管 Jackson、SLF4J、Logback 和 Bouncy Castle 版本，验证 JDK 21、RSA/SM2、HTTP 超时和启动兼容性，不把银行附带的旧依赖覆盖到 Spring Boot。

第三方 SDK 存在错误日志输出原文的风险。受控屏蔽 SDK/底层 HTTP 的报文及 wire 日志，由项目发送 adapter 使用共享 `LogStormGuard` 写脱敏、限频的异常栈及 taskId/orgCode/orderId/msgId/结果分类。失败记录和日志不输出 account、完整业务载荷、token、signKey 或私钥；不得把原始异常 message 直接落入任务 last_error。

## 8. 测试与验收

按红—绿—重构执行，至少覆盖：

1. 三类 operate_type、字段白名单/空值、时间值冒号、金额整数、随机 nonce、内部 keyId 不泄漏。
2. 中英文及补充字符、2499/2500/2501 字符边界、非法代理项和意外逗号；拒绝而不截断。
3. 订单 notify_url 为空时三个银行入口仍可靠生成任务；无商户 HMAC 密钥也不阻止银行任务。直连原语义不变。
4. 缺路由、缺 protocol、关闭投递、缺凭据版本、配置恢复、配置变更不改冻结目标、历史任务不自动换通道。
5. 真实 SDK 对本地网关桩完成 form/签名/验签闭环；三类业务正常 ACK、平台失败或处理中、业务失败、空 body、空响应、HTTP 非 2xx、超时、响应篡改及错误银行公钥均不得误成功。
6. 同任务多次物理投递 msgId 各异，业务文本及 protocol 不变；尝试记录可关联 refMsgId，不把传输幂等误当作业务不重复。
7. 多 Worker 领取竞争、租约过期重领、旧 Worker 延迟成功/失败/转人工均不能覆盖新持有者；CAS 失败统计不伪成功。
8. Liquibase 在测试数据库初始化并验证旧任务默认通道，DTO/DDL 注释一致，日志脱敏且重复失败限频。
