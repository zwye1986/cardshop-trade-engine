# 名创旧卡管请求与鉴权适配设计

日期：2026-10-17。状态：用户已确认方案，已完成四个主动接口、批次快照及履约凭据的本地实现和回归；入站核销协议待补充，未完成真实名创接口验收。

## 目标与依据

实现旧卡管已有的名创专属请求和鉴权，使新服务具有真实名创协议调用能力。协议依据为 `/Users/mac/Downloads/名创三方对接文档V1.5 2023-11-22 (3).pdf`，共 7 页，文件名标注 V1.5，但首页正文标题为 1.4；核对结论仅适用于这份文件，不能推定它就是供应商当前最新版本。

旧实现依据以用户本轮指定的 `/Users/mac/codespace/cardshop` 为准，核对版本 `169ec049`，涉及 `MCUtils`、`MD5Sign.md5`、`HttpUtils.sendMcPost`、`MINISOSupplierTradeServiceImpl`、`McVoucherListOutServiceImpl` 和 `ExtCommonApi#mcNotify`。四个主动调用接口的路径、请求结构及签名算法与 PDF 基本一致；最多 10 张的限制落实不足，作废业务入口对部分成功的处理不统一，回调使用独立 key2 的约定未在 PDF 中定义。

本轮不修改线上 Nacos、网关、凭证和供应商 URL，不发送真实发券、查单或作废请求。最终验收分为本地协议实现验证和未来真实环境验收，两者分别记录。

## 方案选择

推荐独立 MINISO Gateway 和 HTTP 客户端，通过渠道路由复用现有 `RechargeSupplierGatewayPort`。其它渠道及当前 mock 仍走通用 Gateway；只有显式启用名创专属适配才切换，避免部署后把现有 mock 地址当真实供应商。

备选一是在通用 HTTP Gateway 中加入 MINISO 分支：改动文件较少，但渠道鉴权、明细解析和通用响应语义容易互相影响。

备选二是只新增独立名创 HTTP 客户端、不接入 Gateway：便于单独验证签名，但已有 outbox 派单与查单不能直接使用，不能满足服务实际调用目标。

## 请求与鉴权合同

新增 `trade.engine.supplier.miniso` 配置，包含显式 enabled、base-url、tenant、tripartite、version、key 和 timeout。默认关闭。按 PDF 校验 tenant=MINISO、version=tripartite1.0；tripartite、环境地址和密钥由供应商实际分配，不能从本文示例推断。密钥通过部署环境变量引用，不写真实值到 Git；不复用 V1.2 的商户 signKey、SM4 aesKey 或 JWT secret。启用时严格验证配置与 HTTPS，禁止沿用旧工具忽略证书校验的行为。

请求正文只序列化一次，签名和 HTTP BodyPublisher 使用同一份 UTF-8 JSON 字节，避免重新序列化导致签名与请求不一致。旧协议不对业务参数进行另一次键名排序；JSON 对象采用确定顺序构造，签名覆盖实际传输的完整正文。

签名原文为 `key + "nonce" + nonce + "tenant" + tenant + "time" + time + "version" + version + bodyJson`，计算 UTF-8 MD5，输出 32 字符大写十六进制。tripartite 仅随请求头发送，不额外加入旧签名原文。nonce 使用安全随机的 32 字符小写字母数字串，time 为当前 13 位毫秒时间戳。

每次请求携带 Content-Type、tenant、tripartite、version、nonce、time、sign。不得记录 key、签名原文、鉴权头、完整手机号或券码日志；异常使用现有 LogStormGuard 采样并保留 orderId、操作类型及堆栈。

客户端覆盖旧卡管的四个操作：

- batchGrandCoupon：POST `/tripartite/coupon/batchGrandCoupon`，正文包含 phone、batchList、orderNo；batchList 项包含数字 batchId 和 number。
- queryGrand：POST `/tripartite/coupon/queryGrand`，正文包含 orderNo。
- abandonUserCoupon：POST `/tripartite/coupon/abandonUserCoupon`，正文包含逗号拼接的 couponCodes，单次最多 10 个。
- selectUserCouponList：POST `/tripartite/coupon/selectUserCouponList`，正文包含 couponCodes，单次最多 10 个。提供客户端能力，不新增后台轮询任务或对外 HTTP 接口。

## 与现有履约链路连接

派单的批次映射沿用旧系统 `mc_product.external_product_id -> batchId`，不得重新选择同父产品下的其它子商品。选品阶段同时冻结 selectedProductId、batchId、num 等履约信息，并随既有订单快照、MQ 和落库契约传递；恢复时使用冻结值，不通过商品的最新批次配置重新生成请求。当前直充 num 固定为 1，发送 number=1；orderNo 使用平台 orderId，不使用商户 out_order_sn 或 outbox eventId。读取外部批次和配置的实现放在 infrastructure，不让 application/domain 依赖 MyBatis 或名创细节。

查单始终使用同一平台 orderId。作废先读取本订单已持久化的履约凭据，再通过 queryGrand 确认并逐字段比对完整发券结果，只有本地与远端券码、批次、手机号、有效期一致时才调用 abandonUserCoupon；禁止根据手机号猜测券码或扫描其它订单，也不新建本地卡券库存。作废响应必须确认请求券码全部包含在 data.succeed 中；缺失或部分成功不得触发整单退款。

新适配器遵循详细设计 9.1 的不可确认语义：HTTP 超时、非 2xx、非 JSON、未知业务码、code=200 但明细不完整或数量不符，均不得直接推进失败退款或成功回调。派单结果不可确认进入既有查单恢复链路；查询及作废不可确认沿既有 outbox 退避至人工。

PDF 和旧代码均不能提供完整业务失败码白名单，本轮不凭空增加确定失败码。请求未发送前的无效本地批次映射可以拒绝；远端非 200 业务码默认不可确认。有效发券/查单结果要求 code=200、data 为数组、数量与当前单数量一致，且 batchId、phone、couponCode、beginTime、endTime 与冻结的请求匹配且完整，券码不能重复。PDF 规定 data 为数组；旧代码的 getString(data) 后再解析不足以证明供应商实际返回字符串，因此不将字符串化 data 作为标准协议，只有获得脱敏真实样本并补测试后才增加显式兼容。

不能混用两套券状态：selectUserCouponList 的 state 为 1可用/2核销/3作废；queryGrand 的 status 为 0未使用/1已使用/2已过期/3已作废。发券是否完成与券的后续使用状态分别处理；查单确认已成功发券后，不能因券已使用或已过期就把订单改为发券失败或自动退款。

原始供应商响应继续由现有流水留存，访问和日志均按敏感凭据处理。当前设计仍将名创作为手机号账户直充，不恢复旧卡管库存扣减或本地卡券库存模型，不扩展 V1.2 调用方签名合同。

直充模型仍需要持久履约凭据：保存可信 orgCode/orderId、渠道、批次、券码、有效期及使用状态，支持结果一致性校验、精确作废和核销回调定位。该记录属于履约事实，不提供库存出入库能力；具体表结构在两份主设计文档中确定后再实施。成功终态与完整履约凭据应在同一事务落库，再由持久回调任务推进商户通知，避免状态成功但无法定位券码。

## 旧卡管修正建议

旧卡管修正与新引擎适配分别发布，不能让两个系统同时履约同一订单。本节为建议范围，不表示本轮已经授权修改旧卡管或上线。

1. 统一校验 couponCodes：非空、无空项、无重复，查询与作废单次不超过 10 张，超限明确拒绝。暂不自动拆分超限批次，避免一次操作隐含多次远端变更及部分成功。
2. 统一作废结果处理。沿用后台 nullify 对 succeed/failed 分别解析的正确部分；订单适配器不能以 succeed 非空代表全部成功，monisoAbandon 不能忽略供应商结果直接更新本地状态。所有更新只能针对供应商明确成功且属于请求集合的券码。当前新引擎单券订单只在该券明确作废成功后释放预扣；未来多券订单必须先补齐部分退款设计。
3. 发券结果增加必返字段、批次、手机号、数量及重复券码校验；响应缺失时不能直接成功。网络超时或无法识别的业务码保留结果未知，使用原 orderNo 查单，不自动更换 orderNo 或再次发券。
4. HTTP 客户端明确 UTF-8、连接和读取超时，保持正常证书校验；签名原文、密钥和完整券码不得进入日志。响应原文若为审计所需，受控落库而非日志全量输出。

## 核销回调边界

PDF 3.5 只定义 POST JSON 的 couponCode/useTime；未说明回调签名头、key2、签名正文规范、应答内容或重试周期。旧卡管额外使用 nonce/time/sign 与 key2。不能把该历史约定认定为 PDF 已明确支持，也不能为兼容而直接删除验签。

建议保留旧系统当前回调协议至双方确认，再实现新引擎接收。需要供应商确认：回调密钥是否独立、签名覆盖原始正文还是规范化字段、头字段及编码、成功应答、重试和最长补发期限。历史时间的重试不能简单套用下单的短时间窗拒绝。

确认后采用持久接收记录和事务幂等：先按已确认规则验证，关联可信本地履约凭据并确认订单归属，按渠道/券码/核销事件建立幂等约束；可靠保存后按供应商约定应答，异步推进状态和商户回调，防止重复入账与已核销状态回退。不能因本地券码记录缺失就猜测商户或误处理另一个系统的订单。

本项可独立等待协议补充，不阻塞四个主动调用接口的编码和本地协议测试；真实业务闭环放行前必须具备可靠的核销状态同步及归属方案。

## 实施顺序与放行条件

第一阶段修正协议约束与结果归一化，完成四个主动调用接口、鉴权、配置绑定及本地 fake server 验证。真实名创地址仍关闭。

第二阶段完成冻结批次快照、履约凭据事务保存、精确作废和故障恢复测试；原框架测试与模拟器回归通过，证明接口可调用与业务状态可恢复。

第三阶段补齐回调约定和受控沙箱/测试环境端到端证据，分别验证发券成功、结果未知后查单确认、券状态同步、作废成功/失败、重复回调及重启恢复；在同一份集成测试记录中注明实际 profile、Nacos DataId、数据范围、请求量和证据。

放行真实商户流量前，另行完成有效 HTTPS 入口与实际三节点路由核验、供应商配置和出口 IP 确认，以及明确的人工核查和停止接新单措施。发生不可确认订单时，停止接新单不等于停止查单/回调恢复，更不能把该订单转给旧系统重新发券。
